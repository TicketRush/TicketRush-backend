# 성능 측정 종합 리포트

`load-tests/k6/results/` 아래에 쌓인 부하 측정 회차 **23개**(2026-08-16 기준, `ec2-evidence` 는 회차가 아니므로 제외)를 하나로 묶어 읽는 문서다.

**수치의 SSOT 는 각 회차 디렉토리의 `metadata.txt` 다.** 이 문서는 그것을 회차를 가로질러 읽기 위해 옮긴 것이고, 어긋나면 `metadata.txt` 가 맞다. ADR·이슈 본문·과거 리포트는 출발점일 뿐이다. 실행 절차는 [`load-test-guide.md`](load-test-guide.md), 회차별 상세는 각 회차의 `report.md` 에 있다.

이 문서가 답하는 것은 네 가지다.

1. **병목이 어디로 이동했는가** — 회선 → 컨테이너 메모리 → 호스트 CPU → 유입 제어
2. **무엇이 얼마나 나아졌는가** — 개선별 전/후와 그 값이 나온 회차
3. **어떻게 쟀는가** — 판정 기준을 회차 전에 못 박고, 자기 결론을 실측으로 뒤집어 온 규율
4. **무엇을 아직 증명하지 못했는가** — 하드웨어·재현·확장의 한계

측정 대상은 **단일 EC2 `m7i-flex.large`(2 vCPU / 7.6 GiB)** 이고, 그 위에 앱 8개와 MySQL·Redis·Kafka·Prometheus·Grafana 가 함께 올라가 있다([ADR 0006](adr/0006-eight-gib-container-memory-limits.md) · [ADR 0007](adr/0007-observability-stack-colocation.md)). **그래서 이 문서의 수치는 "SLO 를 달성했다" 가 아니라 "이 구성의 최대치와 그 상한을 만드는 자원이 무엇인가" 로 읽어야 한다.**

> **인스턴스 타입이 `metadata.txt` 에 기재된 회차는 23개 중 14개(#505 이후)이고 전부 `m7i-flex.large` 다.** 그보다 앞선 9개 회차(#346 · #344 · #347 · #345 · #402 · #489 · #348 · #496 · #403)에는 기재가 없어, 같은 인스턴스였다고 **단정하지 않는다.** ADR 과 이슈 본문에 적힌 `m7i.xlarge`(4 vCPU / 16 GiB)는 #505 가 IMDSv2 로 확인해 **오류로 정정한 값**이므로 소급 근거로도 쓸 수 없다.

### 이 문서의 용어

| 용어 | 뜻 |
|---|---|
| **무릎** | 도착률을 올려도 처리량이 따라오지 못하고 지연·실패가 꺾여 올라가는 지점 |
| **N 계단** | 도착률이 N/s 인 부하 계단. "N번째 계단" 이 아니다 |
| **`admit-rate`** | 대기열이 초당 예매 서버로 들여보내는 인원(`queue.admit-rate-per-second`) |
| **판정창** | 램프와 무부하 꼬리를 뺀, 그 회차의 판정 구간(회차마다 다르다) |
| **공통창** | arm 끼리 비교하려고 고정한 구간. 이 문서에서는 `t+30–300s` |
| **코호트** | 한 arm 에서 실제로 여정을 끝까지 탄 사람의 집합. 계단·arm 마다 다르다 |
| **`DEFERRAL_RATIO`** | 램프 종료(t+300s) 이후에 처리된 예매의 비율. 대기열이 유입을 **뒤로 미룬 몫**이다 |
| **드레인율** | 적체가 줄어드는 기울기, 즉 초당 소비 건수 |
| **arm** | 한 회차 안에서 변수를 바꿔 나눠 돈 구간(`ON`/`OFF`, `A`/`B`, `a12`/`b12` 등) |

회차는 `#번호` 로 부른다. 그 회차를 만든 이슈 번호이고, **회차 ID 전체 목록은 [부록 A](#부록-a-회차-색인) 에 있다.**

## 1. 병목이 어디로 이동했는가

회차를 시간순으로 나열하지 않는다. **벽이 옮겨간 순서**로 엮는다. 각 칸은 앞 칸의 벽을 치웠더니 다음 벽이 드러난 자리다.

### 1.1 첫 벽은 앱이 아니라 회선이었다 (#348)

좌석맵 응답이 **220,990 B** 였다. 2,080석에 좌석당 107.6 B 이고 압축이 걸려 있지 않았다.

그래서 스모크(browse 10→30→60/s)에서 **클라이언트가 본 좌석맵 p95 는 34.97초**인데 **같은 구간 서버 처리 avg 는 81.96ms** 였다. 35초는 전부 전송 대기였다. 회선이 먼저 막혀 **앱의 무릎에 도달하지도 못했다.**

같은 회차에서 계단식(browse 2→4→8→10/s, 각 5분)으로 회선을 피하자 실패 **0.00%(0/40,597)**, 좌석맵 p95 **92.57ms** 로 떨어졌다. 두 결과의 차이가 곧 "회선이 벽이었다" 는 증거다.

> 이 회차 수치는 nginx `worker_connections` 가 Ubuntu 기본값 768 이던 시절의 것이다(§2 참조).

### 1.2 회선을 풀자 컨테이너가 죽었다 (#505 → #509)

gzip 을 적용하자 좌석맵 단발 응답이 **174,615 B → 8,405 B(95.19% 절감, 20.8배)** 가 됐다(#505, 같은 배포본에서 `Accept-Encoding` 만 토글해 확인).

> 이 174,615 B 를 §1.1 의 220,990 B 와 이어 "220,990 → 8,405" 로 읽으면 안 된다. **두 값은 회차가 다르고 그 사이 좌석 상태가 달라졌다**(#505 `metadata.txt` 가 명시). 압축비는 #505 안에서 같은 응답을 두 번 받아 얻은 값이다.

회선이 풀리자 부하를 더 밀어 넣을 수 있게 됐고, **80 iter/s 스모크에서 seat-service 가 cgroup OOM 으로 죽었다** — HTTP 500 **1,073건**(전부 좌석맵), `dmesg` anon-rss 641,288 kB, RestartCount 1.

처방(#509)은 메모리 상한을 올리는 것이 아니라 **쓰는 쪽을 줄이는 것**이었다. Tomcat `max-threads` 200 → **50**, JVM 상한 명시(`-Xmx384m -XX:ReservedCodeCacheSize=64m -XX:MaxDirectMemorySize=64m`), `mem_limit` 640m 은 그대로. 결과는 peak RSS **571.8 MiB / 640(89.4%)**, 재시작 0, 실패 **0.00%(0/41,542)**.

> peak 시점의 힙 148 + 논힙 211 = 359 MiB 인데 실제 RSS 는 571.8 MiB 였다. 차 약 213 MiB 는 스레드 스택 쪽이다(같은 시점 `jvm_threads_live` 153). **스레드 수를 줄인 것이 메모리 처방이 된 이유가 여기 있다.**

### 1.3 다음 벽은 호스트 CPU였다 (#509)

OOM 이 사라지자 **CPU 가 스레드보다 먼저 찼다.**

같은 회차의 `timeline-ramp.csv` 를 보면, **06:43:00 에 호스트 CPU 가 이미 95.66% 인데 Tomcat busy 는 0/50 이고 k6 는 63.6 rps** 였다. busy 가 50/50 에 닿은 것은 그로부터 2분 30초 뒤인 06:45:30(193.4 rps)이다. **스레드가 포화하기 한참 전부터 CPU 가 차 있었다.** 같은 시점 회선은 상한의 19%(peak ens5 TX 1.12 / 관측 상한 5.8 MB/s)밖에 쓰지 않았다.

> **회차 리포트의 "CPU 99% 도달 06:43:00" 은 그 회차의 `timeline-ramp.csv` 와 어긋난다.** 해당 표본은 95.656% 이고, CPU 가 99% 를 처음 넘는 표본은 06:45:15(99.156%)라 busy 포화(06:45:30)보다 15초 앞설 뿐이다. 여기서는 원자료를 따랐다. **"CPU 가 스레드보다 먼저 찬다" 는 결론 자체는 바뀌지 않는다** — 근거가 "99% 도달 시각 차" 가 아니라 "busy 0/50 인 구간에서 이미 CPU 95.66%" 로 옮겨갈 뿐이다.

이후 회차들이 같은 결론을 반복한다. #344 동일 좌석 경합에서 호스트 CPU peak **99.87%**, #403 좌석 집계 3,000석 계단에서 **99.97~100.00%**, #539 좌석맵 캐싱 전 80 계단에서 **99.74%**. **2 vCPU 단일 인스턴스에서 상한을 만드는 자원은 일관되게 CPU다.**

### 1.4 최적화로 벽을 두 번 밀었고, 남은 몫이 없다는 것을 확인했다 (#529 · #539 · #534)

CPU 가 상한이라고 해서 곧바로 대기열로 간 것이 아니다. **먼저 앱을 두 번 빠르게 만들어 벽을 밀었다.**

- **커버링 인덱스**(#529) — 좌석 집계의 좌석당 비용을 71.0% 줄여 포화 계단이 **240 → 480** 으로, 240 계단 서버 응답이 **122.61ms → 3.59ms** 가 됐다.
- **좌석맵 JSON 캐싱**(#539) — 80 계단 서버 응답이 **741.04ms → 10.11ms(73배)**, 무릎이 60 계단에서 **100 계단에서도 미도달** 로 밀렸다.

그다음 **더 밀 수 있는 몫이 남았는지를 직접 쟀다.** #534 가 좌석 집계의 고정항(약 1.5~1.7ms)을 JFR 로 분해한 결과는 프레임워크 CPU 48.6% / DB CPU 24.1% / 미분류 17.1% / DB 대기 9.6% / **앱 코드 0.7% / 커넥션 획득 0.0%** 였다. **우리가 고칠 수 있는 몫이 1%도 되지 않는다.**

> 그래서 "최적화로는 못 넘는다" 는 포기가 아니라 **측정 결과**다. 두 번 밀어 봤고, 세 번째로 밀 자리가 어디인지 재 봤더니 없었다.

### 1.5 CPU가 상한이면 남은 수단은 유입 제어다 (#549)

앱 쪽에 남은 몫이 없다면 다음 수단은 들어오는 양을 줄이는 것뿐이다. 거기서 대기열이 나왔다([ADR 0009](adr/0009-virtual-waiting-room-with-server-directed-polling.md)).

#549 B-2 는 그것이 작동하는지를 하나의 판정축으로만 봤다 — **"예매 서버 RPS 가 유입 1만 VU 와 무관하게 `admit-rate`(20) 부근에서 평평할 것."** 판정창(t+300~500s) 표본 14에서 **min 19.60 / avg 20.17 / max 21.00**, 회차 전에 선언한 밴드(10–30) 이탈 0건이었다. 호스트 CPU max **79.53%**, 오버셀 **0행**(예매 9,276 = 좌석 9,276 = 사용자 9,276).

### 1.6 대기열이 하는 일과 하지 않는 일을 갈랐다 (#554)

대기열이 있는 회차만 돌면 "대기열 덕분" 인지 알 수 없다. #554 는 **같은 배포본에서 `QUEUE_ENABLED` 하나만 토글해** ON/OFF 를 연속 실측했다.

| 축 | ON | OFF | |
|---|---|---|---|
| 게이트웨이 총 RPS (공통창 max) | 444.6 | 100.5 | **4.4배** |
| 사용자당 폴링 횟수 (avg) | 16.22 | 1 (min=med=max) | **16배** |
| 이연율 `DEFERRAL_RATIO` | 47.01% | 18.73% | 2.5배 |
| 오버셀 | **0행** | **0행** | 불변 |

> OFF arm 의 폴링이 0이 아니라 1회인 것은, 대기열을 꺼도 클라이언트가 상태를 한 번은 확인하고 곧바로 통과하기 때문이다(min=med=max=1).

**대기열은 유입을 이연시키는 장치이고, 그 대가로 서버 부하를 4.4배 만든다.** 그리고 **대기열을 꺼도 오버셀은 0행이었다** — 정합성을 지키는 것은 `@Version` + Redis 락이지 대기열이 아니다.

**부하가 4.4배인데 왜 이것이 해법인가.** 늘어난 몫이 전부 **값싼 폴링 경로**로 갔기 때문이다. 비싼 예매 경로는 `admit-rate` 로 묶여 §1.5 의 판정창처럼 평평하게 유지된다. 즉 대기열은 총 요청 수를 줄이는 장치가 아니라, **비싼 요청을 시간축으로 펴고 그 대신 싼 요청을 늘리는 교환**이다.

> 이 칸의 결론은 "대기열을 넣어서 해결됐다" 가 아니다. **대기열이 하는 일(유입 이연)과 하지 않는 일(정합성 보장)을 갈랐다** 는 것이다. 이 회차가 대기열이 붕괴를 막는다는 것을 증명할 수 없다는 사실도 회차를 돌기 전에 적어 두었다(§3.3).

### 1.7 다이얼을 돌려 무릎을 잡았다 (#555)

#554 까지의 회차는 `ramping-vus` 라 실효 도착률이 상수인 **단일 동작점**이었고, 원리상 스윕이 아니었다. #555 는 전 여정을 `ramping-arrival-rate` 계단으로 옮겨 `queue.admit-rate-per-second` 를 실제로 돌렸다.

| arm | admit | 예매 서버 RPS (판정창 avg) | 호스트 CPU avg / max | 좌석맵 성공률 | 폴링 p95 | 판정 |
|---|---|---|---|---|---|---|
| `b12` | 12 | 8.22 | 34.70% / 61.89% | 99.49% | 2.03s | **통과** |
| `b16` | 16 | 9.84 | 70.89% / 90.53% | 63.51% | 30.95s | **첫 포화** |
| `b20` | 20 | 13.02 | 61.30% / 95.91% | 73.26% | 40.23s | 무릎 위 |

> **arm 이름의 `a`/`b` 는 시리즈다.** 회차 도중 TCP 백로그 설정을 고쳐 대상이 달라졌기 때문에 두 시리즈로 갈렸고, **서로 잇지 않는다**(§2.1 · §4). 위 표는 수정 뒤인 b 시리즈다.
> **표의 모든 값은 계단별 판정창 기준이다.** 판정은 사전 확정한 `STOP_RULE` — "첫 포화 계단을 찾고 그 아래 한 계단이 통과하면 종료" — 를 따랐고, 포화의 신호는 좌석맵 성공률 붕괴(99.49% → 63.51%)와 폴링 p95 급등(2.03s → 30.95s)이다.

**무릎은 12와 16 사이이고, 그때까지 운영값이던 20은 무릎보다 위였다.** §1.5 가 admit 20 을 통과로 본 것은 **다이얼이 없는 단일 동작점에서였고**, 계단으로 돌리자 그 판정이 좁아졌다.

그리고 **무릎을 만든 것은 admit 자체가 아니라 admit 에 비례해 커지는 SSE 팬아웃이었다.** 같은 admit 16 에서 구독자만 0으로 둔 대조(`a16-nosse`)를 보면 분명하다.

| 축 | `a16` | `a16-nosse` |
|---|---|---|
| 좌석맵 성공률 | 63.06% | **100.00%** |
| 대기열 상태 p95 | 2.73s | **180.25ms**(15.1배) |
| 호스트 CPU avg / max | 64.61% / 98.39% | **33.65% / 73.22%** |
| 예매 서버 RPS (판정창 avg) | 9.98 | 9.95 |

**구독자를 뺐더니 CPU 가 절반이 됐는데 예매 처리량은 그대로였다.** 무릎의 축은 예매 경로가 아니라 좌석 SSE 팬아웃이다. **그런데 처방은 팬아웃이 아니라 `admit-rate` 20 → 12 다**(ADR 0009 §3.5) — 팬아웃 크기가 `admit` 에 비례해 커지므로, **지금 손에 있는 다이얼이 `admit` 뿐이기 때문이다.** 팬아웃 자체의 구독자당 비용을 낮추는 것은 별건으로 남아 있다.

완주(좌석맵 통과 + 예매 성공)를 기준으로 1만 명 소요시간을 다시 세면 같은 결론이 더 분명해진다. **이 값들은 실제로 1만 명을 넣어 잰 것이 아니라 2,772–3,867명 실측을 선형으로 늘린 외삽이고, 낙관 쪽으로 치우친 하한이다(§4).** 그 전제 위에서 — **`admit 16` 은 두 시리즈 모두 12보다 느렸고**(`a16` 32분 24초 · `b16` 28분 53초 대 `a12` 21분 32초 · `b12` 24분 38초), 같은 `admit 16` 에서 구독자만 100 → 0으로 두면 **32분 24초 → 18분 32초** 다 — **팬아웃이 주 지표를 1.75배 늘린다.** 그리고 `admit 20` 은 기대값이 아니라 분산이 문제였다(`b20` 18분 59초 ~ `a20` 48분 46초, **2.57배**. 12의 편차는 1.14배). **티켓 오픈은 재시도가 없는 일회성 이벤트라 기대값이 아니라 최악값으로 설계한다.**

> 회차 전에 적어 둔 예측 `PREDICT_KNEE=25~30/s` 는 **틀렸다.** 값도 낙관 쪽으로 틀렸고, 예측이 지목한 축(좌석맵 CPU)도 틀렸다. 예측을 지우지 않고 틀린 채로 남긴 이유는 §3.5 에 있다.

## 2. 무엇이 얼마나 달라졌는가

**모든 행이 개선은 아니다.** 대기열 ON/OFF(#554)의 `4.4배` 는 이득이 아니라 **치른 대가**이고, `keepalive`(#546)와 `admit-rate`(#555)는 전/후가 아니라 **판정**이다. `전 → 후` 열을 방향 없이 "좋아진 폭" 으로 읽지 않는다.

### 2.1 이 표를 가로로 잇지 않는 이유

- **배포본이 다르면 차이의 출처를 못 가른다.** #549 B-2 는 `21d2da2d`, #554 는 `b0f3da84` 이고 그 사이에 **프로덕션 코드만** 134파일 +5,765줄이 들어갔다(측정 산출물까지 포함하면 훨씬 크다). 두 회차의 절대값을 직접 비교하지 않는다.
- **nginx 세대가 다르면 무엇을 쟀는지가 다르다.** `worker_connections` 는 **#546 회차 직전까지 Ubuntu 기본값 768** 이었고 그때 **16,384**(`worker_rlimit_nofile` 65,535)로 올렸다(#549 · #554 · #555 모두 유지). 프록시 요청 1건이 슬롯 2개를 쓰므로 768 은 실질 동시 요청 약 768 이었고, **#546 회차 A 는 1,600 슬롯이 필요해 조치 전이었다면 앱이 아니라 nginx 를 쟀을 회차였다.**
  - **768 세대에 속하는 회차는 #546 보다 앞선 것 전부다** — 증적이 명시적으로 표시한 #348 · #403 · #529 뿐 아니라 **같은 날 #546 보다 먼저 돈 #539 · #540 도 포함된다.** 특히 #539 의 100 계단은 VU peak 1,045(슬롯 약 2,090 요구)라 **"무릎 100 미도달" 에 nginx 몫이 섞였을 가능성을 배제할 수 없다.**
- **#555 는 시리즈 A 와 B 도 잇지 않는다.** 회차 도중 TCP 백로그 설정을 고쳤기 때문에 대상 자체가 달라졌다(§4).
- **수치에는 창을 함께 적는다.** 같은 지표라도 판정창의 avg 와 공통창의 max 는 다른 질문에 답한다. 이 규칙이 생긴 이유는 §3.6 에 있다.

## 3. 어떻게 쟀는가

이 절은 수치가 아니라 그 수치를 얻은 절차를 적는다. 회차가 스스로를 무효로 판정할 수 있어야 수치가 근거가 되기 때문이다.

### 3.1 판정 기준을 회차 전에 커밋한다

결과를 보고 기준을 고치지 않기 위해, 판정축과 무효 기준을 **회차 시작 전에** 커밋한다.

커밋 `dbf2ee52` 는 #549 B-1 시작 전에 만들어졌고 **`metadata.txt` 한 파일만 +109줄** 바꾼다. 주 판정축 하나(예매 서버 RPS 가 `admit-rate` 20 부근에서 평평, 밴드 10–30)와 무효 기준 6개가 그 안에 있다. 회차 전 커밋이라는 규율 자체는 이후에도 이어진다 — #554 는 `57930b89`, #555 는 `7ce665b0`(다만 이쪽은 런북·시딩 스크립트를 함께 바꿔 단일 파일 커밋은 아니다).

### 3.2 기준을 어긴 회차를 스스로 폐기한다

#549 **B-1 은 무효 처리됐다.** 사전 선언한 무효 기준 2개를 동시에 위반했기 때문이다 — `queue_status_unavailable` **15.55%(13,141/84,469)**, `entry_token unavailable` 300건. **남은 13분을 돌리지 않고 중단했다.**

폐기한 회차의 원자료를 지우지 않고 `k6-summary-b1-invalid.txt` 처럼 `-b1-invalid` 접미사로 함께 커밋했다. 폐기 판단 자체가 증적이기 때문이다.

### 3.3 부하 모델을 회차 전에 산술로 확정한다

실행 전에 "이 회차가 무엇을 잴 수 있는가" 를 알기 위해, 도착률을 먼저 산술로 못 박는다.

#554 §1.1 은 `ARRIVAL_RATE = 10,000 VU / 300s 램프 = 33.33 여정/s` 에서 출발해 게이트웨이 RPS 를 예측했고, 세 번 대조했다.

| 검증 대상 | 예측 | 실측 | 오차 |
|---|---|---|---|
| #549 B-2 총 요청 수 | 약 167,000 | 167,083 | 1% 미만 |
| #549 B-2 게이트웨이 RPS max | 453 | 434.36 | 4.1% |
| #554 ON arm 게이트웨이 RPS max | 453 | 444.6 | **1.9%** |

**그래서 "이 회차는 대기열이 붕괴를 막는다는 것을 증명할 수 없다" 를 돌기 전에 적을 수 있었다.** 결과가 나온 뒤에 변명한 것이 아니다.

### 3.4 자기 결론을 실측으로 뒤집는다

| 뒤집힌 것 | 무엇이 뒤집었나 |
|---|---|
| `R = 1,400`(대기열 상태 경로 처리 용량) | **`R` 은 상수가 아니라 동시 커넥션의 함수였다.** 커넥션 약 1,600(#546)에서 1,400 RPS, **16,701(#549 B-1)에서 450 RPS** — 3.1배 차. → **`R = 400` 으로 정정**(ADR 0009 §3). 1,400 은 "이 구성에서 도달한 값" 으로 조건부 보존하되 폴링 주기 산식의 입력으로는 쓰지 않는다 |
| `admit-rate = 20` | #555 계단 실측 → **12**(ADR 0009 §3.5). 근거였던 #344 의 "258 RPS" 는 **98.61%(94,359/95,684)가 409 반려**라 실제 예매는 약 3.3 RPS 였다 |
| #504 의 "concurrency 를 올리면 약 1.4배" 추정 | #598 실측 **2.25배** 로 기각. iowait 을 작업 용량으로 오산한 것이 원인이고, 고쳐 계산하면 약 90/s 로 실측 96.6/s 에 근접한다 |
| ADR 0010 (부하 생성기를 AWS 안으로 옮긴다) | **기각됨**(2026-08-01, #549 실측). "가정용 업로드 대역이 상한이 된다" 는 가정에 맞서 1만 VU 커넥션 프로브가 실제로 쓴 양은 **0.6 Mbps**, 본 회차는 41 kB/s 였다. **재는 데 6분 30초와 비용 0이 들었다** |
| "#403 의 전파 1.25s 는 5초 폴링과 맞지 않는다" | #533 이 outbox 원본 행의 `published_at - created_at` 을 직접 재서 **불일치가 실재하지 않음**을 확정했다. 1,250ms 는 100 구독자 구간의 p95 시간평균이었고 전체 p95 는 3.87s 다. 균등분포(0,5s) 기대치와 오차 −5.2% / +1.7% 로 **폴링 주기가 지배항**이다 |

### 3.5 틀린 예측을 틀렸다고 남긴다

**#554 의 `DEFERRAL_RATIO` 예측은 3.3% 였고 실측은 18.73% 였다.** 이것을 "회차 무효" 가 아니라 **"예측 실패"** 로 처리했다.

근거는 두 가지다. 첫째, 빗나간 이유를 특정할 수 있었다 — "마지막 VU 가 t+300+약 10초에 끝난다" 를 전제했는데 램프 종료 시점에 아직 진입·폴링 중인 VU 가 많아 실제로는 66초에 걸쳐 마무리됐다. 둘째, **회차의 목적인 ON/OFF 분리는 그대로 성립했다** — 47.01% vs 18.73%(2.5배), 지속 237초 vs 66초(3.6배). 예측한 13배는 아니었지만 방향과 분리는 확인됐다.

**#555 의 `PREDICT_KNEE=25~30/s` 도 같은 규율로 남겼다.** 실측 무릎은 12–16 이라 값이 낙관 쪽으로 틀렸고, 예측이 지목한 축(좌석맵 CPU)도 실제 축(SSE 팬아웃)과 달랐다. 회차를 무효로 돌리는 대신 예측과 실측을 나란히 남겨, **다음 회차가 무엇을 잘못 모형화했는지 알 수 있게 했다.**

예측을 사후에 고쳐 맞춘 것으로 만들지 않는다.

### 3.6 증적의 종류마다 답할 수 있는 질문이 다르다

두 번의 오독이 이 규칙을 만들었다.

**#554 — 시계열 덤프는 곡선의 모양을 주지 않는다.** 대조표에 "MySQL 컨테이너 메모리 max — ON 83.67% vs OFF 100.00%, OFF 가 예매를 1.67배 빠르게 밀어 넣는다" 로 적었다가 틀렸다. **인프라 컨테이너 Grafana 캡처를 추가로 찍어 보니 ON arm 중에 차올라 내려오지 않은 것**이었다 — arm 순서 효과이지 ON/OFF 차이가 아니다. 공통창(t+30–300s)이 아직 차오르는 중인 구간이었기 때문에 덤프의 max 만으로는 가릴 수 없었다. 해당 행은 대조표에서 삭제했다.

**#598 — 화면에서 걸러 낸 것은 없는 것이 아니다.** 0만 나오는 시리즈를 `skipzero` 로 걸러 놓은 탓에 HikariCP `pending` 이 "시계열 없음" 으로 보였고, 그대로 "되돌릴 조건 1 미발동" 이라고 리포트에 썼다. 덤프를 다시 열어 **max 71** 을 발견하고 정정했다.

> 그래서 이 문서는 수치마다 **"그 값이 어느 창의 무엇인가"** 를 함께 적는다.

**지표 자체가 틀려 있던 경우도 기록으로 남겼다.** #345 에서 `ticketrush_seat_held` 는 미만료 HOLD 만 세기 때문에 전 구간 0.00 이었고, #504 에서 `kafka_consumer_fetch_manager_records_lag` 는 backlog 곡선으로 쓸 수 없어 브로커 축으로 갈아탔다.

### 3.7 관측 행위가 관측값에 잡힌다

2 vCPU 호스트에서는 **SSH 세션 자체, `docker stats`, `docker inspect`, Prometheus range query 가 전부 호스트 CPU 에 나타난다.**

#554 의 무부하 기저 측정에서 이것만으로 **`max 57.55%`** 가 찍혔다. 같은 순간 `docker stats` 의 컨테이너 CPU 합계는 13%, `load average` 는 0.10 이었다 — 원인은 측정자였다. **명령을 던지지 않은 창에서 기저는 약 7%** 로 일관됐다(min 6.63 / avg 7.03 / max 7.57).

그래서 회차 중에는 대상 서버로 명령을 던지지 않는다. **회차 전 무부하 기저를 5분 재는 동안에도 마찬가지다.** 상세는 [`load-test-guide.md`](load-test-guide.md) §16.6 에 있다.

### 3.8 before 를 과거 회차에서 빌리지 않는다

성능 변경의 before 는 새로 뜬다. 런타임에 켜고 끌 수 있는 변경(인덱스 DDL 등)은 **before 회차 뒤에 적용**해 같은 이미지에서 짝을 만든다 — #529 가 이 규율의 실물이고, #403 을 before 로 쓰지 않은 이유도 그 회차에 적혀 있다. 코드 변경이라 그럴 수 없으면 배포 전후로 가르고 **그 불확실성을 리포트 한계에 적는다.** 규약 전문은 [`load-test-guide.md`](load-test-guide.md) §6.1 에 있다.

## 4. 한계 · 미검증 축

**이 문서의 어떤 수치도 "1만 명을 처리했다" 를 뜻하지 않는다.** 그렇게 읽히지 않도록 아래를 같은 문서에 둔다.

| 축 | 상태 |
|---|---|
| **하드웨어** | 단일 EC2 `m7i-flex.large`(2 vCPU / 7.6 GiB)에 앱 8개 + MySQL·Redis·Kafka·관측 스택 동거. 결과는 "이 구성에서 도달한 지점" 이지 시스템의 한계가 아니다. **인스턴스 타입이 증적에 기재된 회차는 23개 중 14개다**(리드 참조) |
| **CPU 는 버스터블 CPU다** | `m7i-flex` 는 **베이스라인 40% CPU + 24시간 창의 95%까지 버스트** 하는 인스턴스다. 이 문서의 중심 주장이 "상한을 만드는 자원은 CPU" 인데, **그 CPU 는 크레딧의 영향을 받는다.** 개별 회차(15~25분)는 허용량 안이지만 **연속 회차나 장시간 창에서는 스로틀이 섞였을 수 있고, 이 축은 따로 측정하지 않았다.** #505 가 남긴 규칙 — "CPU 가 설명 없이 40% 부근에서 천장을 치면 앱이 아니라 flex 스로틀을 의심할 것" |
| **"1만 명 동시 대기" 는 재현되지 않았다** | 실측 최대 동시 대기는 **#549 B-2 가 3,254명**, **#554 가 약 4,000명**이다(실효 코호트는 #549 9,276명 / #554 ON 9,781명 · OFF 9,545명). 두 회차 당시 `journeyDone` 1회 여정 가드 때문에 유입이 "1만 동시" 가 아니라 `10,000 / 300s = 33.3 여정/s` 였기 때문이고, **램프를 그보다 빠르게 하면 #549 B-1 처럼 CPU 에서 무너진다 — 이 하드웨어에서 둘은 동시에 만족되지 않는다.** (가드는 #555 가 `ramping-arrival-rate` 로 옮기면서 제거됐다) |
| **#555 의 1만 명 소요시간은 외삽이다** | **완주(좌석맵 통과 + 예매 성공) 기준 18분 32초 ~ 48분 46초.** 실제로 1만 명을 넣은 것이 아니라 2,772–3,867명을 넣고 얻은 처리율을 선형으로 늘린 값이고, 리포트 자신이 **"낙관 쪽으로 치우친 하한 추정"** 이라 적었다. 완주자 수 자체도 두 성공 집합이 완전히 겹친다고 본 상한(`min`)이라 **상위 계단 쪽에 유리하게 기울어 있다** |
| **무릎은 찾았지만 조건부다** | #555 는 여러 한계를 함께 선언했고, 그중 결론에 직접 걸리는 것은 — 유입의 17–20%가 전송 계층에서 유실(`LIMIT_GENERATOR`), admit 16 이 20보다 **뒤에** 실행돼 순서 효과를 배제하지 못함(`LIMIT_ORDER`), 계단마다 코호트가 다름(`LIMIT_COHORT`), **여정이 좌석맵 실패를 예매로 전파하지 않아 주 지표가 좌석맵 붕괴에 구조적으로 둔감함**(`LIMIT_JOURNEY_SEATMAP`), a12·a20 k6 시계열 결측(`LIMIT_K6_TIMESERIES`)이다. 마지막 항목 때문에 회차는 **완주자 기준으로 주 지표를 다시 세어** 보정했고, 그 축에서도 같은 판정이 나왔다 |
| **벽은 nginx 아래에도 있었다** | #555 에서 `worker_connections`(16,384)는 통과했는데 **그 아래 계층**이 벽이었다 — nginx `:443` accept 백로그 **511**(`listen` 에 `backlog=` 미지정), `net.ipv4.tcp_max_syn_backlog` 512, SYN 큐 초과를 뜻하는 `TcpExtTCPReqQFullDoCookies` **15,826**. `backlog=4096` / sysctl 8192 로 고쳤고 **CD 가 배포하지 않으므로 수동 적용**이다(`deploy/nginx/api.ticketrush.store.conf`, `deploy/sysctl/99-ticketrush.conf`) |
| **수평 확장은 미검증** | `deploy/docker-compose.prod.yml` 에 `replicas`·`deploy:`·`scale` 이 하나도 없고 서비스마다 `container_name` 이 박혀 있어 구조적으로 스케일아웃이 막혀 있다. 좌석 SSE emitter 는 인스턴스 로컬 `ConcurrentHashMap` 이라(`SeatStatusSseEmitterRegistry`) 다중 인스턴스 브로드캐스트가 없다 |
| **병렬 소비는 측정됐다** | #598 — booking 드레인율 **43.0/s → 96.6/s(2.25배, 주입 종료 기준)**, ticket 86.8 → 177.0/s, 회복시간 465s → 207s. 호스트 CPU avg 는 **+2.67%p**(79.43 → 82.10) 뿐인데 **그중 iowait 이 20.94% → 11.01%** 로 반이 됐다 — **직렬 소비의 상한은 CPU 용량이 아니라 단일 스레드가 DB 를 기다리던 시간이었다.** 병렬 소비에서 좌석 락 경합이 처음으로 실재했지만(3,621건) 오버셀은 0이다. 다만 concurrency 2 는 측정하지 않았고, 파티션 3이 상한이다 |
| **결제·티켓 발급은 부하 여정에 없다** | `StubPaymentApprovalClient` 는 `@Profile("!prod")` **와** `@ConditionalOnProperty(payment.pg.stub.enabled=true)` 의 **AND** 조건으로 등록되므로 `prod` 에서 실행되지 않는다. 잰 것은 파이프라인 입구 이후다 |
| **N+1 은 튜닝한 것이 아니다** | [ADR 0003](adr/0003-shared-database-with-service-boundaries.md) 이 크로스 도메인 연관관계 매핑을 금지해 저장소 전체에 `@ManyToOne`/`@OneToMany` 가 0건이고, 조회는 JPQL 생성자 표현식 DTO 프로젝션으로 처리한다. **구조상 생기지 않는 것이지 고쳐서 없앤 것이 아니다** |
| **HikariCP 는 손대지 않았다 — 단 `pending=0` 은 창 한정이다** | 0이 나온 것은 #345 만료 fallback(단일 스레드 경로)과 #598 S1(컨슈머 전용) 창이다. 0이 아닌 창도 있다 — **같은 #598 의 S2 창(HTTP 400rps 혼합)이 max 71**, 그리고 nginx 768 세대·다른 배포본이라 이것과 잇지는 못하지만 #403 집계 창 **41**, #348 스모크 **113** 이다. **#596 이 되돌릴 조건으로 선언한 `pending > 0` 은 판별력이 없다**(concurrency 1 arm 에서도 이미 참)는 것이 #598 의 결론이다 |
| **줄일 수 있는 몫이 남아 있지 않은 곳도 있다** | #534 — 좌석 집계 고정항 약 1.5~1.7ms 를 JFR 로 분해하면 프레임워크 CPU 48.6% / DB CPU 24.1% / 미분류 17.1% / DB 대기 9.6% / **앱 코드 0.7% / 커넥션 획득 0.0%** 다. 커넥션 획득도 Jackson 도 범인이 아니고, 이 고정항이 사실상 하한이다 |
