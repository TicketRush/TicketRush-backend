# 5. AWS 배포 토폴로지: 단일 EC2 + Docker Compose, 관리형 서비스 미채택

날짜: 2026-07-09

## 상태

승인됨

## 맥락

[ADR 0004](0004-load-test-execution-topology.md)가 "부하 생성기는 로컬, 대상 앱은 AWS 배포본"을 정했으나, 그 AWS 측 실체(어떤 인스턴스에 무엇을 어떻게 올릴지)는 정하지 않았다. 앱 8개(gateway + 서비스 7개)와 인프라 4종(MySQL·Kafka·Redis·관측 스택)을 어디에 배치할지 결정해야 한다.

작용한 힘:

- **비용** — 개인 크레딧 규모다. 배포본의 목적은 부하 테스트 수치 확보와 데모이며, 상시 가동이 아니다.
- **on-demand 운용** — ADR 0004가 전제한 "비테스트 시간엔 중지"가 성립하려면 **스택 전체가 꺼져야** 한다. 하나라도 끌 수 없는 구성요소가 있으면 그 전제가 무너진다.
- **측정 신뢰성** — 부하 테스트 그래프에 찍히는 것이 앱의 성능 한계여야 한다. 인프라 계층이 만드는 인위적 상한이 섞이면 수치의 의미가 사라진다.
- **팀 규모·목적** — 실사용자가 없고 SLA가 없다. 확장성·고가용성은 현재 요구사항이 아니다.

## 결정

AWS 배포본을 **단일 EC2 인스턴스 위의 Docker Compose 스택**으로 구성한다.

- **오케스트레이터를 두지 않는다.** k3s를 검토했으나 채택하지 않는다. 단일 노드에서는 오토스케일·HA·롤링배포가 애초에 불가하거나 Compose로 충분하다. 대신 control plane이 RAM 500MB~1GB를 상시 점유하고, 부하 테스트 중 CPU 노이즈를 더해 측정을 오염시킨다. 얻는 것 없이 측정 대상만 흐려진다.

- **관리형 서비스(MSK·RDS·ElastiCache)를 쓰지 않는다.** 결정적인 이유는 비용이 아니라 **끌 수 없다는 점**이다. MSK는 프리티어가 없어 월 $80+가 상시 과금되고, RDS는 중지해도 7일 뒤 자동으로 재시작된다. 둘 다 ADR 0004의 on-demand 운용 전제와 **구조적으로 충돌**한다. 인프라 전부를 같은 EC2의 컨테이너로 넣으면 인스턴스 stop 한 번으로 스택 전체가 멈추고, 상시 비용은 EBS 볼륨만 남는다.

- **`m7i.xlarge`(4 vCPU / 16GiB, 서울 리전 $0.2478/hr)를 쓴다.** `t3` 계열은 버스터블이라 부하 테스트 중 CPU 크레딧이 소진되면 성능이 계단식으로 떨어진다. 그러면 그래프에 찍히는 것은 앱의 성능 한계가 아니라 **AWS의 크레딧 소진 곡선**이 되어, 측정 자체가 무의미해진다. 월 44시간 기준 t3.large 대비 차액은 $6.3이며, 이는 측정값의 유효성에 대한 대가로 지불할 만하다.

- **DB 스키마는 `infra/mysql/init/01-schema.sql` 스냅샷으로 생성한다.** `prod` 프로파일은 `ddl-auto: validate`인데(각 서비스 `application-prod.yml`) 저장소에 스키마 DDL이 없다. 환경변수로 `update`를 덮으면 7개 서비스가 동시에 같은 `ticket_rush` 스키마에 DDL을 쳐 경쟁 조건이 생긴다. 대신 엔티티에서 뜬 스냅샷을 MySQL 컨테이너의 `/docker-entrypoint-initdb.d`에 마운트해 최초 기동 시 한 번 실행하고, 앱은 `validate`를 유지해 스키마 불일치를 부팅 시점에 검출한다.

  이 스냅샷은 [ADR 0003](0003-shared-database-with-service-boundaries.md)이 미도입하기로 한 **마이그레이션 도구가 아니다.** `validate`를 만족시키기 위한 초기 스키마일 뿐이므로 0003의 결정과 충돌하지 않는다.

- **write 시나리오용 프로파일은 `SPRING_PROFILES_ACTIVE=prod,dev`다.** `application-dev.yml`은 어느 모듈에도 존재하지 않는다(프로파일은 `local`/`prod`/`test` 3종). `prod` 설정으로 접속 정보를 환경변수 주입받으면서 `dev`만 추가 활성화해 `@Profile({"local","dev"})`인 DevToken 빈을 등록한다. Spring Boot는 설정 파일이 없는 프로파일도 활성화할 수 있으므로 **파일 추가는 필요 없다.**

## 결과

- **포기하는 것**: 독립 확장, 무중단 배포, 장애 격리(부분). 한 인스턴스가 죽으면 전부 죽고, 배포 시 순단이 생기며, 서비스별로 리소스를 따로 늘릴 수 없다.
- **유지되는 것**: 서비스 경계, 독립 배포 단위(컨테이너), 프로세스 격리. MSA의 본질인 데이터·배포 캡슐화는 그대로다. 이는 ADR 0003의 공유 DB 결정과 같은 결의 타협이며, 실사용자와 SLA가 없는 현재 목적에 확장성·고가용성은 요구사항이 아니다.
- **(비용)** 월 44시간 기준 약 **$14** — 컴퓨트 $10.9 + EBS 30GB $2.74 + 공인 IPv4 $0.22. Elastic IP는 인스턴스 중지 중에도 월 $3.65가 과금되므로 쓰지 않고, 기동할 때마다 바뀌는 공인 IP를 그대로 쓴다. 이 문서가 배포 비용의 SSOT다.
- **(비용 리스크)** 켠 채 잊으면 24/7 과금으로 월 **$178**이 되어 크레딧이 증발한다. **인스턴스를 처음 켜기 전에** CloudWatch 자동 중지 알람(CPU < 5%가 1시간 지속 → stop)과 AWS Budgets 알림을 걸어 두는 것이 이 결정의 전제다.
- **(보안)** `prod,dev` 조합은 DevToken 발급 엔드포인트(`POST /api/v1/dev/auth/token`)가 **열린 상태**를 뜻한다. 또한 ADR 0004가 정한 대로 관측 스택이 같은 EC2에 있고 Prometheus의 remote-write 수신 포트(9090)에는 인증이 없다. 따라서 보안 그룹에서 **본인 공인 IP `/32`만 허용**하는 것은 선택이 아니라 필수 전제다.
- **(전환 시점)** 다음 중 하나가 발생하면 이 결정을 재검토한다 — ① 부하 비대칭이 측정으로 드러나 특정 서비스만 확장해야 할 때, ② 서비스 하나가 죽어도 나머지가 살아야 할 때, ③ 배포 순단이 문제 될 실사용자가 붙었을 때.
