# 23. 공연 갤러리 변경은 삭제 목록이 아니라 유지 목록으로 선언한다

날짜: 2026-09-25

## 상태

승인됨

## 맥락

공연 파일 교체 API(`PATCH /api/v1/performance/admin/{id}/files`, [#637](https://github.com/TicketRush/TicketRush-backend/issues/637))의 갤러리 계약은 "`gallery` 파트를 보내면 전체 치환, 안 보내면 유지" 둘뿐이었다. 프론트가 공연 수정 화면에 **기존 이미지 삭제** 기능을 붙이면서 네 가지를 요구했다 — ① 기존 대표 이미지 삭제 ② 기존 갤러리 개별 삭제 ③ 갤러리 일부 삭제 + 신규 추가 ④ 삭제는 최종 저장 시 한 번에 반영. 이 계약으로는 ②③이 불가능하다. 새 파일 없이 기존 한 장만 빼거나, 기존 일부를 남기고 신규를 더할 방법이 없다([#688](https://github.com/TicketRush/TicketRush-backend/issues/688)).

같은 맥락에서 3D 모델도 비울 수 없었다. [#650](https://github.com/TicketRush/TicketRush-backend/issues/650)부터 3D 모델은 선택 필드가 됐지만, 이미 올린 모델을 없애는 규칙은 없었다.

**프론트 `develop`의 현재 동작이 이미 위험하다.** 수정 화면은 새로 고른 갤러리 파일만 `gallery`로 보내므로, 기존 3장인 공연에 1장을 추가하려고 저장하면 3장이 그 1장으로 통째로 바뀐다. 계약을 어떻게 확장하든 프론트가 새 계약을 붙이기 전까지는 이 동작이 그대로다.

작용한 힘은 셋이다.

- **하위 호환.** 백엔드는 매주 일요일 CD로 먼저 배포되고 프론트는 그 뒤에 따라온다. 배포 전후로 `request` 파트를 안 보내는 프론트가 깨지면 안 된다.
- **동시 편집 수용 논리.** `Performance` 엔티티는 갤러리 교체를 "전체 치환이 계약이므로 어드민 둘이 동시에 교체하면 나중 커밋의 목록이 통째로 이기는 것을 수용한다"로 정리해 두고, "부분 교체(개별 인덱스 교체·삭제)로 바꾸는 순간 이 수용 논리가 깨져 낙관적 락이나 컬렉션 잠금을 검토해야 한다"고 경고해 뒀다([#459](https://github.com/TicketRush/TicketRush-backend/issues/459)). `@OrderColumn` 컬렉션은 전량 DELETE 후 재INSERT라 부분 교체가 서로의 변경을 지운다.
- **멱등.** 프론트는 저장 버튼 한 번에 API를 한 번 호출하지만, 네트워크 재시도가 같은 요청을 두 번 보낼 수 있다.

후보는 둘이었다.

- **삭제 목록(`delete_gallery_urls`)**: 지울 URL을 나열한다. `gallery` 파트는 "추가"가 되어야 일관된다.
- **유지 목록(`keep_gallery_urls`)**: 남길 URL을 나열한다. 최종 갤러리 = 유지 목록 + `gallery` 파트의 신규 파일.

## 결정

**우리는 갤러리 변경을 유지 목록으로 선언한다.** 선택적 `request` JSON 파트에 `keep_gallery_urls`와 `clear_model3d`를 싣는다.

1. **`keep_gallery_urls`는 화면에 남아 있는 상태를 최종 목록으로 선언한다.** 최종 갤러리 = 유지 목록(그 순서대로) + `gallery` 파트의 신규 파일(그 순서대로). 유지 목록에 없는 기존 URL은 빠진다. `[]`에 신규가 없으면 갤러리가 비워진다. 유지 목록은 개별 인덱스를 고치는 부분 교체가 아니라 **여전히 전체 치환**이다 — 요청 하나가 최종 목록 전체를 결정하고, 같은 요청을 다시 보내도 결과가 같다.
2. **`keep_gallery_urls`를 보내지 않으면 #637 계약 그대로다.** `gallery`를 보내면 전체 치환, 안 보내면 유지. `null`(키 누락)과 `[]`를 구분하는 것이 이 하위 호환의 핵심이며, 도메인의 "빈 목록 무시" 가드를 걷어낸 대신 유스케이스가 request 없는 빈 갤러리 파트를 `null`로 바꿔 넘긴다.
3. **`clear_model3d: true`면 3D 모델 URL을 비운다.** 새 `model3d` 파일과 함께 오면 모순이라 400이다. 비우기는 `replaceFiles()`의 파라미터가 아니라 별도 `clearModel3d()`다 — 그쪽 계약이 "null이면 유지"라 같은 자리에 비움까지 실으면 한 인자가 세 뜻을 갖는다.
4. **동시 편집은 last-write-wins를 유지한다.** 유지 목록도 전체 치환이라 엔티티의 수용 논리 안에 있다. 다만 **유지하려는 URL이 현재 갤러리에 없는 경우만은** 다른 어드민이 먼저 바꾼 stale 화면이 확실하므로 400(`PERFORMANCE_400_011`)으로 드러낸다. 낙관적 락은 도입하지 않는다. **이 400은 한 방향으로만 확실하다.** 400이 왔으면 stale이 확실하므로 재조회 안내가 유효하지만, 200이 충돌 부재를 뜻하지는 않는다 — 검사 근거(`findById` 스냅샷)를 읽은 뒤 커밋까지의 구간(대부분 S3 업로드)에서 다른 어드민이 지운 URL은 400 없이 되살아난다. 그 결과도 last-write-wins 안이라 수용한다.
5. **검증은 업로드 전에 전부 끝내고, 상한은 유지 + 신규의 합으로 센다.** 중복(`_400_012`)·모순(`_400_013`)은 클라이언트 버그, stale(`_400_011`)은 재조회 후 재시도가 유효해 코드를 나눈다. 개수 상한은 기존 `PERFORMANCE_400_003`을 그대로 쓴다.
6. **"변경 지시가 하나도 없을 때만" 거절한다.** 기존 `PERFORMANCE_400_010`("파일이 하나도 없음")의 의미를 넓혀, 실제 파일·유지 목록(빈 배열 포함)·`clear_model3d: true` 셋 중 하나만 있으면 통과한다. `request`가 `{}`이거나 `clear_model3d: false`뿐인 것은 지시가 아니다.
7. **참조를 잃은 S3 객체는 지우지 않는다.** #637과 같은 판단이다. 누적 정리는 별도 이슈다.

삭제 목록을 버린 이유는 세 가지다. `gallery` 파트의 의미를 치환에서 추가로 바꿔야 하므로 기존 계약이 깨진다. 삭제 목록은 "지울 것"을 고르는 부분 교체라 엔티티 Javadoc의 동시성 경고에 정면으로 해당한다. 프론트가 삭제된 URL을 따로 추적해야 하는 반면 유지 목록은 "지금 화면에 남아 있는 것"만 보내면 된다.

## 결과

**긍정**

- 프론트 요구 ②③이 계약 하나로 풀리고, 요구 ④(저장 시 한 번 반영)는 그대로 유지된다. ①(대표 이미지 삭제)은 대표 이미지가 필수라 "새 파일로 교체"가 곧 삭제이므로 추가 계약이 없다.
- `request` 파트가 없는 요청은 #637 그대로라 백엔드를 먼저 배포해도 프론트가 깨지지 않는다. 스키마 변경도 없어 롤백은 코드 revert로 충분하다.
- 유지 목록은 멱등이라 재시도가 안전하고, 순서를 바꿔 보내면 그 순서로 저장되어 재배열도 같은 계약으로 된다.
- 동시 편집에 대한 엔티티의 수용 논리를 바꾸지 않아 낙관적 락 도입을 미룰 수 있다.

**부정 · 감수**

- 갤러리 3장 상한이 "신규 파일 수"에서 "유지 + 신규의 합"으로 바뀐다. 유지 목록을 보내지 않는 경로는 그대로다.
- `PERFORMANCE_400_010`의 의미가 넓어져 프론트가 이 코드에 문구를 붙여 뒀다면 갱신 대상이다.
- 빠진 이미지·비워진 3D 모델의 S3 객체가 고아로 남는다. 교체만 있던 때보다 누적 속도가 빨라질 수 있다.
- 도메인의 "빈 목록 무시" 안전망이 사라졌다. 호출부가 request 없는 빈 갤러리 파트를 `null`로 바꾸는 한 줄이 갤러리 전삭제를 막는 유일한 방어이며, `PerformanceReplaceFilesTest.emptyGalleryWithOtherPart_keepsGallery`가 그것을 고정한다.
- **롤백에 함정이 있다.** 프론트가 `request`를 보내는 상태에서 백엔드만 되돌리면 Spring이 모르는 파트를 조용히 무시해 200을 주며 유지 목록이 무시된다(전체 치환으로 회귀). 되돌릴 때는 프론트에 먼저 알려야 한다.
- `request` 파트가 올바른 JSON이 아니면 500이 나간다. 문법 오류와 타입 불일치(`"clear_model3d":"yes"`)는 Spring이 `HttpMessageNotReadableException`으로 감싸 `GlobalExceptionHandler`의 catch-all(`Exception`)에 떨어지는 경로이고, 파트에 `Content-Type: application/json`을 안 붙인 경우는 `HttpMediaTypeNotSupportedException`으로 같은 catch-all에 떨어지는 별개 경로다. 등록 API의 `request` 파트와 같은 조건이라 이번 범위 밖으로 두고, 앞의 두 경우를 테스트에 실측으로 기록했다. 전용 핸들러는 별도 이슈다.

**후속**

- 프론트에 새 계약과 함께 "현재 `develop`은 신규 갤러리 저장 시 기존 전체가 치환된다"는 사실을 전달한다.
- 어드민 둘이 각자 다른 유지 목록을 보내는 경합을 사용자에게 드러내야 한다면 그때 낙관적 락을 검토한다. 이 결정은 그 순간을 "유지 URL이 이미 사라진 경우"만 400으로 드러내는 데서 멈췄다.
