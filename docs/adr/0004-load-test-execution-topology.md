# 4. 부하 테스트 실행 토폴로지: k6는 로컬, 대상 앱은 AWS 배포본

날짜: 2026-07-09

## 상태

승인됨

## 맥락

#342에서 k6 부하 테스트 인프라(docker-compose `loadtest` 프로파일 컨테이너, 시나리오 2개, 대량 시딩 SQL, `docs/load-test-guide.md`)를 구축했다. 다만 부하 생성기(k6)와 대상(앱)이 **같은 머신을 공유하면 CPU가 경쟁**해 latency·throughput 수치를 신뢰하기 어렵다. 신뢰 가능한 정량 수치를 얻으려면 둘을 서로 다른 머신으로 **분리**해야 한다.

작용한 힘:

- **비용** — 개인·포트폴리오 규모라 상시 과금이 부담스럽다.
- **팀 배포 대상** — 팀은 이미 서비스를 **AWS**에 배포할 예정이다.
- **가정용 회선** — 로컬에서 무언가를 돌린다면 그 트래픽은 비대칭 가정용 인터넷(업로드가 좁고 지터가 큼)을 거친다.
- **인증 제약** — write 시나리오(`booking-create`)가 쓰는 DevToken(`/api/v1/dev/auth/token`)은 `local`/`dev` 프로파일에서만 노출된다.

검토한 대안:

1. **전부 로컬**(#342 기본) — 무료지만 생성기-대상 리소스 경쟁으로 수치가 왜곡된다.
2. **k6=GitHub Actions + 앱=Oracle Cloud Always Free** — "비용 0원 분리"를 목표로 #360 최초 방향으로 채택했으나, **Oracle ARM 인스턴스가 "Out of capacity"로 생성이 반복 실패**해 실현하지 못했다.
3. **k6=원격(EC2 등) + 앱=로컬** — 분리는 되지만 ① 응답 페이로드가 가정용 **업로드**(좁고 지터 큼)를 거쳐 k6의 latency 측정이 앱이 아니라 집 네트워크를 반영하고(분리의 목적을 무너뜨림), ② 로컬 게이트웨이·DevToken·Prometheus를 공개 노출해야 해 보안이 나빠진다.
4. **k6=로컬 + 앱=AWS 배포본** — 대상이 데이터센터의 안정적 네트워크·공인 엔드포인트에 있고, 응답(큰 쪽)은 넓은 가정용 **다운로드**로 수신하며, 노출면은 종료 가능한 AWS 인스턴스로 격리된다.

## 결정

부하 테스트를 **k6는 로컬(기존 `loadtest` 프로파일 컨테이너), 대상 앱은 AWS 배포본**으로 분리해 실행한다(대안 4).

- 기존 시나리오·시딩·env는 그대로 재사용하고 `BASE_URL`만 AWS 엔드포인트로 덮는다.
- 비테스트 시간엔 AWS 리소스를 중지하는 **온디맨드 운용**으로 비용을 세션당 ~3h × 월 8회 = 24h/월 ≈ **$2.5(약 3,500원)** 수준으로 억제한다.
- k6 클라이언트 지표(`k6_*`)는 로컬 Prometheus/Grafana에서, 앱 지표(`ticketrush_*`)는 AWS 측 모니터링(CloudWatch 등)에서 관측한다.
- write 시나리오(`booking-create`)는 DevToken이 필요하므로 **AWS를 `dev` 프로파일로 띄울 때만** 실행한다. read 시나리오(`seat-layouts`)는 프로파일과 무관하다.

Oracle 기반 무료 분리(대안 2)는 폐기하고 관련 자산(GitHub Actions 워크플로우, Prometheus 공인 노출 오버레이)을 제거한다.

## 결과

- 대상이 안정적 네트워크에 있고 응답이 넓은 다운로드로 오므로 **측정 신뢰성**이 확보된다. 노출면이 종료 가능한 AWS 인스턴스로 **격리**된다.
- 기존 `load-test/` 자산을 그대로 재사용해 추가 코드가 거의 없다.
- (비용) 비테스트 시간에 AWS 리소스를 **반드시 중지**해야 $2.5/월이 성립한다. 상시 기동 시 24/7 과금된다.
- (트레이드오프) 앱 지표(`ticketrush_*`)가 로컬 Grafana에 모이지 않아 k6 지표와 한 화면 교차 관측이 불가하고, 앱 쪽은 AWS 측에서 별도로 봐야 한다.
- (한계) 요청 경로는 여전히 가정용 업로드를 쓰므로 초고 VU에서는 업로드 대역이 상한이 될 수 있다. 이 규모를 넘어서야 하면 AWS 내부에 부하 생성기를 두거나 관리형 부하 도구(k6 Cloud 등)를 별도 ADR로 검토한다.
