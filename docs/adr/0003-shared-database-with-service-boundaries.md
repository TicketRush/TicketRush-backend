# 3. 단일 공유 DB를 유지하고 서비스 규율로 데이터 경계를 강제한다

날짜: 2026-07-09

## 상태

승인됨

## 맥락

MSA를 MSA로 만드는 핵심은 데이터 캡슐화다 — 각 서비스가 자기 데이터를 소유하고, 다른 서비스의 테이블을 직접 읽거나 쓰지 않으며, 도메인 간 데이터 교환은 API·이벤트로만 이뤄져야 한다.

데이터베이스 구성은 두 단계에 걸쳐 논의됐다.

**1단계 — database-per-service 검토, 비용으로 기각.** 처음에는 교과서적 MSA대로 서비스마다 DB 인스턴스를 따로 두는 database-per-service를 고려했다. 그러나 서비스별로 DB를 분리 배포하면(관리형 DB 인스턴스를 서비스 수만큼 띄우는 비용 등) 감당하기 어려운 인프라 비용이 발생한다. 현재 프로젝트 규모에서 독립 배포·독립 확장·장애 격리 같은 이점이 이 비용을 정당화하지 못한다고 판단해 단일 DB로 방향을 정했다.

**2단계 — 단일 DB 안에서 schema 분리 검토.** 단일 DB로 가더라도 schema를 도메인별로 나눠 MSA 구조를 더 드러낼지 고민했다. 다만 단일 DB 안에서 schema만 나누는 것은, 서비스별 DB 계정·스키마 권한(grant)으로 접근을 물리적으로 막지 않는 한 이름표(namespace prefix)에 불과해 경계 강제라는 실질 가치를 거의 주지 못한다.

한편 현재 코드는 물리적으로만 한 DB일 뿐, 논리적 결합은 이미 없는 상태다.

- **크로스 도메인 FK 없음** — 다른 도메인을 참조하는 곳은 연관관계 매핑이 아니라 전부 plain `Long` ID 컬럼이다(예: `Booking`의 `userId`·`performanceId`·`seatId`). `@ManyToOne`/`@JoinColumn`으로 도메인을 가로지르는 곳은 하나도 없다.
- **크로스 도메인 조인 없음** — repository의 조인은 전부 같은 도메인 내부다(seat 도메인 내 `Seat↔SeatLayout`, user 도메인 내 `UserAccount↔User`).
- **서비스 간 통신은 DB 공유가 아니라 REST + Kafka 이벤트** — 동기 호출은 `RestClient`, 비동기는 Kafka 도메인 이벤트이며 Outbox/Inbox/DLT로 신뢰성과 멱등성을 확보한다.

즉 단일 DB·단일 schema이면서도 데이터 캡슐화는 이미 지켜지고 있다. 스키마 관리는 `ddl-auto`(local `update` / prod `validate`)에 의존하며 flyway/liquibase 같은 마이그레이션 도구는 도입돼 있지 않다.

## 결정

단일 공유 DB(`ticket_rush`)를 유지하고, 그 안에서 schema도 분리하지 않는다.

데이터 경계는 인프라(FK 제약·스키마 권한)가 아니라 **서비스 규율**로 강제한다.

- 한 서비스는 다른 도메인의 테이블을 직접 조회·변경하지 않는다.
- 도메인을 가로지르는 FK·연관관계 매핑·조인을 만들지 않는다. 타 도메인 참조는 plain ID 컬럼으로만 보유한다.
- 도메인 간 데이터 교환은 REST(`RestClient`) 호출과 Kafka 이벤트(Outbox/Inbox)로만 한다.

향후 트래픽 규모나 조직 분리로 독립 배포·독립 확장·장애 격리의 이점이 인프라 비용을 정당화하게 되면 database-per-service로 이행하고, 그 시점에 별도 ADR로 이 결정을 supersede(대체)한다.

## 결과

- "왜 서비스별 DB 분리가 아니라 단일 DB냐", "왜 schema도 안 나누냐"에 답할 근거가 문서로 남는다. 현재 구조가 방치가 아니라 비용을 고려한 의도된 결정임이 명확해진다.
- 인프라 비용과 운영이 단순하게 유지된다 — 단일 DB 인스턴스, 단일 접속 정보 세트, 마이그레이션 도구 없이 `ddl-auto`로 운영.
- 이미 경계가 깨끗해(끊어낼 크로스 도메인 조인·FK가 없음) 훗날 database-per-service로 이행하는 비용이 낮다. 분산 데이터 일관성이라는 가장 어려운 부분은 Kafka + Outbox/Inbox로 이미 갖춰져 있다.
- (보완) `prod` 프로파일은 `ddl-auto: validate`이므로 스키마를 만들 DDL이 따로 필요하다. `infra/mysql/init/01-schema.sql`(`mysqldump --no-data` 스냅샷)이 그 역할을 한다. 이는 **마이그레이션 도구가 아니라 `validate`를 만족시키기 위한 초기 스키마**이므로 위 결정과 충돌하지 않는다. 환경변수로 `ddl-auto=update`를 덮는 방식은 쓰지 않는다 — 서비스 7개가 동시에 같은 스키마에 DDL을 쳐 경쟁 조건이 생긴다. 엔티티를 바꾸면 스냅샷을 재생성해야 하며, 절차는 `infra/mysql/README.md`에 있다.
- (트레이드오프) shared database는 경계를 코드 규율에 의존하므로, 크로스 도메인 조인·FK가 코드 리뷰에서 새어들 위험이 있다. 컨벤션과 리뷰로 방어한다.
- (후속 과제) DB를 분리하게 되면 (a) 공용 `outbox`/`inbox`/DLT 테이블을 서비스별 DB에 배치하는 작업과 (b) 서비스별 스키마 소유권을 관리할 마이그레이션 도구(flyway 등) 도입을 검토해야 한다.
