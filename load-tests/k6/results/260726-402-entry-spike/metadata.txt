# 캘리브레이션 판단
# 피크 60 iter/s (= 180 HTTP req/s, iteration 당 3요청) 에서 호스트 CPU 가 97.91% 에 닿는다.
# 무릎이 그 지점이므로 본 회차도 피크 60/s 를 유지한다 — 더 올리면 포화된 호스트의 큐잉을
# 재는 것이 되어 검표 경로 자체의 수치가 흐려진다. 단일 EC2 에 앱 9 + Kafka·MySQL·Redis·
# 관측 스택이 동거하므로 절대 수치에 포화가 섞인다는 §10.5·§11.7 단서가 그대로 적용된다.
#
# booking 내부조회 RPS(109.30) 가 entries RPS(110.16) 와 1:1 로 일치한다. verify 와 check-in
# 양쪽 모두 booking 을 호출한다는 §12.1-(a) 의 근거가 실측으로 확인됐다.

# ── 클라이언트 p95 역전에 대한 주석 ─────────────────────────────────────────
# 전 구간 클라이언트 p95 는 qr(27.07) > verify(22.11) 로 역전돼 있다. 설계상 verify 는 qr 에
# booking 왕복이 더해진 경로이므로 이 값을 그대로 왕복 비용으로 쓰면 음수가 된다.
# 원인은 앱이 아니라 측정 순서다. qr 은 iteration 의 첫 요청이라 커넥션 수립 비용을 떠안는다.
#   근거 1) 서버 측 평균은 전 구간·전 단계에서 qr < verify < check-in 으로 단조롭다
#           (1.30 < 4.27 < 11.65 ms). 서버 측정은 네트워크·TLS 를 포함하지 않는다.
#   근거 2) 부하가 6배 오른 피크에서 qr p95 가 46.50 -> 28.89 로 '내려간다'. 포화라면 반대로
#           올라야 한다. 도착률이 높아 커넥션이 계속 살아 있는 구간에서 값이 낮아진 것이다.
#   근거 3) 같은 구간에서 verify p95 는 21.73 -> 21.71 로 평평하다(커넥션 비용을 안 진다).
# 따라서 왕복 비용의 SSOT 는 서버 축 차분(verify - qr)으로 둔다.
# k6_http_req_blocked_p95 도 같은 방향을 가리키지만, baseline 구간 17개 표본이 전부 동일값이라
# staleness 반복으로 판단해 방향성 근거로만 쓰고 수치로 인용하지 않는다.
