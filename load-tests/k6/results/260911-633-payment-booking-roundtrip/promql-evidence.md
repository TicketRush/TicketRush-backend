# PromQL 증적 — #633 회차 1

이 회차에는 `timeseries-*.json` 과 Grafana 캡처가 **없다**. SSH 키가 없어 터널(`-L 9090`)을
띄우지 못했고, 그래서 k6 의 remote-write 도 쓰지 못했다. 대신 EC2 셸에서
`localhost:9090` 에 직접 질의해 값을 떴고, **그 질의문과 출력을 여기에 남겨 재현 경로를 보존한다.**

수치의 SSOT 는 [`metadata.txt`](metadata.txt) 다. 이 파일은 그 수치가 어떤 질의에서 나왔는지를 보인다.

> 🔴 **이 파일의 수치는 2026-09-11 회차 직후가 아니라 사후 재조회로 확정한 값이다.**
> 회차 당일에 뜬 값은 분위수와 버킷이 서로 다른 창에서 나와 **내적으로 모순**이었다
> (예: `le=25ms` 누적 98.55% 인데 p99 가 23.410ms — 98.55% < 99% 이면 p99 는 25ms 를 넘어야 한다).
> 셀프 리뷰에서 잡아 같은 창·같은 `@ epoch` 로 전부 다시 떴다. 그 과정은 §5 에 남긴다.

---

## 1. 왜 `@ modifier` 로 구간을 고정해야 하는가

히스토그램 버킷은 **누적 카운터**다. 그래서 `increase(...[3m])` 같은 상대 창은 **조회 시점**을
기준으로 뒤를 돌아본다 — 회차가 끝나고 몇 분만 지나도 창이 run 바깥을 덮어 `NaN` 이나 0 이 나온다.

`@ <epoch>` 로 평가 시점을 run 종료 직후에 고정하면, 조회가 얼마나 늦어지든 **그 run 의 구간을
정확히 복원**할 수 있다.

> 🔴 **창의 시작점도 검산해야 한다.** `@ run종료+20s` 에 `[3m]` 을 걸면 창이 `run시작+20s` 부터
> 열려 **run 앞부분이 잘린다.** 재조회 1차에서 실제로 밟았다(W1 총건수 1325 vs k6 1440).
> **총건수를 k6 iteration 과 대조**해 창이 run 을 덮었는지 확인하는 절차가 필요하다.

| run | run 구간(UTC) | 확정 창 | `@ epoch` | 총건수 | k6 iteration |
|---|---|---|---|---|---|
| W1 | 11:55:26 ~ 11:58:26.2 | `[3m10s]` | `1789127912` | 1422.93 | 1440 |
| B | 12:40:24 ~ 12:50:45 | `[11m]` | `1789131065` | 6344.19 | 6200 |
| W2 | 12:58:36 ~ 13:01:36.2 | `[3m10s]` | `1789131702` | 1443.86 | 1441 |

B 는 `[11m]` 과 `[12m]` 두 창에서 분위수가 소수점 아래까지 같아(p99 0.009722891566…) 창 선택에
민감하지 않음을 확인했다.

> ⚠ Micrometer 의 `_max` 는 이 방식으로 복원할 수 **없다.** 롤링 2분 창이라 run 종료 직후에
> 뜨지 않으면 값 자체가 사라진다. W2 에서 실제로 놓쳤다.

## 2. 질의문

라벨: `{outcome="success", instance="payment-service:8090"}` · job 은 `ticketrush-services`.

```promql
# 분위수 (p 는 0.50 / 0.95 / 0.99)
histogram_quantile(0.99,
  sum by (le) (increase(
    ticketrush_payment_booking_lookup_seconds_bucket{outcome="success",instance="payment-service:8090"}[3m10s]
    @ 1789127912)))

# 버킷 누적 (le 별)
sum by (le) (increase(
  ticketrush_payment_booking_lookup_seconds_bucket{outcome="success",instance="payment-service:8090"}[3m10s]
  @ 1789127912))

# outcome 별 호출량
sum(increase(
  ticketrush_payment_booking_lookup_seconds_count{outcome="failed",instance="payment-service:8090"}[3m10s]
  @ 1789127912))

# 평균 — #402 의 3.20ms 와 직접 비교할 수 있는 유일한 축(그쪽은 평균 차분이었다)
sum(increase(ticketrush_payment_booking_lookup_seconds_sum{outcome="success",…}[3m10s] @ 1789127912))
/
sum(increase(ticketrush_payment_booking_lookup_seconds_count{outcome="success",…}[3m10s] @ 1789127912))
```

재조회 스크립트 전문은 이 디렉토리의 `b1b2-split-query.sh`(B 내부 구간용)와 회차 노트에 있다.

> 🔴 **EC2 웹 터미널은 붙여넣기에서 따옴표를 유실한다.** PromQL 은 라벨 매처에 따옴표가
> 필수라 그대로 붙여넣으면 조용히 다른 질의가 된다. 스크립트를 base64 한 줄로 감싸
> 전송하는 방식으로 우회했다(`echo <base64> | base64 -d > /tmp/q.sh && bash /tmp/q.sh`).

**읽는 법**

1. **50~100ms 는 세 run 모두 구간건수가 정확히 0 인 빈 구간이다.** 임계를 50ms 로 잡든 100ms 로
   잡든 초과 건수가 같다 — 100ms 는 검출력을 하나도 잃지 않으면서 여유만 두 배다.
   `slowCallDurationThreshold = 100ms` 권고의 핵심 근거가 이 빈 구간이고, **재조회 전후로
   변하지 않은 유일한 논거**다.
2. **워밍업 꼬리는 재현되지 않는다.** W1 은 250ms 초과가 **0건**인데 W2 는 5건이다. p99 도
   24.392 vs 32.133ms 로 32% 차이다. 자릿수는 유지되지만(무효 기준 통과) "같은 모양으로
   재현된다"고 말할 수는 없다.
3. **정상 구간(B)은 25ms 에서 완전히 끝난다** — 6,344건 중 초과 0건.

> ⚠ 값이 소수인 것은 `increase()` 가 스크랩 경계에서 외삽하기 때문이다. 호출량의 SSOT 는
> k6 iteration 수이고(W1 1440 · B 6200 · W2 1441), Timer 건수는 `lookup:booking` 1:1 대조용이다.

## 5. outcome 별 분포 — 🔴 503 이 Timer 에 없다

| outcome | W1 | B | W2 |
|---|---|---|---|
| `success` | 1422.93 | 6344.19 | 1443.86 |
| `failed` | **0** | 0 | 0 (빈 결과) |
| `not_found` | 0 (빈 결과) | 0 | 0 (빈 결과) |

`failed` 버킷은 W1 에서 **전 구간 0** 이다(`le=1.0`·`le=2.0` 포함).

그런데 k6 는 같은 run 에서 `rt_booking_unavailable` **18건(1.25%)** 을 셌다. 그리고
**Timer 총건수(1422.93)가 k6 iteration(1440)보다 17.1건 적다.** 두 수가 거의 일치한다.

**즉 그 503 들은 `getBooking` 의 Timer 를 통과하지 않았다.** Timer 는 메서드 전체를
`try/finally` 로 감싸므로(`BookingRestClient` 86-106행), 예외가 났더라도 `finally` 에서
`outcome=failed` 로 기록됐어야 한다. 기록이 없다는 것은 **실패 지점이 그 메서드 바깥**이라는 뜻이다.

이 사실이 #571 에 직접 영향을 준다 — **서킷브레이커가 감쌀 구간에서 이 실패는 보이지 않는다.**
`failureRateThreshold` 를 이 회차의 k6 실패율 위에 세울 수 없는 이유이고, 원인 규명은
#571 로 넘긴다(회차 노트 §9.5).

> ⚠ **소유자 불일치는 `not_found` 가 아니라 `success` 로 기록된다.** #572 의 소유자 대조는
> `getBooking` 이 200 을 반환한 *뒤* UseCase 가 하는 판정이라, Timer 관점에서는 정상 왕복이다.
> 게이트 `owner_ok=10000` 이 그 오염을 막는다.
