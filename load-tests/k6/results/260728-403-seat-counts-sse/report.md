## 2. 이슈 서사와 실측의 차이

이슈 본문의 전제 몇 가지가 실측과 달랐다. 리포트를 읽기 전에 이 차이를 먼저 잡아야 수치를 오독하지 않는다.

### (a) "전송 스레드풀 포화"의 기전이 다르다 — 큐에 쌓이는 것은 구독자가 아니라 이벤트다

이슈는 `queue(1000) 적체 → max(16)까지 스레드 증가`로 포화를 서술한다. 그런데 `SeatStatusSseEventSender.send()`는 **이벤트 1건당 태스크 1개**를 던지고, 그 태스크 하나가 구독자 전원에게 **순차로** `emitter.send()` 한다(`SeatStatusSseEventSender.java:40-54`).

즉 구독자 N명은 스레드 수요를 N배로 만드는 것이 아니라 **태스크 1개의 길이를 N배로** 만든다. 실측이 이걸 그대로 보여준다 — 태스크 1건의 소요시간을 `활성 스레드 ÷ 태스크 처리율`로 역산하면:

| 구독자 | 태스크 처리율 | 활성 스레드(평균) | 태스크 1건 소요 | 구독자 1명당 send |
|---|---|---|---|---|
| 100 | 7.6/s | 0.4 | 53ms | 0.53ms |
| 300 | 10.1/s | 0.6 | 59ms | 0.20ms |
| 600 | 9.0/s | 1.5 | 167ms | 0.28ms |

**구독자 1명당 send 비용은 약 0.2~0.3ms로 일정하고, 태스크 길이가 구독자 수에 비례해 늘어난다.** 이슈가 서술한 "스레드 수요 증가"가 아니라 "태스크 길이 증가"다.

그 결과 **풀은 600 구독자 구간 내내 core 4에 머물렀다.** 평균 활성 스레드가 1.5로 여유가 있어서다. 풀이 16으로 늘어난 것은 인위적 버스트를 넣은 순간뿐이다(§8). 이슈가 경고한 "큐가 다 차야 스레드가 는다"는 순서가 실측에서 그대로 확인됐다.

### (b) 큐가 차면 지연이 아니라 유실이다

거부 핸들러가 기본값(`AbortPolicy`)이라 `RejectedExecutionException`이 나고, sender는 `log.warn`만 남기고 **이벤트를 조용히 드롭한다**(`:35-37`). 클라이언트는 "이벤트가 안 왔다"는 사실조차 알 수 없다. 실측에서 2,009건이 이렇게 사라졌다(§8).

### (c) 이벤트율은 예매 도착률 하나로 고정되지 않는다

좌석 락 TTL이 5분이라(`SeatLockUseCase.LOCK_TTL_MINUTES`) **예매 5분 뒤 그 좌석이 해제되며 두 번째 이벤트를 낸다.** 즉 회차 5분 이후 정상 상태 이벤트율은 예매 5/s + 해제 ~5/s ≈ **10/s**다.

해제 경로는 **둘**이고 성격이 다르다:

| 경로 | 트리거 | 성격 |
|---|---|---|
| `SeatReleaseSingleUseCase` | **Redis 키 만료 이벤트** | 주 경로. 키가 만료되는 대로 1건씩 즉시 해제 → 이벤트가 고르게 퍼진다 |
| `SeatStatusScheduler` | `@Scheduled(fixedDelay = 60000)` | fallback. Redis 이벤트를 놓친 것을 60초마다 쓸어 담는다(chunk 25 × 최대 80 = tick당 2,000) |

즉 **정상 상태의 해제는 60초 버스트가 아니라 Redis 만료로 고르게 들어온다.** 스케줄러 fallback이 큰 덩어리를 만드는 것은 "해제되지 않은 만료 HOLD가 대량으로 쌓여 있을 때"이고, 그 조건을 인위적으로 만든 것이 §8의 회차 4다.

이건 측정 오염이 아니라 시스템의 실제 성질이므로 통제하지 않고 명시한다.

### (d) 전파 지연은 서버·클라이언트 시계 차로 잴 수 없다

`SeatStatusChangedResponse`에 발생 시각 필드가 없고 EC2와 로컬 k6는 다른 호스트다. 그래서 **probe VU**가 자기가 구독하고 자기가 예매를 걸어 **자기 `seat_id` 이벤트가 돌아오는 시각차**를 잰다. 시작과 끝이 같은 k6 프로세스의 같은 시계다.

probe는 매 iteration마다 새로 구독하므로 `CopyOnWriteArrayList`의 **뒤쪽**에 등록된다 — 팬아웃 전 구간을 통과한 뒤 받는 **최악값**이다. 이 성질을 전제로 읽어야 한다.

## 3. 선결 수정 — SSE가 인터넷에서 도달 불가였다 (nginx 버퍼링)

측정을 붙이려다 드러난 프로덕션 결함이다. **좌석 상태 실시간 구독은 외부에서 쓸 수 없는 상태였다.**

| | |
|---|---|
| 증상 | `curl -sN https://api.ticketrush.store/api/v1/seat/16/seat-status/stream` → 8초 동안 **헤더조차** 오지 않음 |
| 대조 | 같은 시각 EC2 안에서 게이트웨이 8080 직결 → `event:connected` 즉시 수신 |
| 원인 | nginx `location /`의 기본값 `proxy_buffering on`. 업스트림 응답을 버퍼에 모았다 내보내는데 SSE는 커넥션을 열어둔 채 조금씩 흘리므로 버퍼가 차거나 끊길 때까지 아무것도 도달하지 않는다 |
| 노출 범위 | 인터넷에 열린 포트는 nginx 443 하나뿐이다 = 이 기능은 **전면 불통**이었다 |
| 수정 | 정규식 location 하나 — `proxy_buffering off` + `proxy_read_timeout 3600s`. 커밋 `2c630a15` |
| 검증 | 수정 후 https 헤더 즉시 + `event:connected` 수신. 회귀 확인 `seat-counts` 200 / `seat-layouts` 200 |

`proxy_read_timeout`을 3600s로 올린 것은 기본값 60s가 `SseEmitter` 타임아웃(30분)보다 짧아 **서버가 정상으로 여기는 커넥션을 nginx가 1분마다 끊기** 때문이다.

> **nginx 설정을 저장소로 편입했다.** 그전까지 EC2 호스트에만 있어서 저장소를 아무리 읽어도 이 결함을 알 수 없었다. 게이트웨이 라우트는 멀쩡히 있었고(`gateway-service/.../application.yml:50-56`) 막힌 곳은 그 앞단이었다. #402의 검표 라우트 누락과 같은 계열이고, 이번에도 **측정을 붙이는 과정에서** 드러났다.
>
> 이후로는 `deploy/nginx/`를 고쳐 배포한다. 호스트를 손으로 고치면 두 곳이 갈라져 다음 사람이 같은 함정을 다시 밟는다.

07-29 EC2 재기동 후에도 설정 md5가 유지됨을 확인했다(`5ef9b5bf…` = 저장소 blob과 바이트 동일).

## 4. 시딩 규모 (완료조건 1)

기존 `LOADTEST` 코호트(#348/#509의 20,800석)는 **건드리지 않았다.** 타이틀 접두사를 `LTC-`로 분리해 `cleanup_load.sql`의 `LOADTEST-%` 패턴에 걸리지 않게 했고, 회차 후 확인 결과 20,800석 그대로다.

| 코호트 | `performance_id` | 좌석 | AVAILABLE | SOLD | HOLD(미만료) | 용도 |
|---|---|---|---|---|---|---|
| `LTC-A` | 14 | 600 | 360 | 120 | 120 | 집계 스케일 A |
| `LTC-B` | 15 | 3,000 | 1,800 | 600 | 600 | 집계 스케일 B |
| `LTC-SSE` | 17 | 12,000 | 12,000 | 0 | 0 | SSE 대상(예매로 HOLD 전이 유발) |

- **상태 비율은 A·B가 동일하다**(SOLD 20% / HOLD 20% / AVAILABLE 60%). 두 곡선을 겹치려면 좌석 수 외의 변수가 같아야 한다.
- 세 코호트 모두 시딩 검증 SELECT와 `/seat-counts` 응답이 일치했다.
- `hold_expired_at`은 `UTC_TIMESTAMP()` 기준이다. 배포본 앱은 UTC로 돌지만 MySQL 컨테이너는 `system_time_zone=KST`라 세션 `NOW()`가 9시간 앞선다. 집계의 `now`는 `SeatGetStatusCountsUseCase`가 **앱 JVM 시계로** 만들어 넘기는 값이므로(쿼리에 `CURRENT_TIMESTAMP`가 없다) 세션 `NOW()`로 박으면 상태 분포가 통째로 어긋난다.
- 미만료 HOLD의 만료시각을 **+6시간**으로 둔 것은 60초 스케줄러가 회차 도중 해제해 분포가 변하는 것을 막기 위해서다.

### 코호트를 하루 넘겨 재사용할 때 드러난 것

EC2를 껐다 다음 날 켜니 **`+6시간` HOLD가 그 사이 만료돼 있었고, 부팅 직후 스케줄러가 전부 해제했다** — `LTC-A` hold 120→0, `LTC-B` 600→0. 그대로 쟀으면 회차 1과 회차 2의 상태 분포가 달라 두 곡선을 겹칠 수 없었다(무효 판정 대상).

부수 증거로 부팅 직후 `executor_completed_tasks_total`이 정확히 **720 = 120 + 600**이었다 — 해제된 좌석 수와 발행된 이벤트 수가 일치한다.

시드에 `@mode='refresh'`를 추가해 복원했다. 좌석번호 `S-<i>`의 `i`로 시딩 당시 배분 규칙을 재현하므로 **원래 HOLD였던 바로 그 좌석만** 되돌아가고, 공연을 지우지 않으므로 `performance_id`가 보존된다(재시딩하면 id가 바뀌어 회차 1과의 연결이 끊긴다).

## 5. 회차 1·2 — 집계 쿼리의 좌석 수 대비 곡선과 포화점 (완료조건 2)

계단 `40 → 80 → 160 → 240 → 320 → 480 iter/s`, **단계당 5분**(완료조건 5), 전환 램프 10초. 두 회차의 계단·유지시간·VU 설정은 동일하다.

계단 상한은 스케일 B에 `320 → 640/s`를 45초씩 넣은 캘리브레이션으로 먼저 잡았다(수치는 폐기). 그때 예측한 무릎 **246.8 rps**를 본 회차가 그대로 맞혔다.

### 회차 1 — 스케일 A (600석)

각 칸은 `구간평균 / 구간최댓값`, 계단 앞뒤 30초 제외. 원자료 `stage-stats-countsa.txt`.

|---|---|---|---|---|---|---|
| 40 | 39.1 / 40.0 | 2.46 / 2.83 | 4.91 / 5.16 | 14.31 / 15.77 | 0.0 / 0 | 0 / 0 |
| 80 | 79.8 / 80.0 | 1.89 / 1.97 | 4.16 / 4.54 | 19.65 / 20.43 | 0.1 / 1 | 0 / 0 |
| 160 | 158.5 / 160.1 | 1.86 / 1.94 | 4.43 / 4.70 | 30.79 / 33.04 | 0.4 / 2 | 0 / 0 |
| 240 | 239.1 / 240.8 | 2.34 / 2.83 | 6.96 / 9.46 | 43.43 / 44.32 | 0.6 / 1 | 0 / 0 |
| 320 | 319.6 / 320.5 | 4.67 / 12.21 | 20.69 / 64.40 | 60.03 / 74.14 | 1.2 / 5 | 0 / 0 |
| 480 | 472.8 / 480.9 | 22.81 / 28.42 | 85.97 / 98.69 | 88.76 / 91.50 | 14.0 / 50 | 7.7 / 40 |

**포화하지 않았다.** 480 계단에서도 목표의 98.5%를 소화했고 실패는 405,864건 중 1건이다. 600석의 상한은 480 rps보다 위에 있다.

### 회차 2 — 스케일 B (3,000석)

| 도착률 | k6 rps | 서버 avg ms | 서버 p95 ms | CPU % | tomcat busy | hikari pending |
|---|---|---|---|---|---|---|
| 40 | 40.0 / 40.0 | 5.12 / 6.40 | 10.96 / 23.80 | 21.32 / 23.49 | 0.1 / 1.0 | 0.0 / 0.0 |
| 80 | 80.0 / 80.0 | 4.28 / 4.68 | 7.75 / 8.36 | 30.07 / 31.29 | 0.4 / 1.0 | 0.0 / 0.0 |
| 160 | 160.0 / 160.1 | 5.65 / 6.37 | 19.10 / 21.65 | 51.88 / 54.76 | 1.2 / 7.0 | 0.0 / 0.0 |
| 240 | 239.9 / 240.3 | 40.81 / 72.35 | 140.01 / 238.22 | 92.87 / 95.96 | 7.9 / 50.0 | 3.2 / 40.0 |
| **320** | **254.9 / 260.0** | 204.96 / 207.57 | 368.40 / 379.25 | 99.97 / 100.00 | 50.0 / 50.0 | 40.1 / 42.0 |
| **480** | **254.4 / 260.2** | 202.69 / 204.86 | 371.56 / 403.74 | 99.99 / 100.00 | 50.0 / 50.0 | 39.6 / 40.0 |

**포화점 = 320 계단, 고원 247 rps.** 판정 근거는 세 축이 동시에 맞은 것이다:

1. 도착률을 320 → 480으로 **1.5배 올렸는데 처리량이 254.9 → 254.4로 전혀 움직이지 않는다.** VU 부족이면 도착률을 올릴 때 처리량이 조금이라도 늘어야 한다.
2. 호스트 CPU가 **100%**에 붙었다.
3. tomcat busy 50/50(상한), HikariCP pending 40(풀 10) — 대기열이 두 겹으로 생겼다.

무릎은 240과 320 사이다. 240 계단에서 이미 CPU 92.87%이고 tomcat busy 최댓값이 50에 닿는다.

> **처음 나타나는 압박은 커넥션 풀이다.** pending 최댓값 40에 풀 크기는 10이다. 집계 쿼리가 커넥션을 물고 있는 동안 뒤가 줄을 선다. 다만 그보다 먼저 호스트 CPU가 100%에 닿았으므로, 이 포화점은 **"집계 쿼리의 한계"가 아니라 "이 구성(단일 EC2)에서 도달한 지점"** 이다(#509와 같은 결론).

### 좌석 수 대비 비용

두 회차의 **80 계단**을 비교한다. 양쪽 다 CPU 여유가 크고(19.65% vs 30.07%) 대기열이 없어 '좌석 수' 외의 변수가 가장 적다. 40 계단은 JVM 워밍업이 섞여 있어(양쪽 다 80 계단보다 느리다) 쓰지 않는다.

| | 600석 | 3,000석 | 비 |
|---|---|---|---|
| 서버 평균 | **1.89ms** | **4.28ms** | 2.26배 |
| 좌석 수 | 600 | 3,000 | 5배 |
| 처리량 상한 | > 480 rps (미포화) | **247 rps** | — |

1차 근사:

```
cost ≈ 1.29ms + 0.000996ms × 좌석수      (좌석당 약 0.996 마이크로초)
```

- 스캔 몫: 600석에서 0.60ms(**32%**), 3,000석에서 2.99ms(**70%**)
- **"응답 시간이 좌석 수에 비례한다"는 이슈의 전제는 큰 고정 비용 위에서 성립한다.** 고정항 1.29ms는 3,000석에서도 비용의 30%를 차지한다. 좌석 수를 줄이는 최적화의 상한이 여기 있다.

> 07-28 캘리브레이션의 1차 근사(`2.60ms + 0.88µs/좌석`)는 워밍업이 섞인 30초 스모크에서 나온 값이라 **폐기했다.** 위 값은 5분 계단 2개에서 다시 잡은 것이다.

## 6. 비교 회차 — 집계가 좌석맵보다 비싸다

스케일 A(600석), 고정 도착률 20 iter/s, 3분. **같은 iteration에서 두 엔드포인트를 연달아 호출**하므로 부하·시각·커넥션 조건이 동일하다. 두 uri의 rps가 정확히 같은 것(19.267)이 1:1 호출의 확인이다.

| 엔드포인트 | 서버 avg | 서버 p95 | 응답 크기 |
|---|---|---|---|
| `seat-counts` | **3.785ms** | 5.815ms | 203 B |
| `seat-layouts` | 3.538ms | 6.252ms | 약 46 KB |

**응답 크기가 2자리 작은데 서버 비용은 사실상 같고, 오히려 집계가 평균 7% 비싸다.**

둘 다 `performance_id`로 같은 행을 읽는다. 차이는 그 다음이다 — 집계는 행마다 `CASE WHEN` 4개와 `hold_expired_at` 비교를 하고 203 B를 만들고, 좌석맵은 행을 DTO로 옮겨 46 KB를 만든다. 실측은 그 둘이 맞먹는다고 말한다.

> **"집계 API는 가벼운 조회"라는 전제는 이 규모에서 성립하지 않는다.** 응답이 작다는 것이 서버가 싸다는 뜻이 아니다.

스케일 B(3,000석)에서는 이 비교를 하지 않았다 — 3,000석 좌석맵 응답이 CPU·메모리를 삼켜 비교 자체를 오염시킨다. #509가 2,080석 좌석맵으로 seat-service를 cgroup OOM까지 몰고 간 경로가 정확히 이것이다.

## 7. 회차 3 — SSE 팬아웃: 구독자 수 대비 전파 지연 (완료조건 3)

구독자 **100 → 300 → 600**, **각 10분 유지**(완료조건 5), 총 31분 30초. 이벤트 발생원은 `POST /api/v1/booking` 고정 5/s. probe는 2/분으로 전 구간에 고르게 뿌렸다.

VU 1개 = SSE 커넥션 1개다(`sse.open`이 커넥션이 닫힐 때까지 블로킹한다). 각 칸은 `구간평균 / 구간최댓값`, 램프 앞 30초 제외. 원자료 `stage-stats-sse.txt`.

| 구간 | 구독자 | **전파 p95** | 전파 p99 | 수신 ev/s | 큐 깊이 | 활성 스레드 | 풀 크기 | CPU % |
|---|---|---|---|---|---|---|---|---|
| 100 구독자 | 100 | **1,249ms** | 1,286ms | 712 / 1,358 | 37 / 564 | 0.4 / 4.0 | 4 | 30.1 / 44.5 |
| 300 구독자 | 300 | **2,158ms** | 2,346ms | 2,992 / 3,115 | 3 / 53 | 0.6 / 4.0 | 4 | 40.8 / 43.5 |
| 600 구독자 (버스트 전) | 602 | **2,768ms** | 3,150ms | 5,368 / 6,218 | 50 / 307 | 1.5 / 4.0 | 4 | 53.5 / 60.7 |
| 600 구독자 (버스트 후) | 602 | 3,567ms | **9,951ms** | 7,025 / 14,978 | 0 / 0 | 0.4 / 3.0 | **16** | 60.6 / 93.8 |

**이것이 이슈가 요구한 "구독자 수 대비 브로드캐스트 지연 곡선"이다.** 100 → 300 → 600에서 p95가 1.25s → 2.16s → 2.77s로 단조 증가하고, 기울기는 구독자당 약 **3.0ms**다.

### 이 값에 무엇이 들어 있는가

`sse_propagation_ms`는 **예매 요청 송신 → 자기 `seat_id` 이벤트 수신**이다. 즉 booking API + Kafka + seat HOLD 트랜잭션 + SSE 팬아웃 전부다. 같은 iteration의 `sse_probe_booking_duration`이 평균 **36.51ms**이므로 **booking API는 전체의 1.5%밖에 안 된다.** 나머지는 Kafka + HOLD 트랜잭션 + 팬아웃이고, 클라이언트에서 더 잘게 가를 방법이 없다.

### 기울기의 정체 — 팬아웃 자체가 아니라 앞에 쌓인 큐

구독자 1명당 send 비용은 0.2~0.3ms다(§2-(a)). 600명이면 자기 이벤트의 팬아웃만으로는 **약 170ms**다. 그런데 실측 p95는 2.77s다. 차이는 **앞에 쌓인 이벤트를 기다린 시간**이다.

600 구독자 구간의 큐 깊이가 평균 50, 최대 307이다. 태스크 1건이 167ms이고 스레드가 4개이므로 큐 50은 `50 × 0.167 ÷ 4 ≈ 2.1초`의 적체다. **이것이 전파 지연의 지배적 항이다.**

평균 이용률은 `9 태스크/s × 0.167s ÷ 4 스레드 ≈ 38%`로 여유로운데도 큐가 수십~수백까지 쌓인다. 즉 **도착이 고르지 않다.** 다만 그 불균일이 어디서 오는지는 이 회차로 분리하지 못했다 — 후보는 Redis 만료 이벤트의 전달 묶임과 스케줄러 fallback인데(§2-(c)), 둘을 가르려면 이벤트 발행 지점에 경로 태그가 필요하다.

> **평균 이용률이 낮아도 도착이 몰리면 지연은 초 단위가 된다.** 그리고 그 지연은 core 4를 늘려 줄이는 것보다, 도착을 고르게 하거나 큐를 짧게(=빨리 포기하게) 만드는 쪽이 직접적이다 — 큐가 길수록 늦게 도착한 이벤트는 이미 낡은 상태를 나른다.

### 수신 축

| 구독 성립 | 697건 (구독자 600 + probe 63 + 재연결) |

**SQL이 k6를 확인한다** — `booking` 테이블의 `performance_id=17` 행 수가 **9,514**로, k6의 `mutate 9,451 + probe 63 = 9,514`와 정확히 일치한다.

## 8. 회차 4 — 큐 포화·거부 (완료조건 4)

구독자 600명이 붙어 있는 상태에서 `@mode='expire' @expire_count=2000`으로 만료 HOLD를 주입했다. 다음 60초 tick이 이를 해제하며 executor에 버스트를 넣는다. 공연을 지우지 않으므로 `performance_id`가 보존돼 붙어 있는 구독자가 그대로 유효하다.

주입 `05:21:06Z` → 실제 반영 `hold_expired 2,043건`.

### 큐 깊이 시계열 (3초 간격 폴링, 원자료 `executor-queue-poll-saturation.txt`)

```
utc      active completed pool queued
05:21:07   4.0   12786.0   4.0    427      ← 버스트 전에 이미 427이 쌓여 있다
05:21:10   4.0   12786.0   4.0    474
05:21:13  16.0   12786.0  16.0   1000      ← 큐 만석. 그제서야 풀이 4 → 16
05:21:23  16.0   12786.0  16.0   1000
05:21:34  16.0   13058.0  16.0    842
05:21:52  16.0   13058.0  16.0   1000      ← 두 번째 tick 이 다시 채운다
05:22:32  16.0   13058.0  16.0   1000
05:23:26  16.0   14579.0  16.0     30
05:23:29   0.0   14657.0  16.0      0      ← 배수 완료. 총 약 2분 20초
```

**이슈가 경고한 순서가 그대로 확인됐다** — `ThreadPoolTaskExecutor`는 **큐가 가득 차야** max까지 늘어난다. `05:21:10`에 큐가 474인데도 풀은 4였고, 1000에 닿은 `05:21:13`에야 16이 됐다. 큐 1000이 차기 전까지 실질 동시성은 **4**다.

배수에 2분 20초가 걸렸다. 16 스레드로 약 1,900 태스크를 처리했으니 태스크 1건당 약 1.2초 — 600 구독자 팬아웃 1건의 비용이다.

### 거부 = 유실

| | |
|---|---|
| 회차 전체 거부 | **2,009건** |
| executor 완료 태스크 | 17,490건 |
| 시도된 이벤트 | 19,499건 |
| **유실률** | **10.30%** |

발생 이벤트 회계가 맞는다: 예매 9,514 + 만료 해제 약 7,950(5/s × 26.5분) + 인위적 만료 2,043 ≈ **19,507**로, 위 19,499와 거의 일치한다.

거부 로그의 시각 분포 — **2,009건 전부가 `05:21:12 ~ 05:22:33` 한 구간에 들어 있다.** 큐가 1000에 붙어 있던 시각과 정확히 일치하고, 그 밖에서는 한 건도 나지 않았다. 최대 초당 **728건**(`05:21:14`).

발생 스레드는 스케줄러(`scheduling-2`)와 **Kafka 리스너(`…Container#0-0-C-1`)** 둘이다. 즉 **버스트와 무관한 일반 예매 이벤트까지 함께 드롭됐다** — 큐는 공유 자원이라 버스트의 피해가 정상 트래픽으로 번진다.

> **처음 집계에서 "05:26~05:27에 5초마다 25건씩 나는 두 번째 구간"을 보고했는데, 그건 집계 오류였다.**
> 시각 추출에 쓴 `grep -oE "T[0-9]{2}:[0-9]{2}:[0-9]{2}"`가 줄 맨 앞의 로그 타임스탬프뿐 아니라 **이벤트 페이로드 안의 `holdExpiredAt`까지** 잡았다. 매치 총수가 2,289로 실제 줄 수 2,009보다 280 많았고, 그 280이 `holdExpiredAt`이 null이 아닌 줄 수와 정확히 일치한다. 좌석 락 TTL이 5분이라 `05:21:13`에 거부된 HOLD 이벤트의 `holdExpiredAt`이 `05:26:13`이고, 그게 "5분 뒤의 두 번째 구간"으로 보였다. 25건씩 5초 간격이라는 규칙성도 chunk-size가 아니라 원래 거부 묶음의 구조가 5분 평행이동된 것이다.
>
> 줄 맨 앞 타임스탬프만 뽑아 다시 세면 합계가 정확히 2,009이고 전부 한 구간이다. **거부는 큐 포화로 전부 설명된다 — 미해명 구간은 없다.**

### 두 축의 교차검증

거부는 이벤트 드롭이므로 수신 누락과 같은 시각에 나타나야 한다. 실제로 1구간 직후(`600 구독자 버스트 후`)에 전파 p99가 3,150ms → **9,951ms**로 튀고, 구간 최대 수신율이 14,978 ev/s까지 솟는다(밀렸던 이벤트가 한꺼번에 도착). **두 축이 같은 시각에 움직인다.**

## 10. 답하지 못한 것 · 한계

- **큐가 쌓이는 이유(도착의 불균일)를 경로별로 가르지 못했다.** 평균 이용률이 38%인데 큐가 최대 307까지 간다(§7). 해제 이벤트 경로가 Redis 키 만료와 스케줄러 fallback 둘인데(§2-(c)) 이벤트에 경로 태그가 없어 어느 쪽이 몰림을 만드는지 분리할 수 없었다. 발행 지점에 태그를 붙이면 갈린다.
- **집계 오류를 한 번 냈다.** 거부 시각 분포에서 페이로드의 `holdExpiredAt`을 로그 타임스탬프로 잘못 세어 존재하지 않는 "두 번째 거부 구간"을 보고했다(§8의 주석). 줄 맨 앞 타임스탬프만 뽑아 재집계해 바로잡았다. **로그에서 시각을 뽑을 때는 줄 앞을 앵커링한다**(`^`) — 페이로드에도 시각이 들어 있다.
- **다중 인스턴스 SSE.** emitter 레지스트리가 인스턴스 로컬이라 이 측정은 **단일 인스턴스 기준**이다. 스케일 아웃하면 다른 인스턴스에 붙은 구독자는 이벤트를 아예 받지 못한다. 그건 성능이 아니라 설계 과제다.
- **전파 지연의 내부 분해.** `sse_propagation_ms`에서 booking API(36.5ms)만 뗐다. Kafka 구간과 HOLD 트랜잭션 구간은 클라이언트에서 가를 수 없다. 서버에 발생 시각 필드가 없어서다.
- **호스트 CPU가 먼저 포화한다.** 집계 포화점 247 rps는 "이 구성에서 도달한 지점"이지 엔드포인트의 이론 한계가 아니다.
- **k6 퍼센타일과 서버 퍼센타일의 자릿수 차이**는 가정용 회선 RTT다. 이 리포트에서 '앱의 비용'은 전부 서버 축으로 읽었다.
- **회차 1과 회차 2가 다른 날이다.** 같은 `IMAGE_TAG`이고 게이트를 다시 통과시켰지만 호스트 상태가 완전히 같지는 않다.

## 11. 여기서 나온 후속 과제

측정 회차이므로 **아무것도 고치지 않았다.** 근거만 남긴다.

1. **거부를 조용히 삼키지 말 것.**
   - ✅ **거부 시점의 큐 상태를 로그에 남기는 것은 이 브랜치에서 했다.** `queue=<깊이>/<용량> activeThreads=… poolSize=…/…`가 이벤트와 같은 줄에 찍힌다. 이번 회차는 3초 폴링과 15초 스크랩을 로그 시각과 맞춰 보느라 §8의 집계 오류를 걸렀는데, 큐 깊이가 로그 줄 안에 있으면 그 대조 자체가 필요 없다. 스택 트레이스는 뺐다(발생 지점이 늘 같고, 초당 728건이 찍히면 로그를 뒤덮는다).
   - ✅ **카운터 메트릭도 이 브랜치에서 붙였다.** `ticketrush_seat_sse_event_rejected_total`. 이번 회차의 10.30%는 `docker logs | grep -c`로 셌는데, 다음 회차부터는 Prometheus 축으로 바로 읽힌다. 거부는 버스트로 몰려 오므로(초당 최대 728건) 카운터는 생성 시 한 번만 만들어 거부 경로에 레지스트리 조회를 얹지 않는다.
2. **이벤트 발행 지점에 경로 태그를 붙인다.** 전파 지연의 지배적 항이 큐 대기인데(§7), 그 큐를 채우는 도착이 Redis 만료 쪽인지 스케줄러 fallback 쪽인지 지금은 가를 수 없다. 태그가 있으면 어느 쪽을 고르게 펴야 하는지가 바로 나온다 — 스레드를 늘리는 것보다 먼저 할 일이다.
3. **커버링 인덱스 `(performance_id, seat_status, hold_expired_at)`.** 집계가 index-only scan이 되면 좌석당 0.996µs의 스캔 몫(3,000석에서 비용의 70%)이 줄어든다. 고정항 1.29ms는 남는다.
4. **`deploy/nginx/`가 이번에 처음 저장소로 들어왔다.** 다른 인프라 설정도 같은 상태일 수 있다 — 호스트에만 있고 저장소에서 보이지 않는 것들. 별도 이슈로 훑어볼 만하다.

### 캡처 판독 메모

- `graph-counts-{a,b}-latency` — 계단별 rps·avg·p95. 두 장을 나란히 놓으면 §5의 좌석 수 대비 비용이 눈으로 보인다.
- `graph-counts-b-saturation` — **CPU 100% · tomcat busy 50 · hikari pending 40이 한 시각에 함께 붙는 것**이 §5 포화 판정의 근거다.
- `graph-sse-executor` — 큐가 1000에 고착됐다가 약 2분 20초에 걸쳐 빠지는 구간이 §8이다.
- `graph-sse-receipt` — 수신율 계단 700 → 3,000 → 6,000과 버스트 직후 16K 스파이크(밀렸던 이벤트의 일괄 도착).
- `graph-sse-resources` — CPU·힙·`jvm_threads_live`(110 → 127). tomcat 현재 스레드가 10에서 꿈쩍 않는 것이 "SSE는 스레드를 점유하지 않는다"의 그림이다.
- ⚠️ **`graph-sse-propagation`은 다시 찍어야 한다.** `k6_vus`(0~600)를 같은 축에 넣어 전파 지연(원단위 1.2~4.0)이 바닥에 깔렸다. `grafana-capture-links.md`의 해당 링크를 ms 스케일·지연 축 단독으로 고쳐 두었고, 구독자 계단은 `graph-sse-subscribers.png`로 분리했다.
