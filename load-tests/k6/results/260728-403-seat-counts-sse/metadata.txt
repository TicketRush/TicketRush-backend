#    단조 증가하고 기울기는 구독자당 약 3.0ms 다.
#  - 풀 크기가 600 구독자 구간에서도 core 4 에 머문다. 평균 활성 스레드가 1.5 라 늘 이유가 없다.
#    16 이 된 것은 인위적 버스트를 넣은 순간뿐이다(R4).
#  - 태스크 1건 소요 = 활성스레드 / 태스크처리율. 100명 53ms, 300명 59ms, 600명 167ms.
#    구독자 1명당 send 는 0.2~0.3ms 로 일정하고 '태스크 길이' 가 구독자 수에 비례한다
#    = 이슈가 서술한 '스레드 수요 증가' 가 아니다.
#  - 600명 자기 이벤트 팬아웃은 약 170ms 인데 실측 p95 는 2.77s 다. 차이는 앞에 쌓인 큐 대기다
#    (큐 50 x 0.167s / 4스레드 ≈ 2.1s). 평균 이용률은 38% 로 여유롭지만 도착이 60초 tick 마다
#    ~300건씩 몰려 큐가 솟는다 — 지연의 지배항은 팬아웃이 아니라 버스트다.
R3_RECEIPT_RATE=구독자당 수신 ev/s ÷ 서버 태스크/s — 100명 93.7% / 300명 98.7% / 600명(버스트전) 99.4%
#   거부가 없는 구간에서는 수신이 사실상 완전하다. 유실은 큐가 넘칠 때만 생긴다.
# ⚠ 이벤트율은 SSE_MUTATE_RATE 하나로 고정되지 않는다. 좌석 락 TTL 이 5분이라
#   (SeatLockUseCase.LOCK_TTL_MINUTES) 예매 5분 뒤 스케줄러가 해제하며 두 번째 이벤트를 낸다.
#   즉 회차 5분 이후 정상 상태는 약 10 events/s 이고, 그중 절반은 60초 tick 마다 약 300건씩
#   몰아서 들어온다. 측정 오염이 아니라 시스템의 실제 성질이므로 통제하지 않고 명시한다.

# ── 회차 4: 큐 포화·거부 (완료조건 4) ────────────────────────────────────
R4_METHOD=구독자 600명 유지 구간에서 @mode='expire' @expire_count=2000 주입 -> 다음 60초 tick 이 버스트
R4_TRIGGER_UTC=2026-07-29T05:21:06Z
R4_EXPIRED_APPLIED=2,043건 (hold_expired). 공연을 지우지 않으므로 performance_id 17 보존 = 구독자 유효
R4_QUEUE_PRE_BURST=427 (버스트 전에 이미 쌓여 있다 — 600 구독자 x ~10 events/s 의 정상 상태 적체)
R4_QUEUE_FULL_AT=05:21:13Z — 큐 1000 도달
R4_POOL_GROWTH=4 -> 16, 큐가 1000 에 닿은 바로 그 시각. 05:21:10 에 큐 474 였을 때는 여전히 4 였다
#   = 이슈가 경고한 순서의 실증. 큐 1000 이 차기 전까지 실질 동시성은 4 다.
R4_QUEUE_PINNED=05:21:52 ~ 05:22:32 구간 1000 유지(두 번째 tick 이 다시 채움)
R4_DRAIN_DONE_AT=05:23:29Z — 배수 완료. 총 약 2분 20초, 16스레드로 약 1,900 태스크
R4_TASK_COST_UNDER_LOAD=약 1.2초/태스크 (600 구독자 팬아웃 1건)
R4_REJECTED_TOTAL=2,009
R4_EXECUTOR_COMPLETED_TOTAL=17,490 (회차 전체 increase)
R4_ATTEMPTED=19,499 = 17,490 + 2,009
R4_LOSS_RATE=10.30%
R4_EVENT_ACCOUNTING=예매 9,514 + 만료 해제 약 7,950(5/s x 26.5분) + 인위적 만료 2,043 ≈ 19,507
#   -> 시도 19,499 와 거의 일치. 회계가 맞는다.
R4_REJECT_CLUSTER_1=05:21:12 ~ 05:22:33, 1,729건. 큐 1000 구간과 시각 일치. 최대 초당 728건.
#   스레드 내역: scheduling-2 1,523건 + Kafka 리스너(...Container#0-0-C-1) 206건.
#   -> 버스트와 무관한 '일반 예매 이벤트' 까지 함께 드롭됐다. 큐가 공유 자원이라 피해가 번진다.
R4_REJECT_CLUSTER_2=05:26:13 ~ 05:27:33, 280건. 5초마다 정확히 25건씩(25 = 스케줄러 chunk-size).
#   ⚠ 미해명. 같은 시각 큐 깊이가 3초 폴링과 15초 Prometheus 스크랩 양쪽에서 모두 0 이다.
#     AbortPolicy 는 큐가 가득 차야 거부하므로 관측과 모순된다. 두 샘플링 주기로 못 본 순간 포화인지,
#     게이지가 실제 큐를 반영하지 못한 것인지, 다른 기전인지 갈라내지 못했다. 단정하지 않는다.
#     확인하려면 RejectedExecutionException 발생 시점의 큐 크기를 로그에 함께 남겨야 한다.
R4_CROSSCHECK=1구간 직후 전파 p99 가 3,150ms -> 9,951ms 로 튀고 구간 최대 수신율이 14,978 ev/s 까지
#   솟는다(밀렸던 이벤트가 한꺼번에 도착). 거부 축과 수신·지연 축이 같은 시각에 움직인다.
