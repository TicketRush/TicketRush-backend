# #505 응답 gzip 압축 적용 후 조회 축 재측정 — 2026-07-28

`#348` 이 1차 병목으로 지목한 **응답 크기(회선)** 를 `#505` 로 해소한 뒤, 조회 축의 진짜 포화점을 다시 잰 회차다.

## 0. 요약

- **회선 제약은 풀렸다.** 같은 도착률(browse 60 iter/s)에서 좌석맵 p95 가 **34,970 ms → 67 ms** 로 떨어졌다. 서버가 82ms 에 만든 응답을 클라이언트가 67ms 에 받는다 — `#348` 이 기록한 "서버 82ms ↔ 클라이언트 35초" 간극이 사라졌다.
- **이 회차는 포화점에 도달하지 못했다.** 60 iter/s 에서 호스트 CPU 74.3%, `dropped_iterations` 0, 실제 RPS 가 목표를 정확히 추종했다. 판정 3요소(§13.5)가 하나도 서지 않았다.
- **다음 병목은 outbox 릴레이가 아니라 seat-service 컨테이너 메모리다.** 80 iter/s 로 올리면 cgroup OOM 으로 죽는다(`#509`). 호스트 CPU 는 그 지점에서 98% 로, 메모리가 근소하게 먼저 닿는다.
- **부하 생성기 쪽 결함을 하나 고쳤다.** k6 가 `Accept-Encoding` 을 보내지 않아 압축을 켠 뒤에도 압축 전 경로를 재고 있었다(§2).

## 2. ⚠ 먼저 고쳐야 했던 것 — k6 가 압축을 받지 않고 있었다

첫 재측정에서 `data_received` 가 **1.2 GB** 로 나왔다. `#348` 의 1.0 GB 와 같은 자릿수라 "적용이 안 됐나" 싶었지만, 서버에 curl 로 찍으면 gzip 이 정상으로 나온다. 원인은 서버가 아니라 **부하 생성기**였다.

k6 는 Go 의 투명 압축(Transport 가 `Accept-Encoding` 을 자동으로 붙이고 몰래 해제하는 동작)을 끄고 인코딩을 직접 관리한다. 시나리오가 헤더를 명시하지 않으면 비압축 응답을 받는다.

호스트 `ens5` TX 델타로 요청당 실측한 값이다(TLS·TCP 오버헤드 포함).

| 클라이언트 | 요청당 바이트 | `Content-Encoding` |
|---|---|---|
| curl `Accept-Encoding: gzip` | 16,502 | gzip |
| curl `Accept-Encoding: identity` | 232,724 | 없음 |
| **k6 (헤더 없음)** | **228,390** | 없음 |
| k6 `Accept-Encoding: gzip` 명시 | **11,894** | gzip |

**이 함정은 조용하다.** 헤더가 없으면 응답에 `Content-Encoding` 자체가 안 붙으므로 k6 쪽에서는 "압축이 꺼졌다"가 아니라 "원래 그런 것"처럼 보인다. 서버 curl 은 잘 되니 설정을 의심하지도 않게 된다. 실제 브라우저는 항상 이 헤더를 보내므로, 헤더 없는 여정은 사용자를 재현하지도 않았다.

`browse()` 의 auth 헤더 객체에 한 줄 넣어 고쳤다(목록·상세·좌석맵 세 요청이 그 객체를 공유한다).

## 3. 회선 제약은 풀렸다

같은 도착률(browse 60 iter/s)에서 `#348` 과 비교한 값이다.

| | #348 (비압축) | **이 회차 (압축)** |
|---|---|---|
| 좌석맵 p95 | **34,970 ms** | **67 ms** |
| 여정 p95 | 14,340 ms | 108 ms |
| 호스트 TX | 5.8 MB/s | **0.78 MB/s** |
| `dropped_iterations` | 457 | **0** |
| 실패율 | 0% | 0% |

전체 회차 기준 `data_received` 는 **493 MB / 15분 21초**다. 같은 시나리오를 비압축으로 3분 32초 돌렸을 때가 1.2 GB 였다.

**TTFB 는 원래 빨랐다.** `#348` 의 서버 처리 시간이 81.96ms 였고 그때도 그 값이었다. 바뀐 것은 본문 수신 구간이다 — 판정을 `k6_http_req_waiting_p95`(TTFB) 대비 `k6_http_req_receiving_p95`(본문 수신)로 하라는 런북 §13.6 의 지시가 정확히 이 축을 가리킨다.

## 5. 다음 병목 — 릴레이가 아니라 seat-service 메모리다

**60 iter/s 는 여유롭고 80 iter/s 는 죽는다.** 그 사이에 벽이 둘 있고 순서는 이렇다.

### 5.1 첫 번째 — seat-service 컨테이너 OOM (`#509`)

80 iter/s 스모크에서 **HTTP 500 이 1,073건** 났고 전부 좌석맵이다. seat-service 앱 로그에는 대응 예외가 없고, 게이트웨이가 `Connection refused: seat-service:8086` 512건 · `PrematureCloseException` 400건 · `Connection reset` 384건을 뱉었다. 앱이 에러를 던진 게 아니라 **프로세스가 사라졌다.**

```
[Tue Jul 28 02:58:20 2026] Memory cgroup out of memory: Killed process 10681 (java)
  constraint=CONSTRAINT_MEMCG, anon-rss:641288kB
```

> `docker inspect` 의 `OOMKilled` 는 `false` 로 나온다(재시작 뒤 상태를 읽는다). 판정은 `dmesg` 의 `CONSTRAINT_MEMCG` 로 한다.

`mem_limit` 은 **640 MiB**, `-Xmx` 는 **384 MiB** 인데 OOM 시점 RSS 가 **626 MiB** 였다. 힙으로 설명되지 않는 몫이 약 242 MiB 다. 이 회차 종료 후 RSS 도 **546 / 640 MiB (85%)** 였다.

**압축은 원인이 아니다.** `#509` 에서 실측으로 갈랐다 — 같은 도착률에서 gzip 과 identity 의 ΔRSS 가 7% 이내로 같고(21,816 vs 20,460 KB), gzip 만 15/s → 60/s 로 올렸을 때 요청당 비용이 오히려 줄었다(9.59 → 5.92 KB/req). RSS 는 누수 없이 고원에 도달한다(15/s ≈ 456 MiB, 60/s ≈ 482 MiB). **압축이 회선 뚜껑을 걷어내자 그동안 도달할 수 없던 지점이 드러난 것**이다.

### 5.2 두 번째 — 호스트 CPU

80 iter/s 스모크에서 CPU 가 **91-99%** 로 포화했다. 메모리를 풀어도 곧바로 여기를 만난다. 2 vCPU 한 대에 컨테이너 8개와 관측 스택이 동거하는 구성이라(ADR 0006·0007) seat-service 만 키우는 것도 다른 서비스 예산을 깎는다.

### 5.3 outbox 릴레이는 이번엔 병목이 아니었다

`#505` 코멘트가 "다음은 릴레이 상한"을 예고했지만, 이 회차의 backlog 최대는 **booking 272 / seat 55** 로 `#348` 의 **868** 보다 낮다. `in_flight` 도 booking 29 / seat 0 이다.

**단 직접 비교는 아니다.** 이 회차의 예매 축은 최대 12 iter/s 로, `#348` 스파이크 회차보다 낮다. 릴레이 상한 판단은 `#509` 를 해소해 조회·예매 축을 함께 더 올린 회차에서 해야 한다.

## 7. 이 회차가 답하지 못한 것

- **조회 축의 포화점.** 60 iter/s 에서 CPU 74.3%, 80 iter/s 에서 OOM 이라 그 사이를 훑지 못했다. `#509` 해소 후 재측정해야 한다.
- **릴레이 상한.** 위 5.3 대로 예매 축이 낮아 릴레이를 밀어붙이지 못했다.
- **구간별 RSS 궤적.** 샘플러의 RSS 수집이 이스케이핑 오류로 전 구간 실패했다(출력의 `DEAD` 는 **서비스가 아니라 측정이 죽은 것**이다 — 실패율 0%·`RestartCount=0` 으로 확인). RSS 는 회차 종료 후 단발로만 읽었다. 다음 회차에서는 샘플러를 먼저 검증하고 시작할 것.
- **호스트 네트워크 지표.** `node_network_*` 가 컨테이너 것이라 회선 축을 Prometheus 로 못 본다(`#508`). 이 회차의 TX 는 호스트 `/proc/net/dev` 를 직접 읽어 채웠다.
