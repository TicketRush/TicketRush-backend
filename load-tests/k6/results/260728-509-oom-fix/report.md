# #509 seat-service OOM 처방 검증 — 80 iter/s 구간 재측정 — 2026-07-28

## 0. 요약

**OOM 은 해결됐다.** 1차에서 프로세스를 죽였던 구간을 재시작 0회·실패율 0.00% 로 완주했다. peak RSS 는 571.8 / 640 MiB (89.4%) 로, 1차 사망 지점 626 MiB 아래에 머물렀다.

**그러나 도착률 목표에는 도달하지 못했다.** 목표 96 iter/s(browse 80 + purchase 16) 중 실제 달성은 **56.35 iter/s** 이고 555 iteration 이 드롭됐다. 서버 p95 1.62s, 클라이언트 좌석맵 p95 7.8s 로 임계값(800ms)을 크게 넘었다.

**다음 벽은 호스트 CPU 다 — 스레드 상한이 아니다.** CPU 가 99% 에 닿은 것이 06:43:00(k6 63 rps)인데 tomcat 스레드가 50 에 포화된 것은 06:45:30(193 rps)으로 **CPU 가 2분 30초 먼저 찼다.** 2 vCPU 에서 CPU 가 상한인 이상 `max-threads` 를 되돌려도 처리량은 늘지 않고 메모리만 더 쓴다.

## 3. 왜 버텼나 — 스레드 스택 가설이 실측으로 확인됐다

`#509` 는 "힙으로 설명되지 않는 242 MiB" 의 출처로 스레드 스택을 지목했다. peak 시점 분해가 그것을 지지한다.

| | peak |
|---|---|
| heap used | 148 MiB |
| nonheap used (metaspace + 코드캐시) | 211 MiB |
| 합계 | 359 MiB |
| **실제 RSS** | **571.8 MiB** |
| **차이** | **약 213 MiB** |

같은 시점 `jvm_threads_live = 153` 이다. 스레드당 스택 1 MiB(x64 기본) 기준 약 153 MiB 로, 나머지는 다이렉트 버퍼·GC 구조체·JVM 내부다. **차이의 대부분이 스레드 스택으로 설명된다.**

1차에 tomcat 이 200 까지 늘었다면 live 는 300 을 넘고 스택만 300 MiB 가 되어, heap 148 + nonheap 211 과 합쳐 640 MiB 를 넘는다 — 관측된 626 MiB 사망과 일치한다.

## 4. 그러나 벽은 스레드가 아니라 CPU 다

`max-threads` 를 200 → 50 으로 줄인 것이 처리량 손실의 원인이라면, **스레드가 먼저 포화하고 그 뒤에 CPU 가 따라와야** 한다. 실측은 반대다.

| 시각 | k6 rps | CPU% | tomcat busy | tomcat current |
|---|---|---|---|---|
| 06:43:00 | 63.6 | **95.7** | 0 | 25 |
| 06:44:15 | 128.2 | 82.0 | 0 | 30 |
| 06:44:30 | 140.9 | 82.0 | 45 | **50** (상한 도달) |
| 06:45:15 | 191.5 | **99.2** | 19 | 50 |
| 06:45:30 | 193.4 | **99.1** | **50** | 50 |
| 06:46:30 | 221.4 | **99.1** | **50** | 50 |

**CPU 99% 도달이 06:43:00, 스레드 50 포화가 06:45:30 — CPU 가 2분 30초 앞선다.**

06:44:15 까지는 스레드 25-30 개로 128 rps 를 처리했다. Little's law 로 검산하면 `128 × 0.24s ≈ 31` 로 관측된 `current=30` 과 맞는다 — **그 구간에서 50 은 넉넉했다.** 스레드가 상한에 붙은 것은 CPU 가 이미 포화해 응답이 느려지고, 느려진 만큼 동시 요청이 쌓인 **결과**다.

**결론: `max-threads: 50` 은 이 구성에서 옳은 선택이다.** 2 vCPU 가 상한인 이상 200 으로 되돌려도 처리량은 늘지 않고 스레드 스택만 150 MiB 더 먹어 1차의 OOM 으로 되돌아간다. 처방이 벽을 옮긴 것이 아니라, **원래 있던 CPU 벽이 메모리 벽보다 앞에 있었다는 것이 드러난 것**이다.

### 4.1 기준선은 26-38 MiB 만 내려갔다 — 그리고 그것이 정상이다

| | RSS |
|---|---|
| 직전 회차 기준선 | 439 MiB |
| 이 회차 기준선 (부하 전) | **401.4 MiB** |

`max-threads` 는 **상한**이지 실제 생성 수가 아니다. 무부하에서는 `min-spare-threads`(10)만큼만 떠서 기준선 차이가 작다. **이 처방의 효과는 부하 중 스레드가 200 까지 늘지 못하는 것으로 나타나고**, §3 의 분해가 그 증거다. `#509` 의 처방 설명에서 "기준선이 내려갈 것"으로 예상한 것은 부정확했다.

## 7. 유효성

- **좌석 배정은 건전하다.** `e2e_seat_conflict` 0%, `e2e_seat_exhausted` 0%, 예매 2,699건 전부 201. 좌석 재고 20,800 에서 시작해 소진 압박이 없었다.
- **checks 15,644건 전부 통과**, 실패율 0.00%. 즉 이 회차의 지연은 **에러가 아니라 대기**다.
- **서버 p95(1.62s)와 클라이언트 좌석맵 p95(7.8s)의 차이 약 6초가 큐 대기**다. 서버가 처리를 시작하기 전에 요청이 기다린 시간이며, k6 쪽 VU 고갈과 같은 현상의 양면이다 — k6 가 `Insufficient VUs, reached 600 active VUs` 를 경고했고 555 iteration 이 드롭됐다.
- **도착률 목표 미달을 성능 수치로 읽으면 안 된다.** 목표 96 iter/s 중 56.35 만 발생했으므로, 이 회차는 "96 iter/s 에서의 응답 특성"이 아니라 **"이 구성이 56 iter/s 까지만 소화한다"** 는 관측이다.

## 8. 한계 — 다음 회차로 그대로 넘길 것

- **컨테이너별 메모리 시계열이 없다(#515).** cAdvisor 를 넣었으나 이 호스트(Docker 29.1.3 + cgroup v2 + systemd)에서 컨테이너를 하나도 열거하지 못해 되돌렸다. RSS 는 `docker stats` 4초 샘플(`host-samples-ramp.csv`)로만 남으므로 **15초 스크랩 시계열이 아니고, 샘플 사이의 짧은 피크를 놓칠 수 있다.** peak 571.8 MiB 는 하한으로 읽어야 한다.
- **부하가 끝나도 RSS 가 돌아오지 않는다.** 종료(06:46:29) 후 5분이 지난 06:51:24 에도 **564.7 MiB (88.2%)** 다. 직전 회차도 종료 후 546 MiB 였다. **연속 회차를 돌리면 두 번째 회차의 기준선이 88% 에서 시작한다** — 회차 사이에 seat-service 를 재시작하지 않으면 앞 회차의 워킹셋이 뒤 회차의 OOM 여유를 잡아먹는다.
- **`max-threads` 를 바꿨으므로 직전 회차와 처리량·지연을 직접 비교할 수 없다.** 비교는 "OOM 여부"와 "어느 벽에 먼저 닿는가"로 한정했다.
- **단일 EC2 에 앱 8개 + Kafka·MySQL·Redis·관측 스택이 동거한다.** CPU 99% 는 seat-service 단독 소비가 아니다. 이 회차의 산출물은 "앱의 성능"이 아니라 **"이 구성의 최대치"** 다.
- **`m7i-flex.large` 는 베이스라인 40% + 버스트다.** CPU 99% 가 5분 가까이 이어졌으므로 이 회차는 버스트 크레딧을 썼다. 더 긴 회차에서는 같은 수치가 재현되지 않을 수 있고, 잔량 지표가 없어 사후 확인이 어렵다.
- **Nginx 는 부하 경로에 있으면서 전용 지표가 없다.** 게이트웨이 앞단이 상한인지 가릴 수 없다.
- **결제·티켓 발급이 여정에서 빠져 있다.** 파이프라인 backlog 회복시간은 이 회차로 답하지 못한다(#504).
- **1차 배포 실패 이후의 재배포본에서 측정했다.** `MaxMetaspaceSize=128m` 으로 seat-service 가 좀비가 됐던 구간(PR #516 에서 제거)과 EC2 를 손으로 고친 구간이 있었다. **이 회차는 저장소와 배포본이 다시 일치한 뒤의 측정이며**(EC2 compose 에 `MaxMetaspaceSize`·`cadvisor` 잔여 0건 확인, `IMAGE_TAG` 전 서비스 동일), 그 전 시점의 수치는 이 리포트에 섞지 않았다.

## 9. 다음 벽 — 메모리도 스레드도 아니다

| 축 | 이 회차 | 판정 |
|---|---|---|
| 회선 | 1.12 / 5.8 MB/s (19%) | 한가하다 (#505 로 해소) |
| seat 메모리 | 571.8 / 640 MiB (89%) | **버텼지만 여유 10%** |
| **호스트 CPU** | **99.29%** | **포화 — 이것이 상한이다** |
| tomcat 스레드 | 50 / 50 | 포화. 단 CPU 포화의 결과다 |

**CPU 를 내리지 않으면 그 위 구간은 잴 수 없다.** 그리고 `mem_limit` 상향은 답이 아니다 — 여유가 550 MiB 뿐이고(ADR 0006), 메모리를 풀어도 CPU 천장을 바로 만난다.

**응답 크기를 줄이는 것이 메모리와 CPU 를 동시에 내리는 유일한 축이다.** 좌석맵은 페이지네이션 없이 2,080 객체를 직렬화하며, 요청당 워킹셋과 직렬화 CPU 가 그 크기에 비례한다. `#509` 가 응답 스키마 축소를 범위에서 뺀 것은 이 회차 결과를 보고 판단하기 위해서였고, **이제 그 판단 근거가 나왔다.**

- `#469` (좌석 배치 조회 Redis 캐싱) — 캐싱은 DB 조회를 줄이지만 직렬화 CPU 와 출력 버퍼는 그대로다. 이 회차가 가리키는 비용이 정확히 그 부분이므로 **캐싱만으로는 이 벽을 넘지 못한다.**
- 응답 축소·페이지네이션 — 응답 형태가 정해지기 전에 캐시를 설계하면 다시 만들어야 한다(`#509` 코멘트의 순서 논거).
