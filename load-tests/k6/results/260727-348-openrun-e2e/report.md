# #348 오픈런 스파이크 e2e 종합 부하 측정 — 조회 경로의 1차 병목은 응답 압축 부재였다

> **범위** — 계단식·오픈런 스파이크 두 회차와 검표 스모크를 모두 실측했다.

## 요약

**"최대 처리량 X RPS" 는 나오지 않았다. 그 대신 왜 나올 수 없는지가 나왔다.**

- **1차 병목은 앱이 아니라 응답 크기다.** 좌석맵 조회에서 **서버는 81.96ms 인데 클라이언트는 p95 34.97초**였다. 같은 구간 호스트 CPU 58.86%, gateway 5xx 0건. 응답 **221KB 에 gzip 이 걸리지 않는다** — `Accept-Encoding` 을 보내도 `Content-Encoding` 이 없다. 압축하면 **9,709B(95.66% 절감)** 이다.
- **회선을 피해 조회 도착률을 내리자 좌석맵 p95 가 92.57ms 로 떨어졌다.** 스모크 당시 서버 처리 시간과 사실상 같은 값이다. 그 35초가 전송 대기였다는 것이 이 대조로 확정된다.
- **그 부하에서 앱은 전혀 힘들지 않았다.** 실패 0%(0/40,597), 도착률 100% 충족, **VU 6개**, Tomcat busy **최대 1**, HikariCP pending **0**.
- **대신 비동기 발행이 밀렸다.** HTTP 가 노는 동안 `outbox_backlog` 가 **868** 까지 쌓였다(컨슈머 lag 은 최대 52). 릴레이 실효 상한 53.2/s(#489)에 걸린 것이며, 결제를 하지 않아 **예매 1건이 이벤트 3건**이 되는 이 측정의 조건이 겹쳤다.
- **oversell 0**, 예매 18,449건 전부 성공, 좌석 충돌 0.
- **오픈런 스파이크(유입 6배, 10초 램프)도 흡수했다.** 좌석맵 p95 105.83ms, 실패 0%, 도착률 100% 충족.
- **다만 부하가 끝난 뒤에 backlog 정점이 온다.** 피크 중 최대 358 → **피크 종료 86초 뒤 1,219(3.4배)**. 피크에 만든 예매가 5분 뒤 일제히 만료되며 **2차 파동**을 만든다. 회복(backlog 0)까지 피크 종료 기준 **6분 33초**. 그 파동 내내 HTTP 응답은 멀쩡했다 — **HTTP 지표만 보면 이 병목은 안 보인다.**

- **#500 이관 항목 통과** — 임계 완화 배포 후 첫 검표 트래픽에서 `not_permitted` 증가분 **0**, 서킷 closed 유지, booking 왕복 2,400건 전부 성공(§7).

**결론: 조회 축을 올리면 회선이 먼저 차고, 회선을 피하면 앱이 여유롭다.** 그 사이에 앱의 무릎이 있는데 현재 응답 크기로는 그 구간을 통과할 수 없다. **압축을 켜는 것이 다음 병목을 보기 위한 선결 조건이다.**

이슈 본문과 다른 사실 셋(좌석 HOLD 가 API 가 아님 · 결제/티켓발급 실행 불가 · SLO 1,000 RPS 불가)은 §2 에 정리했고 [이슈 코멘트](https://github.com/TicketRush/TicketRush-backend/issues/348#issuecomment-5088692942)로 정정했다.

## 1. 무엇을 쟀나

개별 핫패스 측정(#344 좌석 경합 · #345 만료 청크 · #346 발행 유실 · #347 Inbox 멱등 · #402 검표 스파이크 · #496 booking 장애 주입)과 달리, **사용자 여정 전체를 게이트웨이를 통해** 부하 걸어 현재 구성의 최대 처리량과 1차 병목을 찾는다.

토폴로지는 [ADR 0004](../../../../docs/adr/0004-load-test-execution-topology.md) 그대로다 — **k6 는 로컬, 대상은 AWS 배포본**. 관측 스택은 대상과 같은 EC2 안에 있고([ADR 0007](../../../../docs/adr/0007-observability-stack-colocation.md)) SSH 터널로 접근한다.

측정 대상 배포본은 `d5571697` 이다. **#496 이 `slowCallDurationThreshold` 를 300ms → 500ms 로 완화한 변경이 처음 나간 배포본**이라, 이 회차의 검표 스모크가 그 조정값을 처음 실트래픽으로 확인하는 자리가 된다(§7).

## 2. 이슈 본문과 실제 구조가 달랐던 지점

시나리오를 쓰면서 코드로 확인한 결과 이슈 본문의 여정 정의 중 셋이 실제와 달랐다. 셋 다 측정 설계를 바꾸는 값이라 [이슈 코멘트](https://github.com/TicketRush/TicketRush-backend/issues/348#issuecomment-5088692942)로 정정을 남겼다.

### 2.1 좌석 선점(HOLD)은 HTTP API 가 아니다 — 여정 순서가 역순이다

본문 여정은 `좌석맵 조회 → 좌석 선점(HOLD) → 예매 생성` 이지만 HOLD 를 여는 공개 엔드포인트가 없다. `SeatController` 는 GET 뿐이고 진입점은 `BookingCreatedEventListener`(Kafka) 하나다.

```
POST /api/v1/booking → booking + outbox 한 트랜잭션 커밋
  → OutboxRelayScheduler (fixedDelay 5s, batch-size 300)
    → booking-created-topic
      → seat-service BookingCreatedEventListener (groupId=seat-group, concurrency 1)
        → SeatFacade.tryLockSeat
```

**예매 생성이 좌석 선점을 유발한다.** k6 가 잴 수 있는 것은 유입 축이고, HOLD 는 릴레이·컨슈머 뒤에서 일어나므로 처리 축(`ticketrush_outbox_backlog` + consumer lag)에서 따로 본다. 유입 RPS 와 HOLD 처리율은 애초에 같은 값이 될 수 없다.

### 2.2 결제·티켓 발급은 이 배포본에서 실행할 수 없다

`StubPaymentApprovalClient` 가 `@Profile("!prod")` 이고 javadoc 이 "운영(prod) 프로파일에서는 환경변수 설정과 무관하게 절대 활성화되지 않는다"고 못박는다. ADR 0004 가 정한 측정 대상이 `prod` 단독 배포본이라 `PAYMENT_PG_STUB_ENABLED=true` 를 줘도 stub 은 뜨지 않는다. 실 Toss 는 `paymentKey` 를 PG 가 발급하므로 k6 가 만들 수 없고, 웹훅도 paymentKey 로 PG 에 재조회해 진위를 검증한다.

→ **여정을 예매 생성까지로 한정했다.** 완료 조건의 "예매확정→티켓발급 파이프라인 backlog 회복시간"은 이 회차에서 측정하지 못하며, [#504](https://github.com/TicketRush/TicketRush-backend/issues/504)로 분리해 `payment-confirmed-topic` 에 이벤트를 직접 주입하는 방식으로 잰다. prod 에서 stub 을 허용하는 방향은 **배포본에 결제 우회 경로가 환경변수 하나로 켜지는 상태를 만들기 때문에** 택하지 않았다.

### 2.3 목표 SLO 는 이 하드웨어에서 성립하지 않는다

ADR 0007 의 배치는 **단일 EC2 `m7i-flex.large`(2 vCPU / 7.6 GiB)** 에 앱 8개 + MySQL·Redis·Kafka·Prometheus·Grafana 다. #344 가 `POST /api/v1/booking` **단독** 258 RPS 에서 호스트 CPU 99.87% 를 봤다. 이슈가 세운 "조회 경로 1,000+ RPS" 는 이 구성에서 물리적으로 불가능하다.

따라서 이 회차의 산출물은 **"SLO 달성 여부"가 아니라 "현재 구성의 최대치와 그 상한을 만드는 자원"** 이다.

## 3. 1차 병목 — 조회 경로는 앱이 아니라 응답 크기에서 막힌다

스모크 회차(캘리브레이션 목적, 수치는 폐기 전제)에서 예상하지 못한 것이 나왔다.

### 3.1 서버는 82ms, 클라이언트는 35초

| 축 | 좌석맵 조회 (`GET /api/v1/seat/{id}/seat-layouts`) |
|---|---|
| **서버 처리 시간** (`http_server_requests_seconds`) | 평균 **81.96ms** (구간 max 239.44ms) |
| **클라이언트 체감** (k6) | 평균 **6.22s** / p95 **34.97s** / max **59.99s** |
| 호스트 CPU | 58.86% (피크 82.83%) |
| gateway 5xx | **0건** (시계열 자체가 생성되지 않음) |

**400배 차이다.** 앱은 82ms 에 응답을 만들어 놓고, 그것을 전달하는 데 35초가 걸렸다. 호스트 CPU 는 포화가 아니었고 5xx 도 없었다.

같은 회차의 다른 엔드포인트는 멀쩡했다.

| 엔드포인트 | 클라이언트 평균 | p95 |
|---|---|---|
| 공연 목록 | 137.08ms | 449.74ms |
| 공연 상세 | 111.17ms | 352.95ms |
| **예매 생성** | **182ms** | **600.39ms** |
| **좌석맵** | **6,220ms** | **34,970ms** |

**좌석맵 하나가 여정 전체를 무너뜨렸다.** k6 가 받은 총량은 1.0 GB, 실효 수신 속도는 4.5 MB/s 였다.

### 3.2 gzip 이 걸리지 않는다

응답 크기와 압축 여부를 단발 요청으로 확인했다.

```
$ curl -H 'Accept-Encoding: gzip' -o /dev/null -w '%{size_download}' .../seat/4/seat-layouts
220990

$ curl -D - -H 'Accept-Encoding: gzip' -o /dev/null .../seat/4/seat-layouts | grep -i content-encoding
(없음)
```

**`Accept-Encoding: gzip` 을 보내도 크기가 그대로고 `Content-Encoding` 헤더가 없다.** 원인은 두 겹이다.

- Spring Boot 의 `server.compression.enabled` 기본값이 **false** 이고, 어느 서비스의 `application.yml` 에도 설정이 없다
- 호스트의 Nginx 리버스 프록시에도 `gzip` 설정이 없다(`docs/production-domain-https.md` §7 의 사이트 설정에 gzip 지시어가 없다)

좌석맵은 페이지네이션 없이 그 공연의 전 좌석을 반환한다. 공연당 2,080석 기준 **221KB**, 좌석당 평균 107.6 bytes 다.

```json
{"seat_id": 26121, "seat_layout_id": 4, "seat_number": "Z-1", "seat_status": "HOLD", "hold_expired_at": "2026-07-27 08:51:08"}
```

조회 여정의 다른 엔드포인트는 전부 작다. **여정 1회 수신량의 99% 가 좌석맵 하나다.**

| 엔드포인트 | 응답 크기 | 여정 내 비중 |
|---|---|---|
| `GET /api/v1/performance` (목록) | 1,775 B | 0.79% |
| `GET /api/v1/performance/{id}` (상세) | 367 B | 0.16% |
| **`GET /api/v1/seat/{id}/seat-layouts`** | **223,720 B** | **99.05%** |
| 합계 (browse 1 iteration) | 225,862 B | 100% |

압축을 켜면 여정 1회가 약 11.8KB 가 되어 **19배** 줄어든다. 즉 **개선 대상은 좌석맵 하나로 좁혀진다.**

> 참고로 같은 seat-service 에 **`GET /api/v1/seat/{id}/seat-counts`(203 bytes)** 가 이미 있다 — 전체/가용/판매/홀드 개수만 준다. 화면이 항상 전 좌석 배열을 필요로 하는지는 별개로 볼 여지가 있으나, 이 회차의 범위를 넘으므로 후속 판단으로 남긴다.

### 3.3 압축하면 23배 줄어든다 — 실측

같은 페이로드(223,720 bytes)를 받아 로컬에서 압축해 본 값이다.

| 압축 | 크기 | 원본 대비 | 절감 |
|---|---|---|---|
| 없음 (현재) | 223,720 B | 100% | — |
| gzip level 1 | 13,045 B | 5.83% | 94.17% |
| **gzip level 6** (Spring Boot 기본) | **9,709 B** | **4.34%** | **95.66%** |
| gzip level 9 | 9,318 B | 4.17% | 95.83% |

**221KB → 9.7KB.** 좌석 객체가 같은 키 구조를 2,080번 반복하니 압축이 잘 먹는다.

회선 제약으로 환산하면 이렇다. 실측 수신 4.5 MB/s 기준으로 221KB 응답은 **약 20 iter/s** 가 상한인데, 9.7KB 로 줄면 **약 464 iter/s** 가 된다. 그 지점에서는 회선이 아니라 서버가 병목이 되므로, **압축은 다음 병목을 드러내기 위한 선결 조건이기도 하다.**

### 3.4 압축을 어디에 켜야 하는가 — 선택지는 둘이다

게이트웨이는 **WebFlux/Netty 기반 Spring Cloud Gateway** 이고(`spring-cloud-starter-gateway-server-webflux`), 라우트 필터는 전부 `RewritePath` 뿐이라 **응답 본문을 가공하지 않는다.** 따라서 백엔드가 압축해 보내면 게이트웨이가 `Content-Encoding` 을 유지한 채 그대로 프록시한다.

| | (A) 각 MVC 서비스에서 압축 | (B) Nginx 에서 압축 |
|---|---|---|
| 변경 | 서비스 `application.yml` 에 `server.compression.enabled: true` | 호스트 `nginx` 사이트 설정에 `gzip on` |
| 재배포 | 필요 | 불필요(`nginx -s reload`) |
| CPU 부담 | 앱 컨테이너에 분산 | **호스트 nginx 한 곳에 집중** |
| 내부 홉(서비스→게이트웨이) | 압축됨 | 비압축 그대로 |

**(A)가 구조적으로 낫다.** 이 배포본은 앱 8개 + 인프라가 2 vCPU 한 대에 동거하므로 nginx 한 곳에 압축 CPU 를 몰면 그 자체가 새 병목이 될 수 있고, (A)는 내부 홉의 전송량까지 함께 줄인다. 다만 어느 쪽이든 **먼저 재측정으로 확인해야 한다** — 압축이 켜지면 회선 제약이 23배 완화되면서 다음 병목(호스트 CPU 로 추정)이 드러날 것이기 때문이다.

> 이 회차는 "병목 발견"이 목적이므로 설정 변경은 하지 않았다. 튜닝은 후속 이슈로 분리한다(이슈 #348 본문 방침).

### 3.5 이것은 측정 환경의 한계인 동시에 실제 서비스 문제다

k6 가 가정용 회선을 타는 것은 ADR 0004 가 기록해 둔 이 토폴로지의 한계다. 하지만 **실제 사용자도 같은 조건에 있다.** 오픈런 순간 모바일 회선으로 좌석맵을 여는 상황이 정확히 이 측정과 같다 — 서버가 82ms 에 응답을 만들어도 사용자는 221KB 를 받아야 화면을 본다.

그래서 이 발견은 "측정이 왜곡됐다"가 아니라 **"조회 경로의 실질 상한이 앱 처리 성능이 아니라 응답 크기에 있다"** 로 읽어야 한다.

> 이 병목은 [#469](https://github.com/TicketRush/TicketRush-backend/issues/469)(좌석 배치 조회 Redis 캐싱)와 **별개 축**이다. 캐싱은 서버의 조회 부하를 줄이지만 **응답 크기는 그대로**다. 회선을 타는 구간은 캐싱으로 개선되지 않는다.

## 4. 본 회차 — 계단식

프로파일은 §3 의 캘리브레이션대로 조회 축을 회선이 감당하는 범위로 묶고 예매 축을 계단으로 올렸다.

```
browse    2 →  4 →  8 → 10 iter/s   (각 5분 유지, 계단 전환 램프 10s)
purchase  5 → 10 → 20 → 25 iter/s   (ratio 2.5)
측정 창    2026-07-27T14:38:24Z ~ 14:59:06Z (20m30s)
```

### 4.1 회선을 피하자 좌석맵이 서버 처리 시간으로 수렴했다

| 좌석맵 조회 | 스모크 (browse 60/s) | 본 회차 (browse ≤10/s) |
|---|---|---|
| 클라이언트 p95 | 34,970ms | **92.57ms** |
| 클라이언트 평균 | 6,220ms | **64.80ms** |
| 서버 평균 | 81.96ms | 11.88ms |
| 실효 수신 | 4.5 MB/s | 1.1 MB/s |

**92.57ms 는 스모크 당시 서버 처리 시간(81.96ms)과 사실상 같다.** 즉 스모크의 35초는 앱이 만들어낸 지연이 아니라 **전송 대기였다는 것이 이 대조로 확정된다.** §3 의 진단이 맞았다.

지연을 단계별로 쪼갠 값도 같은 방향이다 — TTFB(`waiting`) p95 82.67ms 대비 본문 수신(`receiving`) p95 는 56.14ms 로, 회선에 여유가 있을 때는 수신이 지배하지 않는다.

### 4.2 앱은 이 부하에서 전혀 힘들지 않았다

| 지표 | 값 |
|---|---|
| `http_req_failed` | **0.00%** (0 / 40,597) |
| checks | **100.00%** (25,829 / 25,829) |
| `dropped_iterations` | **0** (요약에 항목 자체가 없다 = 도착률을 전부 채웠다) |
| **사용된 VU** | **최대 6개** (350 할당) |
| **Tomcat busy** | **최대 1** (상한 200) |
| **HikariCP pending** | **0** (풀 10) |
| gateway 5xx | **0건** |
| 예매 생성 | 18,449건 전부 성공, 좌석 충돌 0 |

여정 전체 p95 가 150ms, 예매 p95 가 46.06ms 다. **VU 6개로 도착률을 다 채웠다는 것이 가장 단순한 증거다** — 앱이 요청을 즉시 소화했다는 뜻이다.

### 4.3 그런데 비동기 발행은 밀렸다 — 예매 축의 실질 상한

HTTP 계층이 놀고 있는 동안 **outbox 가 쌓였다.**

| | 평균 | 최대 |
|---|---|---|
| `ticketrush_outbox_backlog` (booking) | 150.31 | **868** |
| `ticketrush_outbox_backlog` (seat) | 43.82 | 494 |
| Kafka consumer lag | 2.77 | 52 |
| 호스트 CPU | 54.29% | **100.00%** |
| 호스트 iowait | **11.29%** | 19.02% |

**컨슈머는 따라왔지만(lag 최대 52) 릴레이가 못 따라갔다.** §2 에 적은 구조적 상한이 실제로 걸린 것이다 — 릴레이 실효 발행률은 중위 53.2/s(#489)인데, 이 회차의 이벤트 생성률은 그보다 컸다.

이벤트가 예매 건수의 3배로 늘어나기 때문이다.

```
예매 1건 → BookingCreatedEvent 1건
         → (5-6분 뒤 만료) BookingExpiredEvent 1건 + SeatHoldExpiredEvent 1건
```

피크 구간 purchase 25/s 에서 생성 25/s + 만료 계열 약 50/s = **약 75/s** 가 되어 릴레이 상한 53.2/s 를 넘는다. 실제로 **생성한 18,449건 중 13,651건(74%)이 측정 창 안에서 EXPIRED 로 전이했다.**

iowait 이 스모크의 1.85% 에서 11.29% 로 6배 오른 것도 같은 원인이다. 조회 위주였던 스모크와 달리 이 회차는 booking·outbox 쓰기가 실렸다.

> ⚠️ 이 만료 부하는 **결제를 하지 않아서 생긴 이 측정의 조건**이다(§2.2). 결제까지 도는 실제 운영에서는 확정된 예매가 만료되지 않으므로 이벤트 구성이 다르다. 이 수치를 운영 예측에 그대로 쓸 수 없다.

### 4.4 포화점에는 도달하지 못했다 — 그리고 그것이 이 회차의 결론이다

완료 조건은 "현재 구성의 최대 처리량(포화점)"을 요구했지만 **이 토폴로지로는 앱의 포화점을 측정할 수 없다.**

- 조회 축을 올리면 → **회선이 먼저 찬다**(§3). 앱이 아니라 k6 를 돌리는 집 회선을 재게 된다.
- 회선을 피해 낮추면 → **앱이 여유롭다**(§4.2). VU 6개로 끝난다.

즉 두 축 사이에 앱의 무릎이 있는데, 그 구간을 **현재 응답 크기로는 통과할 수 없다.** 압축을 켜면 회선 제약이 23배 완화되어(§3.3) 비로소 앱을 밀어붙일 수 있다.

**따라서 이 회차가 식별한 것은 "최대 처리량 X RPS"가 아니라 병목 두 개와 그 순서다.**

| 순위 | 병목 | 근거 | 개선 |
|---|---|---|---|
| 1 | **조회 응답 압축 부재** | 서버 82ms ↔ 클라이언트 35s, 221KB→9.7KB 가능 | **[#505](https://github.com/TicketRush/TicketRush-backend/issues/505)** — `server.compression` 또는 nginx gzip (§3.4) |
| 2 | **outbox 릴레이 발행 상한** | HTTP 는 놀고(tomcat 1) backlog 868 | batch-size·주기 재조정, 릴레이 병렬화 (후속 이슈 미생성) |
| 3 (후보) | 호스트 CPU / 디스크 I/O | CPU 순간 100%, iowait 11.29% | 2 vCPU 단일 EC2 구성 자체 |

> **1번을 풀기 전에는 2번 이하를 제대로 측정할 수 없다.** 조회 축이 회선에서 막혀 앱을 끝까지 밀어붙일 수 없기 때문이다. #505 적용 후 재측정이 다음 단계다.

Kafka consumer concurrency 1 은 이 회차에서 **병목이 아니었다**(lag 최대 52). 릴레이가 앞에서 조여 컨슈머까지 부하가 도달하지 않았기 때문이며, §2 에서 예고한 대로 "릴레이가 컨슈머보다 앞에서 조인다"가 실측으로 확인됐다. **1번을 풀면 다음은 2번, 그 다음이 concurrency 일 것이다.**

## 5. 오픈런 스파이크 회차

```
browse    2 → 12 → 2 iter/s   (baseline 6m / 램프 10s / 피크 5m / 램프 10s / 회복 6m)
purchase  5 → 30 → 5 iter/s   (ratio 2.5)
측정 창    2026-07-27T15:15:59Z ~ 15:33:28Z, 피크 15:22:19Z ~ 15:27:19Z
```

### 5.1 스파이크를 흡수했다

유입이 피크에서 **6배**로 뛰었는데 지연이 거의 변하지 않았다.

| | 계단식 (최대 browse 10/s) | 스파이크 (피크 browse 12/s) |
|---|---|---|
| 좌석맵 p95 | 92.57ms | **105.83ms** |
| 예매 p95 | 46.06ms | **44.60ms** |
| 여정 p95 | 150ms | **153ms** |
| `http_req_failed` | 0.00% | **0.00%** (0 / 28,497) |
| checks | 100% | **100%** (18,129 / 18,129) |
| 사용된 VU | 6 | **101** (350 할당) |
| 예매 성공 | 18,449 | **12,949 (100%)** |

좌석 충돌·고갈 0건. **10초 램프로 6배를 밀어 넣어도 앱은 도착률을 전부 채웠다**(`dropped_iterations` 항목 자체가 요약에 없다).

### 5.2 ⚠️ 부하가 끝난 뒤에 backlog 정점이 온다 — 5-6분 지연된 2차 파동

`outbox-sampler.sh` 로 5초 간격 164샘플을 떴다(Prometheus 15초 스크랩보다 3배 정밀).

| | booking-service | seat-service |
|---|---|---|
| 피크 구간(5분) 최대 | 358 (평균 174.1) | 182 (평균 24.1) |
| **피크 종료 후 정점** | **1,219** | **976** |
| 정점 시각 | **피크 종료 +86초** (15:28:45Z) | +86초 |

**피크 중 최대가 358 인데, 피크가 끝나고 86초 뒤에 1,219 로 3.4배가 됐다.**

메커니즘은 명확하다. 피크 5분(15:22:19-15:27:19)에 만든 약 9,000건이 `BookingExpireUseCase.PAYMENT_WAIT_MINUTES=5` 뒤 만료되기 시작하는데, **그 시점이 정확히 피크 종료 시점**이다. `BookingExpirationScheduler` 가 60초 주기로 배치 처리하면서 예매 1건당 `BookingExpiredEvent` + `SeatHoldExpiredEvent` 2건을 추가로 밀어 넣는다.

```
피크 유입 (5분, ~9,000건)
   └─ 5-6분 지연 ─→ 만료 파동 (이벤트 ~18,000건) ─→ backlog 정점
```

### 5.3 회복시간

| 기준 | booking | seat |
|---|---|---|
| 정점 → backlog 30 이하 | +254초 | +249초 |
| 정점 → backlog 0 | **+307초** | +312초 |
| **피크 종료 → backlog 0** | **393초 (6분 33초)** | — |

**이것이 완료 조건의 "스파이크 유입 흡수 후 backlog 회복시간"에 대한 답이다.** 단 대상 파이프라인이 다르다 — 결제를 탈 수 없어(§2.2) *예매확정→티켓발급* 대신 **예매생성→좌석HOLD** 파이프라인으로 측정했다.

> ⚠️ **이 파동의 크기는 이 측정의 조건이 증폭한 값이다.** 결제를 하지 않으므로 생성분이 **전량** 만료를 탄다. 실제 운영에서는 결제 완료분이 만료되지 않아 파동이 이보다 작다. 다만 미결제 예매의 만료 자체는 실제로도 일어나므로 **현상은 유효하고 크기만 과장된 것**으로 읽어야 한다.

### 5.4 파동 내내 사용자 경험은 유지됐다

backlog 가 1,219 까지 쌓인 구간에도 **HTTP 응답은 영향받지 않았다** — 좌석맵 p95 105.83ms, 실패 0%, gateway 5xx 0건. 비동기 발행이 밀려도 유입 경로가 버티는 것이 outbox 패턴이 노린 바이고, 그대로 관측됐다.

**반대로 말하면 이 병목은 HTTP 지표만 봐서는 보이지 않는다.** `ticketrush_outbox_backlog` 를 따로 보지 않으면 "스파이크를 문제없이 흡수했다"는 결론에서 멈추게 된다.

## 6. 정합성 — oversell 0

검증은 **outbox 가 완전히 드레인된 뒤**에 했다. 측정 창의 종점은 `outbox PENDING/FAILED = 0` 첫 관측인 **15:05:05Z** 이며, k6 종료(14:59:06Z)보다 6분 늦다 — 마지막 예매가 5-6분 뒤 만료되며 만료 계열 이벤트가 뒤따라 나왔기 때문이다.

| 검증 | 결과 |
|---|---|
| 좌석당 활성(PENDING/CONFIRMED) 예매 2건 이상 | **0행** |
| 앱 생성 예매 총수 ↔ k6 `e2e_booking_created` | **18,449 = 18,449** |
| 유령 HOLD (좌석 HOLD 인데 대응 booking 이 PENDING 이 아님) | **0건** |
| 최종 좌석 상태 | **AVAILABLE 20,800 (전량 회수)** |
| `e2e_seat_conflict` | 0.00% (좌석 유일 배정이 실환경에서 성립) |
| `ticketrush_seat_lock_contention_total` | 시계열 없음 = 증가 0 (락 잔존 없음) |

**만료 파이프라인이 좌석을 유실 없이 되돌렸다.** 18,449건이 전부 EXPIRED 로 전이하고 좌석 20,800개가 전량 AVAILABLE 로 복구됐다. 이 경로(`BookingExpireUseCase` → `BookingExpiredEvent`/`SeatHoldExpiredEvent` → seat 해제)는 이번 회차에서 **의도치 않게 대규모로 검증된 셈**이다 — 결제를 하지 않아 생성분 전량이 만료를 탔기 때문이다.

> 드레인 **중** 관측에서는 유령 HOLD 가 13건 나왔다. 그 시점에는 booking 이 EXPIRED 로 바뀌었지만 `SeatHoldExpiredEvent` 가 아직 처리되지 않은 정상 중간 상태였고, 드레인 완료 후 0 이 됐다. **비동기 파이프라인의 정합성은 반드시 드레인 완료 후에 판정해야 한다**는 것이 이 관측의 교훈이다.

좌석을 유일 배정했으므로 이 회차는 **경합 하의 oversell 을 시험한 것이 아니다.** 경합 방어선 검증은 #344 가 SSOT 다(`unavailable` 비율 + `Seat.version` 낙관적 락).

## 7. 검표 스모크 — #500 이관 항목 통과

#496 이 `slowCallDurationThreshold` 를 300ms → 500ms 로 완화한 변경은 배포본 `d5571697` 로 처음 나갔는데, **그 오탐은 배포 후 첫 검표 트래픽에서만 드러난다.** 이 회차의 스모크가 그 자리였다.

**스모크 직전 `resilience4j_*` 시계열이 아예 없었다** — 검표 경로가 콜드였다는 뜻이고, #500 이 전제한 판정 조건이 그대로 성립한 상태였다.

```
baseline 5/s × 1m → 피크 10/s × 30s → 회복 5/s × 1m   (3m10s, 티켓 2,000건 시딩)
측정 창 2026-07-27T15:41:41Z ~ 15:44:59Z
```

| 판정 지표 | 값 |
|---|---|
| **`not_permitted_calls_total`** | **0** (베이스라인 부재 → 증가분 0) |
| `calls_seconds_count{kind="successful"}` | **2,400** (verify + check-in) |
| `calls_seconds_count{kind="failed"}` | **0** |
| 서킷 state | **closed = 1** (open·half_open 0) |
| `slow_call_rate` / `failure_rate` | **0 / 0** |

k6 축도 같은 방향이다.

| | 값 |
|---|---|
| check-in 성공 | **100.00%** (1,200 / 1,200) |
| `http_req_failed` | **0.00%** (0 / 3,601) |
| **`entry_booking_unavailable`** | **0.00%** (0 / 2,400) |
| QR / verify / check-in p95 | 25.83 / 33.11 / 43.29 ms |

`entry_booking_unavailable` 은 #496 §5.3 에서 워밍업 오탐이 났을 때 **1,472건**이던 바로 그 지표다. **재현되지 않았다.**

판정 조건이 `slidingWindowSize=20` · `minimumNumberOfCalls=10` 인데 2,400건이 평가됐으므로 표본도 충분하다. **300ms → 500ms 완화가 워밍업 오탐을 해소했음이 실측으로 확인됐다.**

## 8. 한계

- **단일 EC2 에 앱 8개 + Kafka·MySQL·Redis·관측 스택이 동거한다.** 절대 수치에 포화가 섞인다(§10.5·§12 와 동일한 단서).
- **조회 축의 절대 수치는 클라이언트 회선이 지배한다**(§3). 서버 축과 함께 읽어야 하며, 조회 경로의 "앱 처리량"은 이 회차로 확정할 수 없다.
- **Nginx 가 부하 경로에 있는데 전용 지표가 없다.** 호스트 CPU 로만 간접 관측되므로 게이트웨이 앞단이 상한인지 가릴 수 없다.
- **결제·티켓 발급이 여정에서 빠져 있다**(§2.2). 파이프라인 backlog 회복시간은 #504 로 분리했다.
- **결제를 하지 않으므로 예매가 5-6분 뒤 전부 만료되고, 그 만료가 outbox 부하를 사실상 2배로 만든다.** `BookingExpireUseCase.PAYMENT_WAIT_MINUTES=5`, `BookingExpirationScheduler` 는 60초 주기다. outbox 수치에는 생성 트래픽과 만료 트래픽이 섞여 있어 운영 예측에 그대로 쓸 수 없다.
- **좌석을 유일 배정하므로 경합은 재지 않는다.** 경합 하의 거동은 #344 가 SSOT 다.
