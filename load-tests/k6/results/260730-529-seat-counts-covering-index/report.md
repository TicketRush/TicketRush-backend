## 1. 요약

`#521` 이 예고한 것이 그대로 나왔다 — **좌석 수에 비례하는 스캔 몫은 크게 줄고, 고정항은 건드려지지 않는다.**

## 2. 이슈 서사와 실측의 차이 — 먼저 읽을 것

**(a) `#403` 을 before 로 쓰지 않고 새로 뜬 것이 옳았다.**

이번 배포(`342a8ef5`)에 `#519`·`#520`·`#515` 가 함께 실렸다. 같은 코호트·같은 계단으로 잰 A-pre 가 `#403` 과 이만큼 달랐다.

| | `#403` (`1f2ed5d2`) | A-pre (`342a8ef5`) |
|---|---|---|
| 고정항 | 1.29 ms | 1.400 ms (+8.5%) |
| 좌석당 | 0.996 µs | 1.367 µs (**+37%**) |
| 3,000석 포화점 | 247 rps | 254.84 rps |

**`#403` 을 before 로 썼다면 이 차이가 인덱스 개선분에 섞였다.** 원인 분해는 이 회차의 범위 밖이라 한계로 남긴다(§6).

**(b) "커버링이면 좌석 수 비례가 사라진다" 는 아니다.**

좌석당 비용이 0 이 되지 않고 1.367 → 0.396 µs 로 **줄어들 뿐**이다. index-only scan 이어도 인덱스 엔트리를 좌석 수만큼 읽는다. 사라진 것은 **테이블 접근을 동반한 몫**이다.

**(c) 고정항이 이 최적화의 상한이라는 것이 수치로 확정됐다.**

1.400 → 1.472 ms. 5.2% 차이는 두 회차 사이 호스트 상태 차이로 설명되는 범위이고, **인덱스는 이 항을 건드리지 못한다.** 3,000석에서도 비용의 55.4% 가 여기다 — 다음 최적화 축은 여기여야 한다.

## 3. 인덱스가 실제로 적용됐는가 (완료조건 1·2)

`@Index` 가 있다는 것은 prod 에 그 인덱스가 있다는 뜻이 아니다(`#464` booking 2 개, `#345` seat 1 개가 미적용으로 발견된 전례). 적용 전후 출력을 [`index-ddl-output.txt`](index-ddl-output.txt) 에 그대로 남겼다.

**적용 전**

```
| type | key                     | rows | Extra |
| ref  | idx_seat_performance_id | 3000 | NULL  |
```

**적용 후**

```
| type | key                                            | rows | Extra       |
| ref  | idx_seat_performance_id_status_hold_expired_at | 3000 | Using index |
```

`Extra: Using index` — **index-only scan 이 성립한다.** 완료조건 2 충족.

DDL 은 `ALGORITHM=INPLACE, LOCK=NONE` 으로 수 초 만에 끝났다(seat 행수 67,301).

### 단일 컬럼 인덱스 제거의 실측 근거 (완료조건 3)

**무릎이 240 에서 480 으로 두 계단 밀렸다.**

**포화점 254.84 → 396.75 rps (+55.7%).** 포화 판정 축 셋(CPU 98.45% · tomcat busy 50/50 · hikari pending 40)이 480 계단에서 함께 붙는다 — A-pre 와 같은 형태가 두 계단 뒤로 이동했을 뿐이다.

### 4.3 비용 모델 재적합 (완료조건 5)

80 계단의 A(600) · B(3,000) 두 점으로 `cost = a + b × 좌석수` 를 푼다.

```
A-pre : cost ≈ 1.400ms + 1.367µs × 좌석수      스캔 몫 600석 36.9% / 3,000석 74.5%
A-post: cost ≈ 1.472ms + 0.396µs × 좌석수      스캔 몫 600석 13.9% / 3,000석 44.6%
```

- **좌석당 −71.0%.** 테이블 접근이 사라진 몫이다.
- **고정항 +5.2%.** 예고대로 건드려지지 않는다. 3,000석 A-post 비용 2.66ms 중 **1.47ms(55.4%)가 여기**다.

#### 두 점 적합을 다른 계단으로 교차검증했다

좌석 규모를 늘리는 회차 없이도, **같은 회차의 다른 계단으로 같은 적합을 반복**하면 모델이 흔들리는지 볼 수 있다.

| 적합에 쓴 계단 | A-pre 좌석당 | A-pre 고정항 | A-post 좌석당 | A-post 고정항 |
|---|---|---|---|---|
| 80 (본 적합) | 1.367 µs | 1.400 ms | **0.396 µs** | **1.472 ms** |
| 160 | 2.308 µs | 0.755 ms | **0.408 µs** | **1.685 ms** |
| 240 | 50.029 µs | −27.477 ms | 0.692 µs | 1.515 ms |

**A-post 는 80 · 160 두 계단에서 좌석당 0.396 vs 0.408 µs(3% 차이), 고정항 1.47 vs 1.69ms 로 일치한다.** 두 점 적합이지만 서로 다른 부하 수준에서 같은 계수가 나오므로 모델이 우연이 아니다.

**A-pre 는 160 계단부터 무너진다** — 3,000석이 5.50 → 7.68ms 로 이미 들리기 시작해 적합이 오염되고, 240 에서는 고정항이 음수가 된다(122.61ms 는 포화값이지 비용이 아니다). **A-pre 의 깨끗한 계단이 80 하나뿐이라는 것 자체가 인덱스 없는 상태의 여유가 얼마나 좁았는지를 말한다.**

> 그래도 **좌석 규모는 여전히 두 점**이다. 선형성 자체(1 차식이 맞는지)는 세 번째 규모가 있어야 검증된다 — 후속 과제로 남긴다.

## 5. 회차 유효성

| 회차 | `scale_mismatch` | 실패 | dropped | `vus_max` |
|---|---|---|---|---|
| A-pre 600석 | **0.00%** | 0.00% | 582 | 666 / 800 |
| A-pre 3,000석 | **0.00%** | 2.34% | 92,362 | **800 / 800** |
| A-post 600석 | **0.00%** | 0.00% | 113 | 212 / 800 |
| A-post 3,000석 | **0.00%** | 0.66% | 22,654 | **800 / 800** |

- **`seat_counts_scale_mismatch` 가 전 회차 0** 이다. 엉뚱한 공연을 재거나 시딩이 덜 된 회차가 없다.
- 시딩은 `@mode='refresh'` 로 `#403` 과 같은 분포(SOLD 20% / HOLD 20% / AVAILABLE 60%)를 복원했고, `/seat-counts` 응답이 `expect_*` 와 일치함을 시딩 직후 대조했다.
- 배포 직후 회차는 폐기했다(3 분 워밍업 별도 실행). 회차 사이 `seat-service` 를 매번 재시작했다 — 부하 종료 후 RSS 가 479-570 MiB 로 돌아오지 않는다.

> ⚠️ **3,000석 두 회차는 `vus_max` 800 상한에 닿았다.** 런북 §14.8 은 "dropped 의 원인이 포화가 아니라 `preAllocatedVUs` 부족" 인 회차를 무효로 본다. 이 회차는 포화가 원인이라고 판정했고 근거는 셋이다.
>
> 1. **480 계단 CPU 가 A-pre 99.97% / A-post 98.45%**(구간최댓값 99.98% / 99.96%)다. 호스트가 실제로 다 찼다.
> 2. **tomcat busy 가 50/50** 으로 상한에 붙고 **hikari pending 40**(풀 10)이 같은 시각에 함께 선다. VU 가 모자란 클라이언트는 이런 서버 측 포화 신호를 만들지 못한다.
> 3. **A-post 의 320 계단은 VU 상한에 닿지 않고도 목표의 99.0% 를 소화했다.** 상한이 처리량을 깎았다면 그 아래 계단에서도 미달이 나타나야 한다.
>
> 다만 **480 계단의 절대 처리량은 "VU 상한 아래에서 관측된 값"** 이라는 단서를 붙인다. 실제 포화점은 396.75 rps 이상일 수 있다 — 즉 **이 회차가 보고하는 +55.7% 는 하한이다.** before/after 가 같은 상한을 쓰므로 비교 자체는 성립한다.

## 6. 한계 — 리포트에 그대로 옮길 것

- **A-pre 가 `#403` 과 다른 이유를 설명하지 못한다.** 좌석당 비용이 37% 비싸졌다. 이번 배포에 세 이슈가 함께 실렸고 그중 무엇이(혹은 호스트 상태가) 원인인지 이 회차는 가르지 않는다. **before/after 비교는 같은 이미지 안에서 이뤄졌으므로 이 불확실성이 개선분에 섞이지는 않는다.**
- **좌석 규모가 두 점뿐이라 선형성을 검증하지 못했다.** 비용 모델은 두 점을 잇는 직선일 뿐이다.
- **호스트 CPU 가 먼저 포화한다.** 396.75 rps 는 "집계 쿼리의 한계" 가 아니라 **"단일 EC2(2 vCPU)에 앱 8 개 + 관측 스택이 동거하는 이 구성에서 도달한 지점"** 이다(`#509` 와 같은 결론).
- **쓰기 비용 변화를 재지 않았다.** 인덱스가 하나 줄고(단일 컬럼 제거) 하나 늘었다(3 컬럼 추가). 좌석 전이 쓰기의 순변화는 이 회차의 범위 밖이다.
- **`seat-layouts` 대비 비교 회차(§14.5)를 돌리지 않았다.** `#403` 이 "집계가 좌석맵보다 7% 비싸다" 고 한 대조가 인덱스 후 어떻게 바뀌는지는 다음 회차 몫이다.

## 7. 여기서 나온 후속 과제

1. **고정항 1.47ms 가 다음 축이다.** 3,000석에서도 비용의 55.4% 이고 인덱스로는 못 줄인다. 무엇이 이 1.47ms 를 만드는지(커넥션 획득 · JPQL 파싱 · 직렬화 · 프레임워크 오버헤드) 쪼개는 것이 다음 최적화의 출발점이다.
2. **`#403` 대비 좌석당 비용 +37% 의 원인 규명.** 배포 묶음 안의 어느 변경이(또는 호스트 상태가) 이것을 만들었는지.
3. **좌석 규모 3 점 이상으로 선형성 검증.**
4. **`seat-layouts` 대비 비교 회차 재실행** — `#403` §14.5 의 대조가 인덱스 후에도 성립하는지.

- **pre**: `18:28`(240 계단)부터 CPU 100 · busy 50 · pending 40 이 **동시에** 붙고 회차 끝까지 유지된다.
- **post**: 같은 240 계단(`20:30` 부근)에서는 바닥이고, **`20:38`(480 계단)에 가서야** 셋이 붙는다. 무릎이 두 계단 밀렸다는 §4.2 의 주장이 이 두 장의 차이다.
- 부수 확인: post 의 `20:30`·`20:35` 에 노랑이 잠깐 **16 · 23** 까지 튄다 — [`metadata.txt`](metadata.txt) 의 240 계단 `2.19/16.00`, 320 계단 `3.25/23.00`(구간평균/구간최댓값)과 정확히 맞는다. **표와 그림이 서로를 검산한다.**

**`graph-counts-a-pre.png` / `-post.png`** — 600석. pre 는 480 계단에서 노랑이 들리기 시작하지만, post 는 같은 계단에서도 약 5ms 에 붙어 있다. 두 장 모두 초록이 480 까지 계단대로 올라가 **600석은 before/after 둘 다 미포화**임을 보여준다 — 개선은 포화점이 아니라 **여유(CPU 92.71% → 80.38%)** 로 나타난다.
