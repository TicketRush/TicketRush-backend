# #539 좌석맵 JSON 캐싱 전/후 무릎 재측정

> 회차 ID `260731-539-seatmap-cache` · 2026-07-31 · 대상 EC2 `m7i-flex.large`(2 vCPU / 7.6 GiB)
> 수치의 SSOT 는 같은 디렉토리의 [`metadata.txt`](metadata.txt) 다. 이 문서와 어긋나면 그 파일이 옳다.

## 0. 한 줄 요약

**좌석맵 JSON 캐싱으로 읽기 경로의 무릎이 60 → 100 이상 iters/s 로 밀렸고(최소 1.67배), before 가 무너지던 80 계단을 after 는 손실 없이 통과했다** — 그 지점의 서버 평균이 741 → 10.1 ms 로 **73배** 빨라졌다. 회차 전체 실패율이 4.92% → **0.00%** 다.

부수로 셋을 얻었다. **캐시는 조회가 몰릴수록 잘 듣는다**(히트율 20 계단 92% → 80 계단 99.9% — 미스 원인인 TTL 만료·evict 가 도착률에 비례하지 않기 때문이다). **Redis 예산은 여유가 14배**이고 `failure` 가 전 구간 0 이라 좌석 락을 위협하는 경로는 열리지 않았다. **`#535` 의 사이드카 가설은 기각됐다**(§8).

**무릎의 정확한 위치는 이 회차가 답하지 못했다** — 100 계단에서도 소화율이 100% 라 상한을 못 봤다.

---

## 1. 이 회차가 답해야 하는 것

`#469`(좌석 배치 조회 Redis JSON 캐싱)의 완료 조건 중 실측 항목 둘이다.

- 캐시 전/후 **무릎(RPS·p95)** 비교
- Redis 128 MiB 상한 내 동작 확인

여기에 `#535`(집계 좌석당 비용 +37% 규명)를 같은 EC2 세션에 편승시켰다. 축이 달라(seat-counts) 같은 k6 실행이 아니고, `#512` 트리아지 규칙 3("측정 방법론 검증 → 10분 미만이면 다음 예정 회차에 편승")에 따른 것이다.

## 2. before 를 배포 *전* 에 뜬 이유 — 이 회차의 설계가 묶음 B 와 다른 지점

묶음 B(`#529`)는 수동 DDL 을 before 회차 **뒤**에 넣어 before/after 를 같은 이미지에서 잡았다. 인덱스는 런타임에 넣고 뺄 수 있기 때문이다.

**캐싱에는 그 장치가 없다.** `SeatMapCacheRepository` 는 `@Repository` 로 무조건 등록되고 `SeatFacade` 에 생성자 주입으로 고정 배선돼 있으며, TTL·키 프리픽스도 `private static final` 상수다. 설정 플래그도 환경변수도 쿼리 파라미터도 없다 — **배포되는 순간 켜진다.**

그래서 순서를 뒤집었다.

```
[before: 342a8ef5, 05:49-06:25Z] -> 묶음 C 배포(PR #538) -> 워밍업(폐기) -> [after: e0b42dc6]
```

`342a8ef5` 는 `#529` 를 돌린 바로 그 이미지다. 덕분에 `#535` 편승도 같은 이미지에서 성립했다.

### 대안을 검토했고 기각했다

| 안 | 기각 사유 |
|---|---|
| 배포 후 `seat:seat-map:*` 를 반복 DEL 해 미스를 강제 | 같은 이미지를 쓸 수 있지만, before 경로에 캐시 `get`/`set` 왕복과 DEL 루프 부하가 얹혀 개선분이 과대평가된다 |
| 과거 회차(`#505` 등)를 before 로 재사용 | `#512` 가 명시적으로 금지한다. `#529` 에서 같은 조건인데 좌석당 37% 가 어긋난 전례가 있다 |

### 이 선택이 남기는 한계 — 리포트에 그대로 적는다

**before 와 after 의 이미지가 다르다.** 그 차이에 `#532`(SSE executor 거부 정책)와 문서 변경이 섞인다. `#532` 는 SSE 전송 경로라 좌석맵 읽기 rps 에 직접 닿지 않지만, **"섞이지 않았다"가 아니라 "섞였고 축이 다르다"** 로 읽어야 한다.

## 4. 계단을 두 번에 걸쳐 확정한 과정 — 스모크를 믿으면 안 됐다

### 4.1 스모크가 거짓 상한을 줬다

부팅 직후 스모크(10,30,60 × 1m)가 60 계단에서 **CPU 95.67% · `dropped` 195 · seat-layouts p95 4.84s** 를 냈다. `#505` 가 정한 상한 60 과 일치해 본 회차 계단을 `20,40,60` 으로 확정했다.

**그런데 워밍업과 seat-service 재시작 뒤 같은 60 계단이 CPU 90.5% · `dropped` 0 · p95 0.54s 로 돌았다.** 스모크 수치는 콜드 JIT 와 부팅 직후 페이지 캐시 미형성이 만든 값이었다.

> **다음 회차에 적용할 것**: 부팅 직후 스모크로 정한 상한을 본 회차 상한으로 믿지 않는다. 스모크는 "시나리오가 도는가"만 보고, 상한은 워밍업 뒤에 다시 잡는다.

### 4.2 1차 회차가 미포화로 끝나 계단을 연장했다

`20,40,60 × 5m` 이 **실패 0.00%(0/117,771) · `dropped` 0 · 도착률 100% 소화**로 완주했다. 무릎에 도달하지 못한 것이다. `60,80,100 × 5m` 을 이어 돌렸다.

**60 계단을 겹치게 둔 것은 두 회차가 같은 곡선 위에 있는지 검산하기 위해서다**(`#529` 가 다른 계단으로 두 점 적합을 교차검증한 것과 같은 논법). 판정 기준은 **회차 전에** 정해 `metadata.txt` 에 적었다 — 겹치는 계단의 마지막 3분 중앙값 기준 CPU 차 ≤ 5%p.

### 4.3 그 기준은 초과했다 — 그리고 초과분의 정체가 규명됐다

2차 회차의 60 계단 CPU 가 99.6% 로 시작해 90.0% 로 내려왔고, 마지막 3분 창에 콜드 구간이 통째로 들어갔다.

```
06:09:50  99.59%   <- 재시작 직후, 콜드
06:10:52  99.76%
06:11:54  98.98%
06:12:56  92.38%
06:13:43  90.03%   <- 계단 종료 직전
```

같은 처리량(app_rps 384 vs 377)에 CPU 만 더 드는 형태였고 단조 감소해 1차 값으로 수렴했다. **1차 60 계단 중앙값 90.51% 와의 차이가 0.48%p 다.**

**판정: 기준 초과를 기록하되 두 회차를 이어 읽는다.** 근거는 "기준을 다시 정해서"가 아니라 **"초과분이 워밍업이라는 것이 수렴 곡선으로 증명돼서"** 다. 2차 회차의 60 계단 앞 3분은 어떤 표에도 넣지 않았다.

소화율 = seat-layouts 서버 RPS / 도착률(1 iteration = seat-layouts 1 요청). 계단당 5분, 각 계단의 안정 구간 중앙값이다.

| 20/s | 40.8% | 64 | 20.0 (100%) | 9.6 ms | 0.05 s | 0 | 0 |
| 40/s | 73.0% | 128 | 40.0 (100%) | 28.4 ms | 0.22 s | 0 | 0 |

## 7. 캐시 동작 확인

### 7.1 히트율은 도착률이 오를수록 올라간다

> **그림이 표에 없는 것을 하나 보여준다**(`graph-after-cache-hitrate.png`) — **miss 는 계단 전환 직후에 튄다.** 40 계단 진입 시 10/s 까지 올랐다가 계단 안에서 잦아든다. 아래 표의 중앙값(3.51/s)은 그 봉우리를 평균해 지운 값이다. 도착률이 오르면 evict 대상과 TTL 만료가 한꺼번에 몰리기 때문으로 읽는다.

| 계단 | hit/s | miss/s | failure | 히트율 |
|---|---|---|---|---|
| 20/s | 18.41 | 1.59 | **0** | 92.06% |
| 40/s | 36.48 | 3.51 | **0** | 91.22% |
| 60/s | 59.73 | 0.26 | **0** | 99.57% |
| 80/s | 79.93 | 0.08 | **0** | 99.90% |
| 100/s | 99.92 | 0.20 | **0** | 99.80% |

히트율의 분모에 `failure` 를 넣지 않는다 — 캐시 리포지토리가 장애를 `miss` 와 분리해 세는 이유가 그것이다.

**미스는 두 경로에서만 난다** — TTL 30초 만료와 좌석 상태 변경 시 evict. 둘 다 **횟수가 도착률에 비례하지 않으므로**, 조회가 늘수록 미스가 전체에서 차지하는 비중이 준다. 20-40 계단의 91-92% 와 60 계단 이상의 99.6-99.9% 는 그 차이다.

**실전 함의**: 오픈 직후처럼 조회가 몰릴수록 캐시가 더 잘 듣는다. 캐시가 가장 필요한 구간에서 히트율이 가장 높다.

### 7.2 Redis 예산 — `#469` 완료조건

| | 값 |
|---|---|
| 최대 사용률 | **6.76%** (100 계단) = 약 4.3 MB / `maxmemory 64mb` |
| 컨테이너 상한 | 128 MiB (`mem_limit`) |
| `failure` 카운터 | **전 구간 0** |

**예산 안이고 여유가 14배다.** `noeviction` 이라 상한에 닿으면 캐시 SET 이 아니라 **좌석 락 SET 이 거절되는데**(캐시는 fail-open, 락은 fail-closed 503 — [ADR 0008](../../../docs/adr/0008-accept-redis-spof-with-fail-closed.md)), `failure` 가 0 이므로 그 경로는 한 번도 열리지 않았다. `used` 만 보면 이 위험이 안 보이므로 두 축을 겹쳐 읽은 결과다.

활성 공연 1건(2,080석, 값 약 221 KB) 기준이므로, 공연 수가 늘면 선형으로 증가한다. 64 MB 상한이면 산술적으로 약 290 공연분이나, TTL 30초라 동시에 상주하는 것은 **그 순간 조회되는 공연**뿐이다.

## 8. `#535` 편승 — 사이드카 가설은 기각됐다

### 8.1 코호트를 먼저 복원해야 했다

EC2 를 껐다 켠 사이 미만료 HOLD(`+6h`)가 만료돼 **부팅 직후 스케줄러가 720건을 전부 AVAILABLE 로 해제했다**(A 120 → 0, B 600 → 0). 그대로 재면 `#529` 와 상태 분포가 달라 곡선을 겹칠 수 없다.

`seed_seat_counts.sql @mode='refresh'` 로 복원했다 — 좌석번호로 시딩 당시 배분을 재현해 **원래 HOLD 였던 그 좌석만** 되돌리고 `performance_id` 를 보존한다(재시딩하면 id 가 바뀌어 `#529` 와의 연결이 끊긴다). 복원 후 `/seat-counts` 응답이 시드의 `expect_*` 와 정확히 일치함을 확인했다.

### 8.2 좌석당 비용은 샘플러와 무관했다

`docker stop ticketrush-container-mem-sampler` 상태에서 `seat-counts` 80 계단을 A(600석)·B(3,000석) 각 5분 돌았다. 전 회차 도착률 100% 소화 · 실패 0.00%.

**k6 클라이언트 avg 로는 좌석 수 차이가 안 보인다**(A 13.72ms vs B 13.97ms) — 로컬↔EC2 왕복 지연이 지배항이라서다. `#529` 와 같은 **서버 축**으로 뽑아야 한다.

| | 서버 avg | CPU |
|---|---|---|
| A 1차 (600석) | 2.236 ms | 37.9% |
| B (3,000석) | 3.039 ms | 27.3% |
| **A 재측정 (600석)** | **2.058 ms** | **23.4%** |

A 1차와 B 의 CPU 가 10%p 어긋나 A 가 콜드였음이 드러나, **B 와 같은 열 상태에서 A 를 다시 떠 짝을 맞췄다.**

| | `#529` A-post (샘플러 켜짐) | 이번 회차 (샘플러 꺼짐) | 차이 |
|---|---|---|---|
| 좌석당 비용 | 0.396 µs/석 | **0.409 µs/석** | **+3.3%** |
| 고정항 | 1.472 ms | 1.812 ms | +23.1% |

**판정: `#515` 사이드카 가설 기각.** 샘플러를 끈 상태의 좌석당 비용이 켜져 있던 `#529` 와 3.3% 안에서 일치한다. 15초마다 cgroup 을 훑는 프로세스가 2 vCPU 를 갉아 집계 비용을 올렸다는 가설은 성립하지 않는다.

고정항 +23.1% 는 남지만, **같은 세션 안에서도 A 가 콜드/웜에 따라 2.236 → 2.058 ms(8%) 흔들렸다.** 이 크기는 재현성 오차 범위로 읽는다.

**원인 후보 중 사이드카만 배제됐다.** 코드(`#519`·`#520`)와 호스트 상태는 이 회차로 가르지 못한다 — `#535` 완료조건 3의 답은 **"사이드카 아님 + 나머지 미확인"** 이고, 이슈가 스스로 허용한 대로 재현성 한계로 문서화하고 닫는다.

### 8.3 이 회차가 만든 방법론 교훈

**좌석당 비용의 두 점(A·B)은 같은 열 상태에서 떠야 한다.** A 를 워밍업 직후에 뜨면 콜드 성분이 A 를 부풀려 기울기가 과소평가된다 — 1차 적합 0.335 µs 가 열을 맞춘 재적합에서 0.409 µs 로 **22% 달라졌다.**

## 9. 한계

1. **after 의 무릎을 못 찾았다**(§6). 100 계단에서도 소화율이 100% 라 "60 → 100 이상"까지만 수치로 말할 수 있다. 개선 배수의 하한이 1.67배이지 그 값이 아니다. 확정하려면 120·140 계단 회차가 필요한데, **좌석 예산이 막는다** — 20-100 계단이 이미 18,500석을 쓰고 확보분이 20,800석이다. 계단을 더 올리려면 `seed_load.sql` 의 `@perf_count` 를 키워 코호트를 다시 만들어야 한다.
2. **before 와 after 의 이미지가 다르다**(§2). `#532` 가 섞였고, 축이 다르다는 것이 그 영향을 작게 만들 뿐 없애지는 않는다.
3. **`#535` 가 미확인으로 끝났다**(§8.2). 회차 간 재현성이 좌석당 수 % 수준에서 흔들린다는 것이 이번에도 확인됐고, 그 오차는 이 회차의 before/after 비교에도 적용된다.
4. **before 100 계단의 VU 상한 접촉**(§5 각주).
5. 단일 EC2 에 앱 9개 + Kafka·MySQL·Redis·관측 스택이 동거하므로 절대 수치에는 이웃 서비스의 포화가 섞인다(ADR 0004).
