## 1. 요약

`#529` 가 커버링 인덱스로 좌석당 스캔 비용을 71% 줄이면서 남긴 **고정항 1.47ms** 가 무엇으로 이루어졌는지 분해했다.

| 구간 | ms | 몫 |
|---|---|---|
| **프레임워크 CPU** (Tomcat·MVC·Security·AOP) | **0.819** | **48.6%** |
| DB 계열 CPU (Hibernate·드라이버·소켓·풀) | 0.406 | 24.1% |
| 미분류 (JFR depth 한계) | 0.289 | 17.1% |
| DB 응답 대기 (wall − CPU) | 0.162 | 9.6% |
| 앱 코드 | 0.012 | 0.7% |
| 커넥션 획득 | 0.000 | 0.0% |
| **합** | **1.688** | 고정항 1.687 에 수렴 |

**한 줄로**: 고정항의 절반이 서블릿·MVC 스택이고, 이슈가 후보 1번으로 꼽았던 커넥션 획득은 **0%** 이며 결과 매핑·직렬화도 **0.03%** 다. 코드로 줄일 수 있는 몫은 없다 — **이 값은 이 구성에서 집계 요청의 하한이다.**

## 2. 이슈 서사와 실측의 차이 — 먼저 읽을 것

### 2-1. 후보 5개 중 2개가 0 으로 나왔다

이슈는 다섯 후보를 세웠다. 실측 결과 둘이 탈락한다.

| 후보 | 실측 | 판정 |
|---|---|---|
| HikariCP 커넥션 획득 | 고정항 **−0.008 ms** (A 0.003 / B 0.047) | **탈락** |
| 결과 매핑(constructor expression → record) | Jackson CPU 샘플 3,444 중 **1 개** | **탈락** |
| DB 왕복 | CPU 24.1% + 대기 9.6% | 3위 |
| JPQL → SQL 변환·`PreparedStatement` 준비 | Hibernate 12.1% 안에 포함 | — |
| Spring MVC 필터·인터셉터·직렬화 | **48.6%** | **1위** |

직렬화가 0 인 것은 당연한 결과다 — 응답이 `record SeatStatusCountsResponse(Long, Long, Long, Long)` 로 **숫자 4 개**뿐이다. 좌석 3,000개를 세도 나가는 것은 4 개 숫자다.

### 2-2. 배포 없이 쟀다

처음 계획은 `Timer` 를 심어 CD 를 한 번 도는 것이었다. 실제로는 필요 없었다.

- **커넥션 몫**은 `hikaricp_connections_acquire_seconds` / `_usage_seconds` 가 이미 노출 중이었다(Boot 바인더). 코드 변경 0.
- **계층 분해**는 JFR 을 `JAVA_TOOL_OPTIONS` override 로 얹고 컨테이너만 재시작해 얻었다. `deploy/docker-compose.prod.yml` 이 JVM 옵션을 `.env` 가 아니라 `environment:` 블록에 두는 덕이다(#509 의 결정). 같은 이미지, CD 미실행, 재시작 1 분.

저장소 변경은 `dump-timeseries.py` 쿼리 2 줄과 분석 스크립트 1 개뿐이다.

### 2-3. 좌석이 5 배여도 앱 CPU 는 그대로다

이것이 고정항/좌석당 모델이 성립하는 이유를 설명한다.

| 계층 | A 600석 | B 3,000석 |
|---|---|---|
| 프레임워크 합 | 53.66% | 54.08% |
| DB 계열 합 | 26.60% | 28.66% |
| 미분류 | 18.96% | 18.34% |

좌석이 5 배인데 **CPU 분포가 거의 같다.** 늘어나는 것은 DB **안에서의** 스캔 시간이고 그동안 앱은 대기한다. 좌석당 0.418 µs 가 순수 DB 몫인 근거다.

`jdk.SocketRead` 가 이를 직접 보여준다 — 1ms 를 넘는 MySQL 왕복이 600석에서는 요청의 **2.55%** 에서만 발생하는데, 3,000석에서는 **100.78%** 다(요청당 1.485 ms).

### 3-3. 합산 — §1 의 표

프레임워크가 순수 CPU(대기 없음)라고 두고 총 CPU 를 역산한다.

```
총 CPU = 프레임워크 wall 0.819 / 프레임워크 CPU 비율 0.5366 = 1.526 ms
각 계층  = 총 CPU × 해당 비율
대기     = 고정항 wall 1.687 − 총 CPU 1.526 = 0.162 ms
```

**⚠️ 이 가정 위의 환산값이다.** 구간별 `Timer` 로 직접 잰 값이 아니다. 합이 1.688 로 고정항에 수렴하는 것이 자체 검증이다.

## 4. 완료 조건 2 — 가장 큰 몫과 그 축소 가능성

**1위는 프레임워크 0.819 ms(48.6%)** 이고, 내역은 서블릿 컨테이너 · MVC 디스패치 · 필터 체인이다.

손댈 수 있는 항목은 **Spring Security 6.57%(약 0.11 ms)** 하나뿐이다. 그런데:

`seat-service/src/main/java/com/ticketrush/global/config/SecurityConfig.java` 를 보면 `seat-counts` 는 이미 `anyRequest().permitAll()` 이다. **`permitAll` 도 "허용" 을 판정하려면 필터 체인을 통과해야 하므로 비용이 든다.** `InternalApiTokenFilter` 도 `/api/v1/internal/seat` 접두사만 처리하지만 모든 요청에서 호출된다.

이 비용을 없애려면 `web.ignoring()` 으로 시큐리티 체인 자체를 우회해야 하는데, 그러면 CORS·CSRF 설정도 함께 빠진다. **고정항의 6.5% 를 위해 보안 경계를 바꾸는 것은 수지가 맞지 않는다.**

나머지(Tomcat 18% + Spring 17% + MVC 9.6%)는 이 스택을 쓰는 한 지나야 하는 경로다. 앱 코드는 0.7% 인데 그마저 `SeatGetStatusCountsUseCase` 의 위임 한 줄이다.

**결론: 줄일 수 있는 것이 없다.**

## 5. 완료 조건 3 — 고정항이 좌석 수와 무관한가

모델의 전제였고, 두 가지로 확인된다.

1. **2점 적합이 성립한다** — 80·160 두 계단에서 좌석당이 0.418 / 0.437 µs 로 4% 안에서 일치한다.
2. **CPU 분포가 좌석 수에 무관하다**(§2-3). 고정항이 앱 처리 비용이고 좌석 수는 DB 스캔에만 영향한다는 것을 계층 수준에서 보여준다.

`#529` 대조:

| | #529 A-post | 이번 (80) | 이번 (160) |
|---|---|---|---|
| 좌석당 | 0.396 µs | 0.418 µs | 0.437 µs |
| 고정항 | 1.472 ms | 1.687 ms | 1.497 ms |

**좌석당이 5~10% 안에서 재현된다** — 배포본이 달라도 커버링 인덱스 효과는 그대로다. 고정항은 계단에 따라 1.47~1.69 사이에서 흔들리는데, `#529` 도 같았다(80:1.472 / 160:1.685). 방향만 반대다. 2점 적합의 한계다.

## 6. 완료 조건 4 — 계측이 값을 얼마나 바꿨는가

**분리하지 못했다.** 같은 이미지의 무계측 회차가 없어서, 고정항이 `#529` 의 1.472 → 1.687(80계단)로 오른 것 중 얼마가 JFR 몫인지 가를 수 없다. 160 계단은 1.497 로 오히려 `#529` 와 1.7% 안에서 일치한다.

말할 수 있는 것은 `settings=profile` 의 공표 오버헤드가 약 2% 라는 것뿐이다. **한계로 남긴다.**

## 8. 한계 — 리포트에 그대로 옮길 것

1. **JFR 스택 depth 가 5 로 잘렸다.** `stackdepth` 를 안 늘린 대가로 미분류 17.1% 가 남았다. 다음에는 `-XX:FlightRecorderOptions=stackdepth=256` 을 함께 준다. 이 때문에 "이 샘플이 seat-counts 요청인가" 를 스택으로 판별할 수 없어 워커 스레드 필터로 대체했다.
2. **`SocketRead` threshold 1ms 가 고정항 구간을 잘랐다.** 600석 왕복의 97.5% 가 미포착이라 고정항의 DB 왕복 몫은 이 이벤트로 못 잰다.
3. **JFR 오버헤드를 분리하지 못했다**(§6).
4. **좌석 규모는 여전히 두 점이다.** 선형성 자체는 세 번째 규모가 있어야 검증된다(`#529` 와 동일한 한계).
5. **분해 표의 계층별 절대값은 환산값이다**(§3-3의 가정).
6. **배포본이 `#529` 와 다르다**(`342a8ef5` vs `21d2da2d`). 분해 대상 경로 코드는 무변경임을 확인했으나(`SeatGetStatusCountsUseCase`·`SeatRepository`·`Seat`·`SeatFacade` 해당 메서드 diff 0), 같은 JVM 에 `#469` 캐싱과 `#532` SSE 역압이 들어와 GC·메모리 프로파일이 다르다.

## 9. 여기서 나온 후속 과제

**다음 축은 캐싱이다.** 고정항은 요청이 앱에 도달하는 순간 확정되는 비용이므로, 줄이는 것이 아니라 **요청을 앱까지 오지 않게 하는** 방향뿐이다.

- 선례가 있다 — `#469` 가 좌석맵에서 DTO 가 아닌 JSON 문자열을 캐싱해 무릎을 60 → 100+ 로 올렸다.
- 무효화 수단도 이미 있다 — `SeatStatusEventPublisher#publishAfterCommit`.
- 응답이 숫자 4 개라 캐시 크기가 극소다.
- 다만 **정합성 검토가 선행**되어야 한다. 집계는 좌석 상태가 바뀔 때마다 변하므로 TTL 과 무효화 설계가 `#469` 보다 까다롭다.

이 회차의 범위 밖이므로(`#534` 는 규명이지 최적화가 아니다) **백로그로만 남긴다.** 착수는 별도 지시가 있을 때.
