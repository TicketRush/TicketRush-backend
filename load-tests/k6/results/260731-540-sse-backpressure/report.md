# #540 SSE 큐 역압 재현 — 거부 0건 확인

> 회차 ID `260731-540-sse-backpressure` · 2026-07-31 · 배포본 `e0b42dc6`(PR #538)
> 수치의 SSOT 는 같은 디렉토리의 [`metadata.txt`](metadata.txt) 다.

## 0. 한 줄 요약

**`#528` 이 649건을 유실했던 조건에서 거부가 0건이 됐다.** 큐는 986/1000 까지 여전히 차지만, 넘친 몫을 버리는 대신 **호출 스레드(스케줄러 tick)가 37회 떠안았다.** 대가는 그 tick 의 소요가 약 0초 → 약 60초로 늘어난 것이고, ShedLock `lockAtMostFor = 2m` 안이지만 **여유가 절반뿐이다.**

정상 상태(구독자 600 · 이벤트율 5/s)의 큐 깊이는 여전히 0 이다 — 고치려다 상시 경로를 느리게 만들지 않았다.

---

## 1. before 를 새로 뜨지 않은 이유

`#532` 의 완료조건이 **절대 기준(거부 0건)** 이라 개선분 귀속이 필요 없다. `#512` 트리아지가 이 근거로 `#469` 와 같은 배포에 실으면서도 검증 회차는 따로 돌게 판정했다.

**`#528` 이 곧 before 다.** 같은 구독자 수(600), 같은 주입량(만료 HOLD 2,000건), 같은 시나리오다.

## 2. 재현 조건

| | 값 |
|---|---|
| 구독자 | 600 (VU 1개 = SSE 커넥션 1개) |
| 이벤트율 | `SSE_MUTATE_RATE=5`/s |
| 주입 | 만료 HOLD 2,000건 (`@mode='expire'`) |
| 코호트 | `LTC-SSE` `performance_id=21`, 12,000석 |

**코호트는 재시딩했다.** `LTC-SSE` 는 예매가 좌석을 비가역 소모하므로 상태 분포가 아니라 좌석 점유 자체가 깎여 `@mode='refresh'` 로 되돌릴 수 없다(런북 §14.3). `performance_id` 가 바뀌므로 검증 쿼리 출력에서 새 id 를 읽어 넘겼다.

**seat-service 를 재시작하고 시작했다.** `#539` after 회차 직후 RSS 가 527.4/640 MiB(82%)였고, SSE 600 구독자는 메모리를 크게 쓴다(`#403`·`#509` 선례).

**포화는 그대로 났고 유실만 사라졌다.** 이것이 (C) 역압 채택이 의도한 동작이다 — 큐 용량을 늘리거나(B) 스케줄러를 조이는(A) 대신, 넘친 몫을 호출 스레드가 떠안는다.

`pool` 이 4 → 16 으로 늘어난 것은 **큐가 다 찬 뒤**다. `ThreadPoolTaskExecutor` 의 정상 순서이고, 이 순서가 뒤집혔다면 오독이었을 것이다.

큐는 약 2분 20초 만에 0 으로 해소됐다.

### 4.1 로그가 카운터를 검산한다

```
2026-07-31T07:57:05.217Z  WARN [seat-service] [scheduling-1] SeatStatusSseConfig :
  좌석 상태 SSE 전송 큐가 가득 차 호출 스레드가 팬아웃을 대신 실행합니다(이벤트는 유실되지 않습니다).

```

- **로그 37건 = 카운터 37** (교차검증 일치)
- **스레드가 `scheduling-1`** — 스케줄러 tick 스레드가 직접 팬아웃을 떠안았다는 직접 증거다
- `queue=1000/1000 poolSize=16/16` — 완전 포화 상태에서 찍혔다
- **스택 트레이스 0건** — `#403` 에서 초당 728건의 로그가 디스크를 뒤덮은 교훈대로 남기지 않는다
- `"전송 작업이 거부"` 문구 **0건** — 거부 경로는 한 번도 타지 않았다

## 5. 역압의 대가 — tick 하나가 건너뛰어졌다

`PR #536` 이 리뷰 요청으로 남긴 항목이다. 스케줄러 tick 로그를 보면:

```
07:54:48  tick
07:55:48  tick
07:56:48  tick   <- 주입분 2,000건을 이 tick 이 처리
   (07:57:48 없음)
07:58:48  tick
07:59:48  tick
```

`@Scheduled(fixedDelay = 60000)` 은 **[실행 종료 + 60초]** 가 다음 tick 이다. `07:56:48 → 07:58:48` 이 120초이므로 **그 tick 의 소요가 약 60초**였다는 뜻이다(평소에는 사실상 0초에 끝난다).

| | 값 |
|---|---|
| tick 소요 | 약 60초 (평소 약 0초) |
| ShedLock `lockAtMostFor` | 2분 |
| 판정 | **초과하지 않았다** |

**초과하지는 않았지만 여유가 절반뿐이다.** 주입량이 2배(4,000건)였다면 락 유효시간을 넘겨 다른 인스턴스가 같은 tick 을 중복 실행할 수 있었다. 지금 배포는 단일 인스턴스라 즉시 문제가 되지는 않으나, **수평 확장 시 이 값이 제약이 된다.**

ShedLock 관련 경고 로그는 0건이다.

## 8. 한계

1. **주입량 2,000건 한 번만 봤다.** tick 소요가 약 60초였으므로 4,000건이면 ShedLock 2분을 넘길 수 있다는 것은 **외삽이지 실측이 아니다.**
2. **단일 인스턴스 환경이다.** ShedLock 초과의 실제 위험(중복 tick)은 수평 확장 시에 드러나며, 이 회차는 그것을 재현할 수 없다.
3. 이 회차는 `#539` 와 같은 배포본에서 돌았으므로, seat-service 의 자원 상태에 좌석맵 캐싱(`#469`)의 영향이 섞여 있다. 다만 축이 달라(읽기 vs SSE 전송) 큐·거부 수치에 직접 닿지는 않는다.
