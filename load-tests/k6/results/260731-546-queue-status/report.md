# 대기열 상태 확인 경로 용량(`R`) 실측 — #546

## 0. 한 줄 요약

**`R = 약 1,400 RPS`, `T = 8초`.** ADR 0009 §3이 보수적으로 쓴 `R ≥ 400 / T ≥ 25초`보다 **용량이 3.5배 컸고 폴링 주기는 1/3로 짧아졌다.** nginx `keepalive_timeout`은 **75초(기본값) 유지**로 판정했다 — 15초 단축은 CPU 이득이 없으면서 메모리·핸드셰이크 비용만 늘었다.

---

## 1. 이 회차가 답해야 하는 것

**`R`(상태 확인 경로가 감당하는 RPS)을 실측한다.** [ADR 0009](../../../../docs/adr/0009-virtual-waiting-room-with-server-directed-polling.md) §3의 폴링 주기 하한 산식 `T ≥ N / R`의 입력값이고, 그 값이 없으면 대기열의 유일한 다이얼을 근거 없이 돌리게 된다.

부수적으로 ADR §5의 방향(nginx `keepalive_timeout` 유지/단축)을 A/B로 가른다.

---

## 2. 이슈 서사와 실측의 차이 — 먼저 읽을 것

**`R`은 지금까지 존재한 적이 없는 수치다.** #470은 "#348에서 실측한 폴링 경로 무릎"을 입력으로 쓰라고 적었지만, **#348은 회선 제약(좌석맵 응답 221 KB, 압축 없음)에 막혀 앱의 무릎에 도달조차 못 했다.** ADR 0009 §3이 이 사실을 명시하고 #529의 `seat-counts` 포화점 396.75 RPS를 하한 대용으로 빌려 썼다.

**그 대용값이 3.5배 보수적이었음이 이번에 확인됐다.** ADR은 "DB를 타지 않는 ZRANK 경로는 그보다 빠를 수밖에 없다"고 적었는데, 방향은 맞았고 폭이 컸다.

**ADR §5는 틀렸다.** "게이트웨이 keep-alive 타임아웃을 짧게 둔다"고 적었지만 게이트웨이 8080은 `127.0.0.1`로만 publish되고, `deploy/nginx/api.ticketrush.store.conf`의 `location /`은 upstream 블록 없이 `proxy_pass` 직접이라 **`keepalive` 지시자가 구조적으로 부재**하다. nginx는 게이트웨이 커넥션을 재사용하지 않으며, 유휴 커넥션은 **nginx가 쥔다.** 그래서 이 회차는 게이트웨이가 아니라 nginx 쪽 다이얼을 돌려 가른다.

## 3. 사전 게이트 — 새로 조치한 것은 G1 하나

| | 변경 전 | 변경 후 |
|---|---|---|
| `worker_connections` | **768** (Ubuntu 기본값) | 16,384 |
| `worker_rlimit_nofile` | 없음 (워커 fd soft 1,024) | 65,535 |
| 커넥션 슬롯 총량 | 768 × 2워커 = **1,536** | 32,768 |
| 실질 동시 요청 | 약 **768** | 약 16,384 |

**프록시 요청 하나가 슬롯을 2개 먹는다**(클라이언트 1 + 업스트림 1 — 재사용이 없으므로). 회차 A는 `maxVUs` 800이라 1,600 슬롯이 필요해, **변경 전 상태로는 앱이 아니라 nginx를 쟀을 것이다.** `nginx -t` 후 `reload`로 무중단 적용했고(health 200/47ms), 호스트에만 있는 설정이라 #522에 기록했다.

`QUEUE_ADMIT_RATE=1`로 낮춘 근거는 §6.3 참조.

## 6. 판정

**판정 기준은 회차 전에 확정했다**(`metadata.txt`의 `KNEE_CRITERIA`·`AB_CRITERIA`, 커밋 `4650b73a` — A-1 실행 중에 커밋해 시각으로 남겼다). 결과를 보고 고치지 않았다.

### 6.1 `R` 과 `T`

**무릎은 1600 계단이다.** 회차 전 정한 세 신호가 모두 같은 곳을 가리켰다.

| 신호 | 관측 |
|---|---|
| 실제 RPS 정체 | 200~800 계단은 94~96% 소화, **1600에서 87.5%로 꺾임** |
| `dropped_iterations` | 800까지 누적 95건 → **1600에서 39,634건 급증** |
| 호스트 CPU 수렴 | 90.7%(이 구성의 확정된 벽은 99% — #509·#518) |

A-1 1,399.8 / A-2 1,412.7 → **보수적으로 `R = 1,400`을 채택한다.**

```
T = ceil(10,000 / 1,400) = 8초
```

ADR 0009 §3의 보수값은 25초(`R=400` 가정)였다. **`R`이 3.5배 컸으므로 `T`가 3배 짧아진다** — 대기 인원이 많을 때도 사용자가 8초마다 순번을 갱신받는다.

### 6.2 keepalive A/B — 75초 유지

| 순위 | 지표 | A-1 (75s) | A-2 (15s) | 판정 |
|---|---|---|---|---|
| 1 | 호스트 CPU avg | 40.89% | 41.18% | 차이 +0.29%p → **5%p 이내라 2순위로** |
| 2 | 게이트웨이 메모리 avg | 318.0 MiB | 368.6 MiB | **+50.6 MiB (+15.9%) → 10% 초과, 여기서 판정** |
| 2 | 호스트 메모리 avg | 4.65 GiB | 4.79 GiB | +0.14 GiB |
| (참고) 3 | connecting p95 | 7.27 ms | 15.41 ms | 2.1배 |
| (참고) 3 | TLS p95 | 4.83 ms | 16.59 ms | 3.4배 |

**15초 단축은 CPU 이득이 없으면서 메모리와 재핸드셰이크 비용만 늘었다.** 회차 종료 후 `keepalive_timeout 15;` 지시자를 제거해 기본값 75초로 되돌렸다.

### 6.3 `QUEUE_ADMIT_RATE=1` 이 없었다면 이 회차는 무의미했다

승급 임계치는 `경과 × admit-rate`다. 기본값 20이면 PRELOAD 1만을 **8분 20초**에 넘어서는데 회차는 20분이라, **폴링 대상이 도중에 승급해 버린다.** 승급 후 폴링은 입장 토큰 `SET`이 붙어 Redis 명령이 **2회(`GET`+`ZRANK`) → 3회**가 되므로, 재려던 "대기 중인 사용자의 폴링"이 아니라 다른 경로를 재게 된다.

배포 전 로컬 스모크에서 발견해 `queue_status_admitted_leak` 지표를 신설했고(PR #547), 그 지표가 rate 20에서 **77.48%**, rate 1에서 **0.00%** 를 냈다. 본 회차 두 번 모두 0%다.

## 8. 한계 — 이 회차가 답하지 못한 것

- **A/B가 "1만 명이 유휴 커넥션을 물고 있는" 조건을 재현하지 못했다.** `status` 프로파일은 VU 최대 783이고 k6가 커넥션을 재사용하므로, keepalive 단축의 진짜 이점(유휴 커넥션 메모리·fd 절감)이 드러나는 조건이 아니다. **회차 B(1만 VU)에서 다시 본다.**
- **게이트웨이 메모리 +50.6 MiB가 순서 효과일 수 있다.** A-1 → A-2를 연속 실행하며 그 사이 게이트웨이를 재시작하지 않았다. JVM 힙의 시간 경과 증가와 keepalive 효과가 분리되지 않았다. 다만 판정은 이 값에 의존하지 않는다 — 3순위(재핸드셰이크)도 같은 방향을 가리킨다.
- **1600 계단에서 VU가 `maxVUs` 800에 닿았다**(A-1 783, A-2 800). `dropped`의 일부가 서버 포화가 아니라 생성기 VU 상한 때문일 수 있다. 같은 계단에서 CPU 90.7% + p95 급증이 동반됐으므로 서버 포화가 주 원인이라고 읽지만, **`R = 1,400`은 "이 조건에서 도달한 값"이지 경로의 절대 상한이 아니다.** 더 위를 보려면 `maxVUs`를 올린 계단 연장 회차가 필요하다.
- **이 회차 수치를 ADR 0004 토폴로지 회차(#348·#403·#529)와 절대값으로 직접 잇지 않는다.** nginx `worker_connections`가 768 → 16,384로 바뀌었다. 같은 호스트라도 전제가 다르다.
- **회차 B와도 생성기가 다르다.** 이 회차는 로컬 k6(ADR 0004), 회차 B는 AWS 임시 EC2(ADR 0010)다.
- 측정 대상은 **단일 EC2(2 vCPU)에 앱 8개 + Kafka·MySQL·Redis·관측 스택이 동거**하는 구성이다. 여기서 나오는 값은 "대기열 경로의 한계"가 아니라 "이 구성에서 도달한 지점"이다.
