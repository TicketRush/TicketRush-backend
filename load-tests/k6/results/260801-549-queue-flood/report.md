# 대기열 1만 VU 유입 제어 검증 — #549

## 0. 한 줄 요약

**유입 제어는 작동한다.** 유입이 VU 2,317 → 10,000으로 4.3배 늘어나는 동안 예매 서버 RPS는 **19.60-21.00**(평균 20.17)에 머물렀다 — 입장 허용량 20 대비 ±5% 안이다.

**대신 [ADR 0009](../../../../docs/adr/0009-virtual-waiting-room-with-server-directed-polling.md) §3의 폴링 주기 산식에 설계 결함이 있다.** `T = ceil(N/R)`이 `R`을 상수로 쓰는데, `R`은 동시 커넥션의 함수다. 그래서 붐빌수록 주기를 짧게 지시해 대기열이 스스로를 무너뜨린다. **회차를 한 번 날리고서야 알았다.**

---

## 1. 이 회차가 답해야 하는 것

[#472](https://github.com/TicketRush/TicketRush-backend/issues/472)의 완료 조건이자 ADR 0009 "결과" 첫 줄을 수치로 확인하는 유일한 축 — **`POST /api/v1/booking`의 서버 RPS가 유입 규모와 무관하게 `admit-rate-per-second`(20) 부근에서 평평할 것.**

## 3. B-1이 무너진 이유 — Redis가 아니다

`RedisCommandTimeoutException: GET. Command timed out after 1 second(s)`가 5분간 **25만 줄** 찍혔다. 그런데 같은 순간 Redis는 놀고 있었다.

| | |
|---|---|
| Redis 컨테이너 CPU | **3.89%** |
| Redis `slowlog` | **비어 있음** |
| Redis 처리량 | 1,283 ops/s |
| **호스트 CPU** | **99.20%** (avg 68.01%) |
| 게이트웨이 컨테이너 CPU | 89.65% |

**Lettuce의 타임아웃은 클라이언트 쪽에서 재는 값이다.** 게이트웨이가 CPU를 못 잡아 자기 이벤트 루프를 못 돌리면, 서버가 즉답해도 1초가 지나간다. 잰 것은 Redis 성능이 아니라 **CPU 굶주림**이다.

### 램프가 아니라 폴링 수요다 — 커넥션은 증상이다

처음에는 "램프 버스트 때문"이라고 판단해 램프 연장을 제안했다. **틀렸다.** 램프가 끝난 뒤에도 `unavailable`이 계속 났고, 커넥션 수와 함께 오르내렸다.

그래서 한때 "커넥션 4,000이 선"이라고 적었는데 **그것도 틀렸다.** B-2가 커넥션 **4,752**까지 가고도 `unavailable` 0이었다 — 그 선은 B-1 내부 표본만으로 그은 것이라 B-2에 성립하지 않는다.

**커넥션은 원인이자 결과다.** 진짜 레버는 폴링 수요가 용량을 넘은 것이고, 커넥션 폭증은 그 증상이다.

```
B-1 폴링 수요 1,250 RPS  vs  이 동시성에서의 처리 용량 약 450 RPS
   → 응답이 밀린다 (queue_status_duration p95 5.27초)
   → 리틀의 법칙: 진행 중 요청 ≈ 1,250 × 5.27 ≈ 6,600건 × 2슬롯 ≈ 13,200
   → 최대 커넥션 16,701 의 대부분이 '쌓인 요청' 이다
```

프록시 요청 1건이 클라이언트+업스트림 **2슬롯**을 먹는다(회차 A G1에서 확인한 그대로). 그래서 요청이 밀리면 커넥션이 그 2배로 불어나고, 불어난 커넥션이 다시 CPU를 먹어 응답을 더 밀리게 하는 되먹임이 된다.

**두 회차를 가른 것은 커넥션이 아니라 `R`이다**(1,400 → 400). 그 하나를 바꾸자 수요가 400 RPS로 내려가 되먹임 자체가 시작되지 않았다.

| | B-1 | B-2 |
|---|---|---|
| 폴링 수요 (`N/T`) | **1,250 RPS** | **400 RPS** |
| 최대 동시 커넥션 | **16,701** | 4,752 |
| `status_duration` p95 | **5.27s** | 32.1ms |
| `unavailable` | 15.55% | **0%** |

## 4. 핵심 발견 — `R`은 상수가 아니다

같은 경로, 같은 호스트, 같은 이미지(`21d2da2d`)인데 상태 확인 경로의 처리량이 **3.1배** 차이났다.

| 회차 | 동시 커넥션 | 상태 확인 처리량 | `queue_status_duration` p95 |
|---|---|---|---|
| A (#546) | 약 1,600 (VU 783) | **1,400 RPS** | 650ms(무릎) |
| B-1 | **16,701** (VU 1만) | **450 RPS** | **5.27s** |
| B-2 | 4,752 (VU 1만) | — | **32.1ms** |

ADR 0009 §3의 산식은 이 의존성을 모른다.

```
N=10,000 · R=1,400 → T=8초 → 폴링 수요 1,250 RPS
                     그 동시성에서의 실제 용량 450 RPS
                                     → 수요가 용량의 2.8배
```

**대기 인원이 많을수록 커넥션이 늘어 `R`이 떨어지는데, 산식은 한산할 때 잰 `R`을 쓴다.** 정확히 붐빌 때 주기를 너무 짧게 지시하는 구조다.

**ADR 0009의 원래 보수값(`R ≥ 400`, `T = 25초`)이 옳았다.** 회차 A가 그것을 "3.5배 보수적이었다"며 1,400으로 정정한 것이 오히려 위험한 방향이었다 — 회차 A 자신이 *"`R = 1,400`은 '이 조건에서 도달한 값'이지 경로의 절대 상한이 아니다"* 라고 적어 둔 경고가 맞았다.

`R=400`으로 되돌린 B-2가 유효 회차가 됐다.

## 6. 실효 코호트는 9,276명이다 (1만이 아니다)

**724명이 진입(`enqueue`)에서 실패했다** — `http_req_failed` 724건과 정확히 일치한다.

⚠️ **계측 구멍이다.** 시나리오가 `if (!waitingToken) return;`으로 조용히 넘어가고, 서버에도 `enqueue` 결과 카운터가 없다. B-1 때는 *"대기 3,420 + 임계치 3,000 = 진입 6,420"* 으로 역산해서야 3,500명이 사라진 것을 알았다. **다음 회차 전에 k6 `queue_enqueue_failed` + 서버측 카운터를 넣는다.**

## 8. 생성기 EC2를 만들지 않았다 — ADR 0010 기각

[ADR 0010](../../../../docs/adr/0010-in-aws-load-generator-for-ten-thousand-vu.md)은 이 회차를 위해 "생성기를 AWS 임시 EC2로 옮긴다"고 결정했다. **회차 전 프로브에서 그 근거 세 가지가 전부 무너졌다.**

| ADR 0010이 든 벽 | 실측 |
|---|---|
| 가정용 업로드 대역이 상한 | 1만 VU 프로브가 쓴 양 **0.6 Mbps**. 본 회차도 41 kB/s |
| Docker NAT · 포트 고갈이 앱보다 먼저 | ephemeral 포트 **28,231** · 컨테이너 `nofile` **1,048,576** |
| 가정 공유기 세션 테이블 "통상 수천" | 서버측 established **정확히 10,000**을 3분 이상 유지, `probe_connect_failed` **0.00%**(0/99,944) |

대역폭 가정이 특히 크게 빗나갔다 — 폴링 요청·응답이 작아서(203 B 이하) 1만 명이 붙어도 1 Mbps를 넘지 않는다. ADR은 응답이 221 KB였던 좌석맵 회차(#348)의 경험을 대기열에 그대로 옮겨 적은 것으로 보인다.

**비용 0, 셋업 0으로 회차를 마쳤다.** ADR 0010의 상태를 이 실측으로 정정한다.

## 9. 이 회차가 답하지 못한 것

- **"1만 명이 동시에 줄 서 있는" 조건은 이번에도 재현되지 않았다.** 대기 인원 최대가 **3,254명**이다 — 승급이 20명/초로 빠지는 동안 5분에 걸쳐 채웠기 때문이다. 회차 A가 남긴 같은 숙제가 그대로다. **재현하려면 램프가 배수보다 빨라야 하는데 그게 바로 B-1이고, B-1은 CPU에서 무너졌다 — 이 하드웨어에서는 둘을 동시에 만족할 수 없다.**
- **`R`이 동시성의 함수라는 선을 두 점으로만 그었다**(1,600 / 16,701 커넥션). 함수 형태를 알려면 커넥션을 계단으로 올리는 별도 회차가 필요하다.
- **실효 코호트가 9,276명이다.** 724명의 진입 실패 원인을 계측하지 못했다(§6).
- 측정 대상은 **단일 EC2(2 vCPU)에 앱 8개 + Kafka·MySQL·Redis·관측 스택이 동거**하는 구성이다. 여기서 나오는 값은 "대기열 경로의 한계"가 아니라 "이 구성에서 도달한 지점"이다.
- **이 회차 수치를 nginx `worker_connections` 768 시절 회차(#348·#403·#529)와 절대값으로 직접 잇지 않는다.**

## 10. 후속 작업

1. **ADR 0009 §3 정정** — `R`을 상수로 쓰는 산식의 결함과 `R = 400` 복원. 회차 A(#546)가 갱신한 1,400을 되돌린다.
2. **ADR 0010 정정** — 생성기를 옮기지 않기로. 실측 근거는 §8.
3. **`queue.status-rps-capacity` 기본값 1,400 → 400** (`application.yml`).
4. **진입 실패 계측** — k6 `queue_enqueue_failed` + 서버측 `enqueue` 결과 카운터.
