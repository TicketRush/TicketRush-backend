# 대기열 ON/OFF 대조 1만 VU 회차 — #554

## 0. 한 줄 요약

**대기열은 유입을 이연시킨다. 그리고 그 대가로 서버 부하를 4.4배 만든다.**

| | ON | OFF |
|---|---|---|
| 게이트웨이 총 RPS | **444.6** | **100.5** |
| 사용자당 폴링 | **16.22회** | **1회** |
| 램프 종료 후 예매 지속 | **237초** | **66초** |
| 호스트 CPU max (공통 창) | **88.59%** | **84.02%** |
| 오버셀 | 0행 | **0행** |

**두 arm 모두 무너지지 않았다.** 이슈 본문이 미리 지목한 그 경우다 — *"무너지지 않으면 그것이 더 큰 발견이다. `admit-rate 20` 이 과하게 보수적이라는 직접 근거가 되고 #555 의 계단 상한을 올려 잡을 수 있다."*

그리고 **대기열 없이도 오버셀이 0이었다.** 대기열은 정합성 장치가 아니라 부하 정형화 장치이고, 정합성은 `@Version` + Redis 락이 지킨다 — 이 회차가 그것을 분리해 보여 준다.

**주의: 이 회차는 "대기열이 붕괴를 막는다" 를 증명하지 않는다.** OFF arm 이 도달한 예매 33.73 RPS 는 [#344](https://github.com/TicketRush/TicketRush-backend/issues/344) 붕괴점(258 RPS)의 **13%** 다. 그 이유를 회차 **전에** 산술로 적어 두었고(§1.1), 실측이 그 산술을 오차 2% 안에서 확인했다.

## 1. 이 회차가 답해야 하는 것

[#549](https://github.com/TicketRush/TicketRush-backend/issues/549) B-2 는 대기열 **ON** 에서 예매 서버 RPS 19.60-21.00 · 예매 p95 최대 42.9ms · 오버셀 0행을 얻었다. 그런데 **"대기열이 없으면 어떻게 되는가" 의 실측이 저장소에 없었다.** 비교 대상이 없으면 그 수치가 성과인지 판별할 수단이 없다.

`queue.enabled` 가 환경변수 하나로 열려 있어 **같은 배포본에서 대조군을 만들 수 있다.** 이 회차의 결론은 절대값이 아니라 **회차 내부의 ON/OFF 차이**이고, 결과는 후속 admit-rate 계단 회차([#555](https://github.com/TicketRush/TicketRush-backend/issues/555))의 입력값이 된다.

### 1.1 이 회차가 답할 수 있는 질문은 하나뿐이다 — 회차 전에 확정했다

부하 모델을 회차 전에 산술로 확정하고 `metadata.txt` 에 커밋했다(커밋 `57930b89`).

```
ARRIVAL_RATE = QUEUE_FLOOD_VUS(10,000) / QUEUE_FLOOD_RAMP(300s) = 33.33 여정/s
```

`waiting-room.js` 의 `journeyDone` 가드로 **VU 1개는 여정을 1회만 탄다.** 그래서 유입은 "1만 동시" 가 아니라 "초당 33.3 도착" 이고, 유지 15분 구간의 도착률은 0 이다.

| | ON arm | OFF arm |
|---|---|---|
| enqueue | 33.3 RPS | 33.3 RPS |
| status(폴링) | **≈400 RPS** — 수요 = `waiting/T` 인데 `T = ceil(waiting/400)` 이라 `waiting ≥ 1,200` 부터 R 에 산식으로 고정된다 | **33.3 RPS** — 첫 폴링에 승급하므로 사용자당 1회 |
| booking | 20 RPS (admit-rate) | 33.3 RPS (도착률) |
| **게이트웨이 총** | **≈453 RPS** | **≈100 RPS** |

이 모델은 세 번 검증됐다.

| 검증 | 예측 | 실측 | 오차 |
|---|---|---|---|
| #549 B-2 총 요청 수 | 약 167,000 | 167,083 | 8% 안 |
| #549 B-2 게이트웨이 RPS max | 453 | 434.36 | 4.1% |
| **이번 ON arm 게이트웨이 RPS max** | **453** | **444.6** | **1.9%** |

**따라서 이 회차는 "대기열이 붕괴를 막는다" 를 증명할 수 없다.** OFF arm 이 도달하는 예매 33.3 RPS 는 [#344](https://github.com/TicketRush/TicketRush-backend/issues/344) 붕괴점(booking 단독 258 RPS 에서 호스트 CPU 99.87%)의 **12.9%** 다. 그리고 대기열을 끄면 전체 요청의 88% 인 폴링이 사라져 **OFF arm 이 ON 보다 서버 부하가 4.5배 가볍다.**

증명할 수 있는 것은 **이연(deferral)** 하나다. 램프가 선형이라 두 arm 다 예매 RPS 가 평평하므로 **평탄성은 판별력이 0** 이고, 수준 차이도 1.67배뿐이라 ON 밴드 상한과 겹칠 위험이 있다. 두 arm 을 실제로 가르는 것은 **유입이 끝난 뒤에 무슨 일이 일어나는가** 다.

| arm | 창 | 근거 |

### 2.2 대조표에 넣지 않은 축 — 유령값

`ticketrush_queue_waiting` 과 `ticketrush_queue_poll_interval_seconds` 는 **OFF arm 에서도 ON 과 거의 같은 곡선을 그린다.** `toSnapshot()` 이 `enabled` 와 무관하게 `remainingWaiting(enqueued, threshold)` 를 계산하고 `recordAdmitted()` 가 게이지에 그대로 쓰기 때문이다(`WaitingRoomService.java:202, 235`). 실제로 기다린 사람은 0명인데 대기 인원 곡선이 그려지므로 나란히 두면 오독한다.

`ticketrush_queue_entry_token_*` 은 OFF 에서 전부 0 인데, 통과해서가 아니라 `EntryTokenGatewayFilter.java:91` 이 계측 **전에** 리턴하기 때문이다. 이 0 을 "OFF 가 통과했다" 로 읽으면 계측 부재를 건전성으로 오독한다 — 그래서 **`> 0` 을 '킬 스위치가 안 먹었다' 는 반대 방향 신호로 뒤집어** 무효 기준에 넣었다.

### 4.5 꺾이는 지점 — 임계는 걸렸지만 포화가 아니다

회차 전에 정한 9개 임계 중 `KNEE_WATCH_3`(booking p95 ≥ 150ms, 2연속)이 **t+42s ~ t+87s** 에 걸렸다.

**포화로 읽지 않는다. JIT 워밍업이다.**

```
t+42s 219ms → t+57s 200ms → t+72s 183ms → t+87s 167ms → t+102s 149ms → t+117s 132ms
```

- 101개 표본 중 **4개만** 임계를 넘었고 전부 램프 초반의 연속 구간이다
- 같은 구간에 VU 는 917 → 10,000 으로 **10배** 늘었는데 p95 는 **단조 감소**했다
- 부하가 늘수록 지연이 내려가는 것은 포화의 반대다

→ **실질 `KNEE=N/A`.** 나머지 8개 임계는 교차가 없다.

> **이 판정은 기준을 고친 것이 아니다.** `KNEE_WATCH_3` 은 그대로 두고 해석에 근거를 달았으며, **같은 기준이 OFF arm 에도 그대로 적용된다.** 회차 전에 정한 것을 결과에 맞춰 바꾸면 §6.1 위반이다.

### 4.6 오버셀 — 검증 방법을 바꿔야 했다

**0행.** 예매 9,781 = 좌석 9,781 = 사용자 9,781 (완전한 1:1:1).

**런북 §13.4-(7)의 (a) 쿼리는 이 회차에서 검출력이 0 이었다.** 그 쿼리는 `booking_status IN ('PENDING','CONFIRMED')` 로 거르는데, 검증 시점의 LTQ 예매는 **전부 `EXPIRED`(9,749) / `CANCELED`(32)** 였다 — 예매가 5-6분 뒤 만료되고 이 회차는 20분짜리라 종료 시점에 `PENDING` 이 하나도 없다. **쿼리가 아무 행도 보지 않은 채 "0행 = 정상" 이 나온다.**

→ 상태와 무관한 좌석 중복 검사로 다시 쟀다. 이 회차는 VU 마다 유일 좌석을 노리고 1회 여정이므로 중복이 있으면 그 자체가 오버셀이다.

| `entry_token` 카운터 | 증가 없음 | `EntryTokenGatewayFilter:91` 이 계측 전에 리턴 |
| `queue_booking_forbidden` | 0.00% | 게이트가 예매를 막지 않았다 |

### 5.2 주 판정축 — 이연이 사라졌는가

**(i) `DEFERRAL_RATIO` 18.73%** — 선언 기준 ≤10%를 **넘겼다.** 회차 전 예측은 3.3%였다.

```
ON  : 램프 종료(t+300s) 후 237초간 예매 지속 → t+537s 에 0
OFF : 램프 종료 후  66초간 예매 지속 → t+366s 에 0
```

**예측이 빗나간 이유.** "마지막 VU 가 `t+300+T`(약 10초)에 끝난다" 를 전제했는데, 램프 종료 시점에 아직 진입·폴링 단계인 VU 가 많아 실제로는 66초에 걸쳐 마무리됐다.

**그래도 분리는 성립한다** — 47.01% vs 18.73%(2.5배), 지속 시간 237초 vs 66초(3.6배). 예측한 13배는 아니지만 **방향과 분리는 확인됐다.**

**(ii) 예매 RPS 판정창(t+30~300s)** min 6.60 / **avg 28.73** / max 33.73 → 선언 밴드 33.3 ± 20%(26.7~40.0) 안. **"입장 허용량 20" 이 아니라 "램프 기울기" 를 따라간다**는 판정이 확인됐다.

### 5.4 꺾이는 지점 — 미도달

> `KNEE_WATCH_4`(k6 `http_req_failed` ≥ 1%)는 수치상 걸리지만 자동 판정에 잡히지 않았다(그 시계열이 덤프에 없다). 수동 확인 결과 위 §5.3 대로 진입 실패이므로 포화 신호가 아니다. **이 사실을 적어 둔다 — 다음 회차는 `k6-req-failed` 를 덤프에 넣어야 자동 판정이 완결된다.**

## 8. 이 회차가 답하지 못하는 것

회차 **전에** `metadata.txt` 에 적은 그대로다.

- **무릎(포화점)의 위치** — `ramping-vus` 는 다이얼이 없어 실효 도착률이 33.3/s 상수인 **단일 동작점 회차**다. 원리상 스윕이 아니다. 무릎을 원하면 전 여정을 `ramping-arrival-rate` 계단으로 돌리는 별도 회차가 필요하다.
- **"대기열이 붕괴를 막는다"** — §1.1. 이 회차가 답하는 것은 이연의 유무뿐이다.
- **"1만 명 동시 대기"** — 대기 인원 최대는 약 4,000명이다. #546 · #549 가 남긴 숙제가 그대로 남는다. 램프를 배수보다 빠르게 하면 #549 B-1 이 되고 그 회차는 CPU 에서 무너졌다 — 이 하드웨어에서 둘은 동시에 만족되지 않는다.
- **arm 순서 효과** — ON→OFF 연속 실행이라 JIT 워밍업 · 페이지 캐시 · MySQL 버퍼풀이 두 번째 arm 에 유리하다. 순서를 뒤집은 대조가 없다.
- **배포본 드리프트의 몫** — ON arm 이 #549 B-2 와 다르게 나와도 그 차이가 코드 134파일 때문인지 다른 조건 때문인지 이 회차 단독으로는 못 가른다.
- **OFF 는 "대기열 미도입" 이 아니다** — OFF arm 도 enqueue 1회 + status 폴링 1회를 친다.
- **`R=400` 은 OFF 에서 의미가 없다** — 두 arm 의 `T` 가 같은 것은 `enqueue` 응답이 같은 산식을 쓰기 때문이지 OFF 에 폴링 제어가 있다는 뜻이 아니다.

### 8.1 시계열을 잇지 않는 범위

- **#549 B-2(`21d2da2d`)와 절대값으로 직접 잇지 않는다.** 배포본이 다르고 그 사이 39커밋 · 프로덕션 코드 134파일이 들어왔다. 참고 수치로만 병기한다.
- nginx `worker_connections` 768 시절 회차(#348 · #403 · #529)와도 잇지 않는다.
- 단일 EC2 2 vCPU 에 앱 8개 + Kafka · MySQL · Redis · 관측 스택 동거(ADR 0006 · ADR 0007). 절대값에 이웃 서비스의 포화가 섞인다.
- **결제 · 티켓 발급은 여정에 없다.** `StubPaymentApprovalClient` 는 `@Profile("!prod")` **와** `@ConditionalOnProperty(payment.pg.stub.enabled=true)` 의 **AND** 조건으로 등록되므로 prod 에서 실행되지 않는다. 예매가 5-6분 뒤 만료되며 outbox 부하가 사실상 2배가 되는 점은 #348 과 동일하다.

## 9. 회차 중에 발견한 것

측정 결과와 별개로, 이 회차를 준비하고 실행하면서 **다음 회차가 같은 함정에 빠지지 않게** 고쳐야 할 것들이 나왔다. 전부 런북과 도구에 반영했다.

### 9.1 #549 의 "유령 `IMAGE_TAG`" 는 불일치가 아니라 엉뚱한 파일이었다

#549 는 *"`.env` 는 `6b7301a0…` 을 가리키는데 그 태그가 ECR·CD기록·저장소 어디에도 없었다"* 고 기록했다. **EC2 에 `.env` 가 두 개 있다.**

| 경로 | `IMAGE_TAG` | 쓰이는가 |
|---|---|---|
| `~/ticketrush/.env` | `6b7301a0…` | **아니다 — 잔재** |
| `~/ticketrush/deploy/.env` | `b0f3da84…` (CD 성공 SHA) | **이것이 실제** |

`cd.yml` 이 `docker compose --env-file deploy/.env` 로 실행하므로 `deploy/.env` 만 유효하다. 잔재를 고쳐도 배포에 아무 영향이 없고, **고쳤다고 믿으면 오히려 위험하다.** 런북 §16.4 의 경고문을 이 사실로 교체했다.

> 준비 중에 실제로 잔재 파일을 먼저 고쳤다가 되돌렸다. 그 파일에는 `QUEUE_*` 키가 아예 없었는데, 그것이 "이 파일은 안 쓰인다" 는 첫 신호였다.

### 9.2 2 vCPU 에서는 관측 행위가 관측값에 잡힌다

무부하 기저 CPU 를 5분 재다가 **`max 57.55%`** 가 나왔다. 원인은 대상이 아니라 측정자였다 — 그 구간에 SSH 점검 명령을 던졌다. 같은 순간 `docker stats` 의 컨테이너 CPU 합계는 **13%**, `load average` 는 **0.10** 이었다.

명령을 던지지 않은 구간에서는 값이 일관됐다.

| 창 | 표본 | max |
|---|---|---|
| 10:47:00~10:50:00Z | 13 | 9.86% |
| 10:50:30~10:52:15Z | 8 | **7.57%** |

비용을 만드는 것: SSH 세션 자체 · `docker stats`(컨테이너 16개 샘플링) · `docker inspect` · Prometheus range query(`dump-timeseries.py` 는 쿼리를 40개 넘게 던진다).

→ **회차 중에는 원격 명령을 던지지 않는다.** 런북 §16.6 에 이 경고를 추가했다.

### 9.3 오버셀 검증 쿼리가 이 회차 형태에서 검출력이 0 이다

§4.6 그대로다. 런북 §13.4-(7)의 (a) 는 `booking_status IN ('PENDING','CONFIRMED')` 로 거르는데, **20분짜리 회차의 종료 시점에는 예매가 전부 만료돼 `PENDING` 이 0** 이다. 쿼리가 아무 행도 보지 않은 채 "0행 = 정상" 이 나온다.

→ 상태 무관 좌석 중복 검사를 함께 돌리고 **SQL 원문을 증적에 남긴다**(#549 는 남기지 않았다).

### 9.4 회차 전에 정한 임계 하나가 이 프로젝트에서 상시 참이었다

`container-mem-limit-pct >= 90%` 를 포화 신호로 잡았는데, **#549 B-2(유효 회차)의 공통 창에서도 `booking-service` 가 96.28-98.34%** 였다. ADR 0006 의 `mem_limit` 설계상 정상 운영값이라 어떤 arm 이든 시작하자마자 "포화" 로 오판된다.

`container-oom-kills > 0` 으로 교체했다. **근거가 이번 회차 결과가 아니라 #549 덤프이고 ON arm 결과를 보기 전에 고쳤다** — §6.1 이 금지하는 "결과를 보고 기준을 고치는 것" 이 아니라 측정 불가능한 임계를 걷어낸 것이다.

### 9.5 램프 초반 지연을 포화로 읽으면 안 된다

§4.5 그대로다. `KNEE_WATCH_3` 이 t+42s 를 지목했지만 p95 가 219 → 132ms 로 **단조 감소**했다. 부하가 10배 느는 동안 지연이 내려가는 것은 포화의 반대다.

이 회차는 기준을 고치지 않고 해석에 근거를 달았다. **다음 회차에서 임계를 손볼 거라면 "램프 종료 이후" 로 판정 구간을 제한하는 편이 옳다** — 임계값을 올리면 진짜 포화도 놓친다.

### 9.6 런북 §16.4 의 실행 명령을 그대로 복사하면 무효 회차가 된다

두 가지가 실측과 어긋나 있었다.

| 런북 | 실제 |
|---|---|
| `QUEUE_FLOOD_RAMP` 인자 없음 | 기본값이 `2m` 이고 **램프 2분이 곧 #549 B-1 을 무효로 만든 조건이다.** `-e QUEUE_FLOOD_RAMP=5m` 명시 필요 |
| `--network host` + `localhost:9090` | 생성기가 Windows Docker Desktop 이면 동작하지 않는다. `host.docker.internal:9090` 을 쓴다(#549 도 실제로는 그랬다) |
| G2 = `docker compose restart` | `env_file` 은 `restart` 로 다시 읽히지 않는다. `--force-recreate` 여야 한다 |

전부 런북에 반영했다(커밋 `8d25a0e2`).

## 10. 후속 작업

### 10.1 #555 (admit-rate 계단 회차)로 넘기는 입력값

이 회차가 그 회차의 **입력값을 만드는 것**이 존재 이유였다.

- **`admit-rate 20` 은 보수적이다.** OFF arm 이 예매 **33.73 RPS** 를 통과시키고도 포화하지 않았다(호스트 CPU max 84.02%). 계단의 하한을 20 위에서 잡아도 된다.
- **천장의 근거는 이 회차에 없다.** 33.73 은 부하 모델이 만든 상한이지 시스템의 한계가 아니다(§5.4). #555 는 **`ramping-arrival-rate` 계단**으로 돌아야 무릎을 잡는다 — `ramping-vus` 는 다이얼이 없다(§8).
- **CPU 여유의 출처를 함께 넘긴다.** ON arm 의 CPU 66.31%(avg) 중 폴링이 상당 부분이다. 계단을 올리면 폴링 수요도 `T = ceil(waiting/R)` 로 함께 오르므로, **예매 RPS 만 보고 계단을 정하면 안 된다.**

### 10.3 다음 회차 전에 손볼 것

1. **`k6-req-failed` 를 `dump-timeseries.py` 에 넣는다.** `KNEE_WATCH_4`(k6 `http_req_failed` ≥ 1%)가 이번 OFF arm 에서 수치상 걸렸는데 **시계열이 없어 자동 판정에 잡히지 않았다**(§5.4). 임계를 정해 놓고 재지 못하면 기준이 아니다.
2. **KNEE 판정 구간을 "램프 종료 이후" 로 제한한다.** 램프 초반 JIT 워밍업이 `booking p95 ≥ 150ms` 를 두 arm 모두에서 건드린다(§4.5). 임계값을 올리면 진짜 포화도 놓치므로, 구간을 자르는 편이 옳다.
3. **오버셀 검증을 상태 무관 검사로 런북에 못 박는다.** §9.3 — 현재 §13.4-(7)의 (a) 는 20분짜리 회차에서 검출력이 0이다.
4. **서버측 `enqueue` 결과 카운터.** 이번엔 k6 쪽만 넣었다. 진입 실패가 ON 219 → OFF 455 로 2배 늘었는데 **원인을 서버에서 확인할 수단이 없다**(콜드 스타트 영향으로 추정되나 근거가 없다). 별도 이슈 대상.

### 10.4 이 회차가 만든 새 질문

- **왜 OFF arm 의 진입 실패가 2배인가?** 455 vs 219. OFF 는 arm 사이 재시작으로 콜드 스타트였다는 것이 유일한 후보이지만, 서버측 계측이 없어 확인하지 못했다(→ 10.3-4).
- **MySQL 컨테이너 메모리가 OFF 에서 100.00% 에 닿았다**(ON 83.67%). 예매를 1.67배 빠르게 밀어 넣은 결과로 보이나, OOM kill 은 0건이었다. `admit-rate` 를 올리는 #555 에서 이 축을 감시 대상에 넣어야 한다.
