# /commit — 팀 형식으로 커밋

현재 변경사항을 팀 커밋 규칙에 맞춰 커밋한다. **이 커맨드는 메인 컨텍스트에서 실행되므로, 지금까지의 대화 맥락을 살려 요약을 작성한다.**

## 입력
- `$ARGUMENTS` (선택) = 타입 지정·요약 힌트·스테이징 범위 등 추가 지시. 예: `Fix 로그인 토큰 만료 처리`, `Docs만`, `staged만`.
- 없으면 변경 내용과 대화 맥락으로 타입·요약을 추론한다.

## 커밋 형식 (commit-msg 훅이 강제)
- `.githooks/commit-msg` 규칙: 첫 줄이 **`[Type] #이슈번호 한 줄 요약`** 이어야 한다.
- **Type 7종만 허용:** `Feat` / `Fix` / `Docs` / `Refactor` / `Test` / `Chore` / `Infra`
- **이슈번호는 단일 `#N`** 만 가능하다 (훅 정규식이 `#숫자` 하나만 허용 — `#1, 2` 같은 다중 표기는 커밋 거부됨).

## 작업 순서

**1단계: 변경 확인**
```
git branch --show-current      # 브랜치명 (이슈번호 추출용)
git status --short             # 변경 파일
git diff                       # 미스테이징 변경
git diff --cached              # 이미 스테이징된 변경
```

**2단계: 이슈번호 결정**
- 브랜치명(`feature/248`, `fix/12` 등)에서 **숫자를 이슈번호로 추출**한다.
- 브랜치에서 못 뽑으면(예: `develop`에서 작업) 사용자에게 이슈번호를 물어본다.

**3단계: Type·요약 결정**
- `$ARGUMENTS`에 타입이 있으면 그대로 쓴다. 없으면 변경 성격으로 7종 중 고른다 (애매하면 가장 가까운 것 + 고른 이유 한 줄 보고).
- 요약은 **대화 맥락 + diff**로 한국어 한 줄. 무엇을 했는지 명확하게. 필요하면 본문(빈 줄 뒤 불릿)으로 상세를 덧붙인다.

**4단계: 스테이징**
- 기본은 `git add -A` (전체). `$ARGUMENTS`에 `staged만`/특정 경로 지시가 있으면 그에 따른다.
- **커밋 직전 무엇을 커밋할지 한 줄로 보고**하고 진행한다.

**5단계: 커밋**
```
git commit -F - << 'EOF'
[Type] #번호 요약
... (필요 시 본문) ...
EOF
```
- ⚠️ **pre-commit 훅 주의**: 스테이징된 `.java` 파일이 있으면 `spotlessApply` + `checkstyleMain/Test`가 실행된다. spotless가 파일을 고치면 자동 재스테이징되고, checkstyle 실패 시 커밋이 막힌다 — 실패하면 그대로 보고하고 멈춘다(억지로 우회하지 않는다).
- `.java`가 없으면 pre-commit은 스킵된다.

**6단계: 커밋 후 이슈/PR 본문 동기화**
- 커밋 뒤, 현재 브랜치에 연결된 **이미 발행된 이슈·PR이 있으면 그 본문을 이번 작업 내용까지 반영하도록 업데이트**한다. 절차·원칙은 `/issue` 커맨드(`.claude/commands/issue.md`)의 **「커밋 후 기존 이슈/PR 본문 동기화」** 섹션을 따른다(실제 한 작업만 반영·기존 내용 보존·완료조건 체크박스 동기화·코드 미수정).

## 보고 형식
1. 결정한 커밋 메시지 (`[Type] #번호 요약`)
2. 커밋된 파일 수 / 커밋 해시
3. pre-commit 훅 실행 결과(스킵/통과/실패)

## 주의
- **push는 하지 않는다.** 사용자가 명시적으로 요청할 때만 push 한다.
- 팀 컨벤션 단일 출처는 `docs/backend-convention.md`.
