# /dev-cycle — 이슈 기반 개발 사이클 자동 진행

`$ARGUMENTS`로 받은 **이슈 번호** 기준으로 권장 작업 사이클(`docs/ai-workflow-guide.md` 6장)을 순서대로 진행한다.
완전 무인 자동이 아니라 **승인 게이트에서 멈추는 "자동 순서 진행"** 이다. 두 승인 게이트(플랜 / PR)는 절대 건너뛰지 않는다.

## 입력

- `$ARGUMENTS` = 이슈 번호 (예: `1`). "이슈 1번 개발 진행하자" 같은 자연어로 들어와도 **숫자만 추출**해 이슈 번호로 쓴다.
- 번호가 없으면 어떤 이슈인지 사용자에게 먼저 물어본다.

## 진행 순서

### 1단계: 이슈 확인 (이슈 생성 단계 건너뜀)

- 이슈는 **이미 존재**한다고 가정한다. `gh issue view <번호>` 로 제목·본문·라벨을 읽어 작업 범위를 파악한다.
- **새 이슈를 만들지 않는다.** (`/issue` 단계는 생략)

### 2단계: 조사 (researcher, 자동)

- `researcher` 에이전트로 이슈와 관련된 현재 코드/스펙 현황을 조사한다.
- 결과를 근거(`파일:라인`)와 함께 요약해 사용자에게 보고한다.

### 3단계: 계획 (planner 초안 → /grill-me 대화 → 확정)

- 먼저 `planner` 에이전트로 조사 결과 기반 **초안 플랜**을 만든다 (변경 파일 · 단계 · 리스크/영향 · 롤백 · 사람이 결정할 사항).
- 초안을 보여준 뒤, **사용자에게 `/grill-me` 입력을 요청하고 기다린다.**
    - ⚠️ `grill-me`는 `disable-model-invocation: true` 라서 **모델이 자동 실행할 수 없다.** 반드시 사용자가 직접
      `/grill-me`를 입력해야 한다. "초안을 다듬으려면 `/grill-me`를 입력하세요"라고 안내하고 대기한다.
    - grill-me 세션에서 나온 결정사항으로 초안을 보완한다.
    - `/grill-me` 미설치거나 사용자가 건너뛰길 원하면: `AskUserQuestion`으로 핵심 결정사항·엣지케이스를 직접 캐물어 대체한다.
- 대화가 끝나면 **확정된 최종 플랜**을 정리해 보여준다.

### ⏸ 승인 게이트 1 — 플랜 승인

- 최종 플랜을 제시하고 **사용자 승인을 기다린다. 승인 전에는 코드를 수정하지 않는다.**

### 4단계: 브랜치 분기 + 구현 (승인 후에만)

- `develop` 최신 기준으로 `{이슈 label}/{번호}` 브랜치를 만든다(이미 있으면 체크아웃). 팀 규칙: `{브랜치 단위}/{이슈번호}`이며 **브랜치 단위는 이슈에
  붙은 label과 동일하게** 맞춘다(예: label `refactor` → `refactor/{번호}`). 상세는 `docs/backend-convention.md` 브랜치
  규칙.
- 확정된 플랜대로 구현한다. **이때 변경에 대한 테스트 코드도 함께 작성한다**(프로덕션 + 테스트). 테스트 범위는 플랜에서 정한 대로 따른다.

### 5단계: 테스트 실행 (/test, 자동)

- `/test` 커맨드로 변경된 모듈의 테스트를 **실제로 실행**해 통과를 확인한다(추측 아님). 실패하면 고치고 다시 돌린다.

### 6단계: 셀프 검증 (reviewer) → 리뷰 반영 승인

- `reviewer` 에이전트로 `develop...HEAD` 변경을 점검한다(🔴 Must / 🟡 Should / 🔵 Nit).
- reviewer 지적을 **심각도별 분류표(번호 | 파일 | 위치 | 심각도 | 요약 | (메인이 덧붙인) 추천)로 사용자에게 제시**한다. `reviewer` 산출물엔 '추천'이 없으므로 메인이 의견을 덧붙인다. **여기서 멈추고** 사람이 건별 수용/거절을 결정한다(예: "1·2 반영, 3 거절"). **결정 전에는 어떤 코드도 미리 고쳐 두지 않는다**(이미 반영했다면 되돌리고 미반영 상태로 제시).
- 승인된 지적만 반영한 뒤 `reviewer`로 **재점검**(반영 결과 확인 목적)하고, 거절 건은 반영하지 않는다. 재점검에서 새 지적이 나오면 다시 분류표로 제시해 승인받는다. 승인분 수정은 **7단계 커밋에 함께 포함**한다(6단계는 아직 첫 커밋 전이라 합쳐 커밋 — 9단계는 답글용 해시가 필요해 작업별 개별 커밋).
- **지적이 0건(또는 모두 거절)이면** 분류표 없이 바로 7단계로 진행한다.
- 이 6단계는 **로컬 reviewer** 대응이고, 원격 PR 리뷰(Copilot·사람) 대응은 9단계(`/apply-review`)다.

### 7단계: 커밋

- 포맷 확인(`./gradlew spotlessCheck` 등) 후, 팀 규칙 `[Type] #<번호> 요약` 형식으로 커밋한다.

### 8단계: PR 초안 (/pr)

- `/pr` 커맨드로 PR 초안(제목 · 본문 6섹션 · assignee · 라벨 자동 매핑)을 만든다. base는 `develop`, **바로 리뷰 가능한 PR**(Draft 아님).
  `✅ 테스트` 칸은 비워 두고, 5단계 `/test` 결과를 붙여 채운다.

### ⏸ 승인 게이트 2 — PR 업로드 승인

- 초안을 제시하고 **사용자 승인 후에만** PR을 생성한다.

### 9단계: 리뷰 대응 후 머지 (/apply-review)

- **이 프로젝트는 PR 생성 시 GitHub Copilot 코드 리뷰가 항상 자동으로 달린다.** 따라서 사이클은 PR 생성으로 끝나지 않는다 — **Copilot 리뷰가 달릴 때까지 기다렸다가** 반드시 대응한다. 추가로 사람 리뷰가 달리면 그것까지 대응한다.
- `/apply-review <PR번호>` 로 대응한다: 분류표 → ⏸ 사람이 건별 수용/거절 결정 → 수용 건은 **작업별 개별 커밋** 후 그 커밋 해시로 답글, 거절 건은 사유 답글.
- 모든 리뷰(Copilot + 사람) 대응이 끝나고 **CI(`ci.yml`)가 그린**이면 **PR을 머지**한다. CI 실패 시 실패한 step을 고쳐 push하고 재확인한다.

## 원칙

- 두 승인 게이트(플랜 / PR)는 **절대 건너뛰지 않는다.**
- **리뷰 지적(6단계 로컬 `reviewer` · 9단계 PR 리뷰)은 사용자 승인 후에만 반영한다** — 분류표로 제시하고 건별 수용/거절을 받으며, 임의로 미리 반영·커밋하지 않는다.
- **사이클 완료 기준 = PR 생성이 아니라 "리뷰 대응 + 머지"까지.** 9단계(리뷰 대응)를 건너뛰지 않는다(Copilot 리뷰는 항상 달린다).
- **`/review-pr`(남이 올린 PR을 리뷰)는 이 사이클에 포함되지 않는다** — 내 작업 사이클과 무관한 독립 커맨드다.
- 각 단계로 넘어갈 때 무엇을 할지 한 줄로 알리고 진행한다.
- 팀 컨벤션은 `docs/backend-convention.md`(단일 출처)와 `CLAUDE.md`(아키텍처)를 따른다.
