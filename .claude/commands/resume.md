# /resume — 세션 재개 오리엔테이션 (read-only)

끊긴 세션을 다시 시작할 때, 저장된 작업 메모와 git 상태를 **읽기만 해서** 진행 상황을 파악하고 다음 작업 1개를 제안하는 **read-only 오리엔테이션 커맨드**다. 코드/커밋/브랜치를 바꾸지 않으며, 실제 구현은 `/dev-cycle`로 위임한다. 메인 컨텍스트에서 실행되므로 대화 맥락을 살린다.

## 절대 규칙

- **코드·커밋·브랜치를 변경하지 않는다.** 상태 파악(읽기)과 안내만 한다. 실제 구현은 `/dev-cycle`로 위임한다.
- 추측으로 진행 상황을 단정하지 않는다. 파일·git에서 확인한 것만 보고한다.

## 진행 순서

### 1단계: 작업 맥락 메모 읽기

- `.claude/claude-progress.txt`를 읽어 직전 작업 맥락(지금/직전/다음/막힌 점)을 파악한다.
- 파일이 없으면(첫 세션) **사용자가** `.claude/claude-progress.txt.example`을 복사해 만들도록 **안내만 한다**(직접 생성하지 않음).

### 2단계: 작업 항목·상태 읽기

- `.claude/feature_list.json`을 읽어 `items`의 상태(`todo`/`doing`/`done`)를 파악한다.
- 없으면 **사용자가** `.claude/feature_list.json.example`을 복사해 만들도록 **안내만 한다**(직접 생성하지 않음).

### 3단계: git 현황 확인

- `git status`, `git branch --show-current`, `git log --oneline -10`으로 현재 브랜치·미커밋 변경·최근 커밋을 확인한다.

### 4단계: 개발 서버 실행 안내

- 필요 시 빌드·개발 서버 실행 방법을 안내한다(`AGENTS.md`의 빌드·테스트 명령 참고). 실행 여부는 사용자가 판단한다.

### 5단계: 다음 작업 1개 선정

- feature_list에서 **`doing` 항목을 우선**, 없으면 `todo` 첫 항목을 다음 작업으로 제안한다.
- 그 작업이 GitHub 이슈와 연결되면(`issue` 필드) `/dev-cycle <번호>`로 이어갈 수 있음을 안내한다.

### 6단계: 컨텍스트·포크 안내

- 컨텍스트 사용량이 **40%**를 넘으면 진행 메모(progress/feature_list)를 갱신해 정리하고, 포크하거나 새 세션으로 이어갈 것을 안내한다.

## 보고 형식

1. 직전 맥락 요약(progress 기반) 2~3줄
2. 작업 항목 상태 요약(done/doing/todo 개수 + 현재 `doing` 항목)
3. git 현황(브랜치 · 미커밋 변경 · 최근 커밋)
4. **제안하는 다음 작업 1개** + 이어가는 방법(`/dev-cycle <번호>` 등)

## 원칙 — `/resume` vs `/dev-cycle` (역할 분리, 중복 0)

- **`/resume`**: 세션 재개 시 **상태 파악 + 다음 작업 선정까지**(read-only 오리엔테이션). 코드/커밋/브랜치를 변경하지 않는다.
- **`/dev-cycle <번호>`**: 선정된 **이슈 1개를 구현→test→커밋→PR→머지까지** 실행하는 사이클.
- → `/resume`으로 "다음은 #N" 을 파악한 뒤 `/dev-cycle N`으로 진행한다. 둘은 짝을 이루며 기능이 겹치지 않는다(`/resume`의 git 조회는 "현황 보고용", `/dev-cycle`의 조회는 "각 단계 실행 입력용").
- 작업 메모(`feature_list.json`/`claude-progress.txt`)는 **기기 로컬 개인 데이터**(gitignore)이고, 제품 SSOT는 GitHub 이슈다. 오래 가는 교훈·환경 사실은 메모리에 둔다(→ `docs/ai-workflow-guide.md` 6.2절 역할 경계 참고).
